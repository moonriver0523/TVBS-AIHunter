# 自動寫稿(CTV)

當使用者只給一組 CNN Newsource story ID（例如「WE-018FR」）並以此名稱呼叫時，自動執行以下完整流程，不需逐步詢問許可，但需在過程中回報找到/需留意的事項（禁運期、限制等）。

**開始前必讀**：[`common/00-寫稿通則.md`](../common/00-寫稿通則.md)（版權、單位換算、**數字寫法**、**寫稿前事實分層**、**SB 五行格式**）與 [`common/08-execution-efficiency.md`](../common/08-execution-efficiency.md)（瀏覽器操作、額度禁令、下載重試）。本文件另規定 CTV 特有的「只為 SB 定位 TC、不把官方稿／ASR 全文灌進對話」省 Token 流程。

**Rollback：** 省 Token 改寫前的完整舊版保存在 [`_archive/cnn/01-auto-script-writing.pre-token-saving-2026-07-20.md`](../_archive/cnn/01-auto-script-writing.pre-token-saving-2026-07-20.md)。

## 檔名命名規則（2026-07-20 訂定）

下文所有 `<ID>` 皆代表輸出檔案的檔名前綴，依使用者下指令時是否提供 SLUG 決定：

- **使用者有明確提到 SLUG**（例如「幽浮檔案1600」）：以該 SLUG 作為檔名前綴（例如 `幽浮檔案1600 原始文稿.txt`、`幽浮檔案1600.mp4`、`幽浮檔案1600 完成文稿.txt`），**不使用 CNN 素材編號命名**。
- **使用者未提到 SLUG**：沿用原本規則，以 CNN Newsource story ID 作為檔名前綴（例如 `WE-018FR 原始文稿.txt`）。

## 省 Token 核心流程（優先遵守）

1. **官方稿只抓一次、立刻落地**：≡Q Preview 全文抓到後，直接寫 `"<ID> 原始文稿.txt"`。後續只讀這個檔，不要重開 Preview、不要把 SUPER／LEAD IN／全稿貼進對話。
2. **對話只回摘要，不回全文**：步驟過程只回報 ID、Title、Source、Embargo／限制、TRT、Reporter、受訪者人數與必要警示。**不要**在對話重貼原始文稿、ASR 全文或逐步截圖 walkthrough。
3. **下載確認用檔案系統**：輪詢 `D:\Downloads` 的檔名／暫存檔大小；不要截圖確認下載進度。卡住時依 [`common/08-execution-efficiency.md`](../common/08-execution-efficiency.md) 的**統一重試階梯**處理（CTV 屬「單支任務」，確認失敗後直接回報使用者，不無限重試）。
4. **TC 只服務 SB，不服務 OS**：完成文稿只有 SB 需要 `MMSS-MMSS`；OS 旁白不對 TC、不取樣畫面。
5. **先抽 SB 句，再跑／查 ASR，不要整支片當閱讀材料**：
   - 從 `"<ID> 原始文稿.txt"` 抽出全部可用的 SOT／SOUNDBITE／受訪者引言英文句（這才是要 TC 的集合）。
   - 同一支片 **`video_analyze`（`transcription: true`）只跑一次**；結果若很長，落地存 `"<ID> ASR.txt"`（可與完成檔一同上傳或暫存工作目錄），**不要把整份 ASR 貼進對話**。
   - 對每句 SB 取 5–10 個關鍵字（專有名詞、數字、特殊詞優先）→ 在 ASR 裡命中 → **只核對命中位置前後約 5 秒** 決定起訖。
   - 寫稿 context **只保留**「SB 英文原文 + 起訖 TC」對照表。
6. **用字以官方稿為準**：ASR 只用來定位時間；SB 英文與發言者姓名／職稱一律信官方稿／SUPER 8。ASR 有同音錯字仍可定位，但輸出不得照抄 ASR 錯字。細節同 [`cnn/02-clip-bite.md`](02-clip-bite.md)。
7. **原則上不取 frame**：SUPER 8 已提供姓名+職稱時不要截幀；只有發言者身份在官方稿仍無法確認時才取樣畫面。
8. **同一 ID 不重跑分析**：追加改稿、補 SB、重出完成稿時，沿用既有 `"<ID> ASR.txt"`／先前分析結果，不重新 `video_analyze`。
9. **最終交付精簡**：對話以完成文稿路徑＋禁運／限制／「用了幾個 SB／有無 SB 無TC」為主；完整內容在檔案裡。
10. **完成版先交付，不預設啟動第二審（2026-07-21 訂定）**：寫稿階段本身完成事實分層、SB／TC 對照與**步驟 6.5 的 `--mode ctv` 驗證關卡**後，直接把這一版視為「完成版」交付；**不要預設另派 agent 重讀官方稿、ASR、完成稿與整份規則做深度審稿**。只有使用者明確下令「檢查／複核／校稿／嚴格審稿」時，才啟動第二輪語意審查。若寫稿前真的存在會改變事實的姓名、金額、歸因或畫面判讀矛盾，應在寫稿階段先釐清或標註，不可把問題留給事後複查。

## 步驟 1 — 找到該則並取得**完整官方稿件**（關鍵，不可省略）
在 CNN Newsource（newsource.ns.cnn.com）搜尋該 ID，開啟該則展開的詳細框（Story Number、Title、Description、Source、Embargo、Footage Type、TRT、Reporter、Script）。

⚠️ **CNN Newsource 不支援用網址直接搜尋**（2026-07-21 使用者確認）。`https://newsource.ns.cnn.com/search?q={ID}` 會回 **Page Not Found**，只能在網站上方搜尋欄輸入。這點與 Reuters／AP 相反，不要套用它們的網址查詢做法。送出後若整頁凍結，見 [`../common/09-known-issues.md`](../common/09-known-issues.md#cnn-newsource)。

⚠️ 此展開框裡精簡的「Script」欄位**經常只是佔位符**（例如「*EDITORIAL INFORMATION PROVIDED BY [source]*」），**不是**完整稿件，不要誤用。真正完整的稿件（SUPER 8 姓名/職稱清單、LEAD IN、完整記者包裝含所有旁白與 BITE）在「Media:」列旁的 **「≡Q」icon** 後面（會開啟一個「Preview」彈窗，左側播放器、右側為完整稿件文字，可捲動）。

務必先點這個 icon、捲完整份稿件再做任何事——漏掉這一步會導致完全依賴 ASR 寫稿，受訪者姓名／職稱必定出錯或籠統（案例見 [`../common/09-known-issues.md`](../common/09-known-issues.md#規則由來案例歷史紀錄)）。

搜尋 → 開詳情 → 點 ≡Q → 捲完取文：連續動作能 batch 就 batch；全文取得後立刻進入步驟 3 存檔，不要在對話貼全文。

## 步驟 2 — 下載影片
先回報步驟 1 找到的禁運/限制事項（一句話摘要即可），再點下載圖示，選擇格式 **H264 HD NTSC**（網站會記住上次選擇）與位置 **D:/Downloads**（同樣會記住）。

⚠️ **CNN Newsource 的下載不會出現在 Chrome 的下載清單（2026-07-21 訂定）**：它是交給**背景下載程式**處理，完成後檔案直接出現在 `D:\Downloads`，Chrome 從頭到尾不會跳任何下載提示或進度條。

**所以「Chrome 沒跳下載」不等於沒下載成功，絕對不可以據此枯等或判定失敗。** 一律直接用 PowerShell 查 `D:\Downloads`（精確 filter），這是唯一可信的判斷依據。

⚠️ 這一點與 [`common/08-execution-efficiency.md`](../common/08-execution-efficiency.md) 的**額度鐵則**直接相關：誤判成「沒下載成功」而再點一次 Download，就是拿會消耗額度的動作做無謂重試，正是該鐵則禁止的行為。**沒看到 Chrome 有反應時，先查檔案系統，不要重點。**

下載為伺服器端排隊處理，需輪詢 `D:\Downloads` 中的暫存/工作檔（`#chkpt_file#...`、`#work_file#...`）確認檔案大小是否持續增長；若卡住（多次輪詢檔案大小不變），回報給使用者，不要無限重試。

## 步驟 3 — 將完整官方稿件存為「原始文稿」
把步驟 1 從 Preview 彈窗取得的完整稿件文字（SUPER 8 名單、LEAD IN、完整記者包裝旁白+BITE、END、KEYWORD TAGS）存成 `"<ID> 原始文稿.txt"`，前面加上 Story Number/Title/Description/Source/Embargo/Footage Type/TRT/Reporter 等 metadata。此為使用者內部參考副本，非對外散布。

存檔後，後續步驟**只讀這個檔**；不要重抓 Preview，也不要在對話重貼全文。

## 步驟 4 — 重新命名下載的影片
將下載的檔案（原始檔名通常是系統產生的長檔名）重新命名為 `"<ID>.mp4"`。

## 步驟 5 — 只為 SB 定位精確 TC（省 Token 版）

官方稿件本身通常沒有時間碼；**只有受訪者 SB 需要 TC**，OS 旁白不需要。

⛔ **鐵則：官方稿有引言，完成文稿就必須有 SB（2026-07-21 訂定）。** 步驟 1 取得的官方稿裡，凡是 `講者姓名／職稱：引言`、`SOT:`、`SOUNDBITE:` 形式的句子都是可用 BITE，**必須全部盤點**，再依新聞價值取捨要出哪幾句。**一篇 0 段 SB 的 CTV 稿不是完成版**：

- 若步驟 1 抓到的官方稿**不完整或尚未上架**（只有 `*EDITORIAL INFORMATION PROVIDED BY…*` 之類佔位符），就**不可以先交一份沒有 BITE 的稿並稱之為「完成文稿」**。此時要嘛回頭補抓完整官方稿，要嘛明確標為「暫存版／等待官方稿」並向使用者說明缺什麼，不得以完成版交付。
- 只有官方稿確實通篇沒有任何引言（純 B-ROLL／VO 素材）時，才允許 0 段 SB，且必須在交付時明講。
- 這一條在步驟 6.5 由驗證器強制：`--mode ctv` 對 0 段 SB 直接判 `[FAIL]`；加上 `--source-script` 時，還會回報官方稿有幾句引言、哪幾句沒用到。

### BITE 最短可用長度與「語意完整」取捨（2026-07-21 訂定）

**「有 SB」不是目的，「SB 說得完一件事」才是。** 上方的鐵則要求盤點官方稿全部引言，但盤點完是要**取捨**，不是全部塞進去。

| 單段 SB 長度 | 處理 |
|---|---|
| **< 3 秒** | **不得單獨成 SB**（驗證器直接 `[FAIL]`）。這種長度放不進一個完整意思，改寫進 OS 敘事即可 |
| **3~4 秒** | 驗證器給 `[WARN]`。可以用，但要能說明它是完整句、且比改寫成 OS 更有價值 |
| **≥ 4 秒** | 正常範圍 |

取捨準則（比秒數更重要）：

1. **英文原句必須是官方稿裡的完整一句**——從句首到句末的 `.`／`?`／`!`。不可只截半句，也不可把兩句拼接成一句。
2. **純情緒反應、感嘆、無資訊量的短句不要獨立成 SB**。例如 `爆紅浣熊1600` 官方稿裡的 `"what am I looking at?"`、`"Almost a little supernatural."`——這兩句適合改寫成記者 OS 的敘事起手式，不是 BITE。
3. **寧可少一段 SB，也不要湊碎句**。該案初版硬塞 1 秒的「我到底在看什麼」，使用者直接退回：「BITE掐太短了」。
4. TC 要**跟足整句**，不要為了壓秒數在句子中間切斷。

> 這一節與 [`common/07-bite-assistant.md`](../common/07-bite-assistant.md) 方式2 的「2句話或10-20秒，上限25秒」**不衝突**：那是 CNN 六碼側錄（整節新聞側錄，句子長）的規格；CTV 是 1~2 分鐘的 PKG 包裝，單句本來就短，適用本節的 3 秒下限。

> 本節的找 TC 做法若與 [`common/07-bite-assistant.md`](../common/07-bite-assistant.md) 不一致，**一律以 `07` 為準**；此處只是 CTV 情境的具體展開。

0. **先檢查 `--SUPERS--` 區塊本身有沒有附 TC**（部分較短的 DONUT/PKG 稿件會在每位受訪者名字/職稱下方直接列一組 `MM:SS - MM:SS`）。若某位受訪者在完成文稿中**只引用一句**、且 SUPERS 剛好有列對應 TC，可直接採用該 TC，**不必再跑 `video_analyze`**。但 SUPERS 通常只標「該人物第一次出現」的一組 TC——若同一人要引用不只一句，或 SUPERS 完全沒附 TC，仍需下列步驟 1–2 跑 ASR 補齊其餘句子。
1. 讀 `"<ID> 原始文稿.txt"`，抽出全部可用的 SOT／SOUNDBITE／受訪者引言（保留官方英文用字與對應發言者）。
2. 若步驟 0 判定仍需要 ASR：對 `"<ID>.mp4"` 呼叫 claude-video-vision：`video_analyze`，`filters: { transcription: true }`。**同一支片只跑一次**；輸出過長時寫入 `"<ID> ASR.txt"`，不要整份貼進對話。
3. 對每句要出的 SB：取 5–10 個關鍵字 → 在 ASR 結果命中 → 只核對前後約 5 秒，取起訖秒數，編成 `MMSS-MMSS`。
4. 產出精簡對照表即可進入寫稿，例如：`發言者 | 官方英文句 | MMSS-MMSS`。不要把整份 ASR 或整份官方稿再餵進寫稿 context。
5. 英文用字與姓名／職稱以官方稿／SUPER 8 為準；ASR 僅供定位（同 [`cnn/02-clip-bite.md`](02-clip-bite.md)）。
6. 只有官方稿仍無法確認發言者身份時，才額外取樣畫面（通常不需要）。
7. 若某句確實無法可靠對到 ASR，標「SB 無TC」，**不要捏造 TC**。

## 步驟 6 — 撰寫完成的台灣播出格式文稿（「完成文稿」）

### 寫稿前先完成事實分層

**依 [`common/00-寫稿通則.md`](../common/00-寫稿通則.md) 的四層分類與原文精度守則**（2026-07-21 由本流程升為通用，SOT／掃帶入庫同樣適用），本文件不重述。

CTV 專屬的一點：完成事實分層後**直接寫出完成版**，後續只跑字數、格式、TC 等確定性腳本，**不預設再做完整語意審稿**（見上方省 Token 第 10 條）。

- 繁體中文，口語化電視新聞語感——不是逐字直譯。
- 忠於原始素材——不可添加原文沒有的事實。
- 精簡用詞，短句、明快節奏。
- 保留所有可用的受訪者 BITE/SB，翻譯成自然的台灣觀眾語感。
- 每個 SB 都必須附上 **TIMECODE**，寫在五行格式的**第 4 行**，格式為緊湊的 `MMSS-MMSS`（例如 `0006-0013`），取自步驟 5 的定位結果——絕不可捏造。若某段確實找不到可追溯的 TC，該行標註「SB 無TC」。
- 姓名/職稱/機構：使用步驟 1 官方 SUPER 8 名單裡的確切姓名/職稱。**無論是開頭的 SUPER 清單或內文每個 SB 標籤，一律「中文職稱 + 英文姓名」**，例如「Cupertino Electric現場作業總監 Nick McComb」——**不要**額外加上中文譯名（不要「尼克·麥科姆（Nick McComb）」這種寫法，英文姓名直接跟在中文職稱後面即可）。若官方稿件已提供姓名/職稱，不要自行猜測或籠統帶過。**職稱精簡（2026-07-20 訂定）**：不堆砌非必要修飾詞（例如「哈佛大學科學教授」精簡為「哈佛大學教授」、「明尼蘇達州第211航空團聯絡官」精簡為「211航空團聯絡官」，只要不影響識別即可省略）；英文暱稱（如 `"Avi"`）預設整段省略，不需要用 `""` 特別保留，除非該暱稱本身是識別受訪者的關鍵資訊。
- 避免大量 Markdown 格式，僅使用下方指定的純文字結構。
- **斷行/標點規則（2026-07-13 訂定，2026-07-20 更新字數上限與引號規則）**：此輸出是「剪接上字用逐字稿」（字幕/上字參考稿），不是主播讀稿機稿，因此每行要能直接當字幕使用。斷行文字內部**去除所有標點符號**（不出現，。、！？等）。**SB 引言起始不加任何引號（不用「」也不用 `""`）**；記者 OS 與 SB 口白一律不使用「」符號，**只有內容中有需要特別強調之處，才在該處局部使用 `""`**（不是整段/整句包起來）。**口白（每段 OS 旁白、每句 SB 引言逐行）上限 14 個全形字，絕對不可超過。**（原先為 8–10 字目標／12 字硬上限，2026-07-20 校準為單一 14 字上限。）在自然的詞語/語意邊界斷句（不要斷在字詞中間、不要把英文專有名詞切開），盡量精簡，只有在找不到更短的乾淨斷點時才延伸到 14 字上限。此規則套用在完成文稿中的每一段 OS 旁白與每一句 SB 引言，**不適用於稿頭**（稿頭以單一整段文字呈現，見輸出結構第 1 項，不分句/不套用此斷行與字數上限）。

### 輸出結構（順序固定，格式力求精簡）
1. 一段約 100–150 字的口語化開場/主播稿頭，摘要事件核心、起因、影響與後續發展。**稿頭以整段連續文字呈現即可，不需要像口白一樣分句/分行，也不套用下方口白的 14 字斷行上限。**
2. `##` 分隔線，**下方空一行**再接 `SUPER:`（2026-07-20 訂定）。
3. **`SUPER:` 區塊** — 只列出**完成文稿中實際有引用 SB** 的受訪者，一行一位，格式為 `中文職稱 英文姓名`（同下方 SB 標籤規則——不加中文姓名譯名）。**原始文稿裡具名但這次沒有被引用 SB 的人物不列入**（2026-07-20 訂定）。**每行（中文職稱＋英文姓名合計）上限 18 個全形字**；職稱過長時精簡措詞，但不可省略關鍵資訊。**估算時英文/數字半形字約算 0.5 個全形字、中文全形字算 1 個**——職稱裡若要保留英文機構/公司名，一併把整段職稱換算長度，超過上限時優先把機構名也譯成中文縮短（不要只精簡中文修飾詞卻放任一長串英文機構名留在職稱裡），**寧可職稱整段用中文，也不要讓 SUPER 一行超長**。**受訪者若在官方稿中為匿名（只有 `SOT:` 沒有姓名/職稱，常見於路人／抗議民眾片段）**：仍要上 SUPER，但只放**中文通用角色描述**（例如「拉皮茲教區居民」），**不放英文姓名**；同一通用角色重複出現多次只需在 SUPER 區塊列一次，內文每處 SB 標籤仍照樣標示該角色描述（2026-07-20 訂定，實例見 SE-003SA）。
4. **BAR 字卡列表緊接在 `SUPER:` 區塊下方**：依序列出四張 BAR 的編號與完整文字（`BAR 1` / `BAR 2` / `BAR 3` / `BAR 4`）。**卡片中間可留一個空格，分成前後兩個語意半句**（headline 風格，例如「五角大廈再公布UAP解密檔案 疑氣球飛碟」），採電視字卡風格（非文學／書面語）。四張 BAR 的完整文字只在此處出現一次。字數規格見下方。

   #### BAR 字卡字數：17–18 全形字（2026-07-21 訂定）

   **每張 BAR 字卡文字為 17～18 個全形字——這是區間，不是「上限」，低於 17 一樣要改；而 18 是硬上限，絕對不可超過。** 2026-07-20 曾把它放寬成「上限 18、不必刻意湊滿」，理由是怕逼出湊字贅詞；`罕見四胞1600` 案證實這個放寬與播出需求不符（該篇初版 11／9／9／8 字全部被使用者退回），該放寬**作廢**。若寫不滿 17 字，正確做法是補進真正的新資訊（數字、地點、對象、後果），不是塞贅詞；若超過 18 字則必須刪減，**不得以「只多 0.5 字」為由放行**。

   > 本區間當日調整過三次：`固定 18` → `17–18` → `15–17` → **`17–18`（現行）**。看到舊值一律以本節為準。
   >
   > 本規則之前寫的舊稿（例如 `罕見四胞1600` 的四張 18 字 BAR）跑驗證會 `[FAIL]`，依 [`common/08-execution-efficiency.md`](../common/08-execution-efficiency.md) 的「規則異動不溯及既往」，**舊稿可以驗但不回頭修改**。

   適用條件與換算方式，逐項寫清楚避免再誤判：

   | 項目 | 規格 | 說明 |
   |---|---|---|
   | **BAR 1–BAR 4 字卡文字**（`SUPER:` 下方的四行完整字卡） | **17–18 全形字**（18 為硬上限） | 本規格只指這四行 |
   | `SUPER:` 每一行（中文職稱＋英文姓名） | **上限 18 全形字**（可以少於很多） | 見輸出結構第 3 項，沒有下限 |
   | 內文 `BAR1`–`BAR4` 定位標記 | 無字數規格 | 只是剪接定位標記，不重複字卡文字 |
   | OS 旁白／SB 中文口白每行 | 上限 14 全形字 | 見上方斷行規則 |
   | 自動寫稿(SOT) 的主標題／次標題 | 18–19 全形字 | **字數區間不同**（BAR 17–18），但 2026-07-21 起**換算方式與空格／半形標點規則與 BAR 相同**。見 [`common/06-auto-script-sot.md`](../common/06-auto-script-sot.md)；只有「幾個字」不可互套，「怎麼算」是同一把尺 |

   換算方式（與 SUPER 同一把尺）：**中文全形字算 1，英文／數字等半形字算 0.5，空格不計入字數**。半形字元個數為奇數時會出現 `.5`（例如卡片裡只有 `UAP` 三個半形字），只要落在 17～18 之間就合格。範例「五角大廈再公布UAP解密檔案 疑氣球飛碟」＝ 7＋1.5＋4＋5 ＝ **17.5，合格**。

   **字卡可用的半形字元（2026-07-21 訂定）**：

   - **半形空格最多 1 個**，就是分隔前後兩個語意半句的那一個；不計入字數，但不得出現第二個，也不得用全形空格代替。
   - **半形標點只准用 `!`、`"`、`+`、`:`、`.` 這五個**。其餘半形標點（`,` `?` `-` `/` `%` `(` `)` 等）**一律不得出現在字卡上**。`.` 專供數值簡寫使用（`5.7萬`、`950.3萬`，見 [`common/00-寫稿通則.md`](../common/00-寫稿通則.md) 的數字寫法），不是句末句號。
   - 半形英文字母與數字不受此限（機構名、型號、代號照常使用），一樣各算 0.5 個全形字。**數字一律優先用半形**，這同時讓字卡在同樣的播出寬度裡塞得下更多資訊。

   落檔前一律以 [`scripts/validate_sot.py`](../scripts/validate_sot.py) `--mode ctv` 實測，不得人工目測（見輸出結構第 8 項）。
5. **內文區的 BAR 只作剪接定位標記**：依序交錯排列 `BAR1` → 其 OS（記者口白，1–2 短段）→ **五行 SB 區塊** → `BAR2` → OS → 五行 SB → `BAR3` → OS → 五行 SB → `BAR4` → 結尾 OS。內文的定位標記固定寫成無空格的 `BAR1`、`BAR2`、`BAR3`、`BAR4`，**不可在內文重複字卡文字**。最後一個 `BAR4` 之後不再接 SB；全篇須以 OS 收尾，總結後續發展／影響／趨勢，不引入新事實。

   **SB 區塊統一用 [`common/00-寫稿通則.md`](../common/00-寫稿通則.md) 的五行格式**（2026-07-21 起與全 repo 一致，取代舊的 `SB <TC>` 三段寫法）。CTV 的 TC 欄位為純 4 碼 `MMSS-MMSS`、**不加來源前綴**：

   ```text
   SB
   {中文職稱} {英文姓名}
   {中文引言口白，可多行}
   {MMSS}-{MMSS}
   {官方稿英文原句}
   ```

   引言起始不加引號；僅內容中有需要特別強調之處才局部用 `""`。第 5 行英文原句逐字照抄官方稿，不斷行、不套字數上限。

   ⚠️ **中文引言口白可以佔多行（2026-07-21 訂定，取代舊的「第 3 行」寫法）**：解析時以 **TC 那行為界**：`SB` → 職稱姓名 → 中文（1 行以上）→ TC → 英文。全 repo 的 SB 都接受多行中文（見 [`common/00-寫稿通則.md`](../common/00-寫稿通則.md)）；**CTV 的特別之處是每行還有 14 全形字上限**——這跟上方的 OS 斷行規則是同一條，所以 CTV 的 SB 中文實務上幾乎一定是多行。

   ⛔ **中文必須完整對應英文原句，絕對不可為了通過字數檢查把翻譯砍成殘句。** 舊版驗證器把中文當固定單行，`爆紅浣熊1600` 案的寫稿代理因此把「看起來的確相當不尋常／但這其實是一種／其他哺乳類也會出現的狀況」壓成殘句「看起來特別其他哺乳類也會」，被使用者退回。**14 字是斷行單位，不是刪字理由。**
6. 不加任何 meta 說明（例如「以下是整理結果」），直接輸出完成的文稿。
7. 同一受訪者重複出現時，職稱+姓名格式需保持一致（SUPER 區塊與內文 SB 皆同）。
8. **（2026-07-20 訂定，2026-07-21 升級為交付關卡）落檔前必須跑 CTV 驗證，不要人工肉眼估**：見下方「步驟 6.5」。原本這裡只要求用臨時 `python -c` 加總 SUPER／BAR 字數；`罕見四胞1600` 案證實臨時腳本用固定行號抓文字會整段漏驗、且 PASS 不代表目標區塊真的檢查過，因此改為固定使用 [`scripts/validate_sot.py`](../scripts/validate_sot.py) `--mode ctv`。

## 步驟 6.5 — 交付前的 CTV 驗證關卡（2026-07-21 訂定，不可跳過）

完成文稿落檔後、進入步驟 7 上傳前，**一律跑這一關，且要跑到 exit code 為 0**：

```bash
python scripts/validate_sot.py "<ID> 完成文稿.txt" --mode ctv --source-script "<ID> 原始文稿.txt"
```

`--mode ctv` 檢查的項目：稿頭是否為單一整段、`SUPER:` 每行是否在 18 全形字上限內、四張 BAR 是否**各為 17–18 全形字、空格不超過一個、沒有用到白名單以外的半形標點**、內文 `BAR1`–`BAR4` 定位標記是否齊全且不重複字卡文字、SB 是否為五行格式（**中文可多行，逐行檢查**）、TC 是否為合法的純 4 碼 `MMSS-MMSS`（`SS` 不得大於 59）、**單段 SB 是否短於 3 秒**、OS 與 SB 中文口白是否都在 14 全形字內、SUPER 名單與內文 SB 標籤是否逐字一致、全篇是否以 OS 收尾、以及**是否至少有一段 SB**。給了 `--source-script` 時，另外比對官方稿的引言有沒有被漏掉，並確認每段 SB 的英文原句真的出自官方稿（防止照抄 ASR）。引言辨識支援兩種官方稿寫法：`講者: 引言` 與**整行被引號包住的引言**（CNN 的 TALAT／PKG 稿常用後者）。

改動驗證器之後一定要跑一次反例測試：`python scripts/test_validate_sot.py`（PASS／FAIL 兩種樣本都有，涵蓋多行中文、碎句、逐行字數、SOT 標題規則與引號式引言抽取）。

有 `[FAIL]` 就先改稿再重跑，**不得帶著 FAIL 交付**。`[WARN]` 不影響通過，但要看過並能說明（例如「官方稿還有 1 句引言未使用」要能講出是刻意取捨）。

三條由 `罕見四胞1600` 案訂下的紀律：

1. **不得自己寫臨時檢查代替這一關。** 該案用固定行號抽文字的臨時腳本漏驗了兩行 SUPER 與 BAR4，卻回報 PASS。驗證一律解析實際標記（`##`、`SUPER:`、`BAR n`、`SB`），不用行號猜位置——通則見 [`common/08-execution-efficiency.md`](../common/08-execution-efficiency.md)。
2. **不得拿不涵蓋 CTV 結構的工具充數。** 預設的 `--mode sot` 檢查的是主標／次標 18–19 字與總長度，跟 CTV 規格不同；SOT 模式跑出來的結果對 CTV 稿沒有意義。
3. **驗證要能對本案的錯誤亮紅燈才算數。** 交付前自問：這次跑的檢查，如果 BAR 少一字、如果一段 SB 都沒有，它會不會 FAIL？不會就是沒驗到。

這一關是確定性腳本檢查，屬於上方省 Token 第 10 條所說的「後續只跑字數、格式、TC 等確定性腳本」，**不是**它排除的那種「另派 agent 重讀全部素材做深度語意審稿」。
