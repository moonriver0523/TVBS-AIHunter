# 自動寫稿(業配) 前台化評估

- 日期：2026-08-31
- 目的：評估整條業配流程（寫稿＋製片）是否適合做成前台程式，讓非本人使用者也能操作，不必透過 Claude Code 對話
- 相關：[`common/19-auto-script-advertorial.md`](../../../common/19-auto-script-advertorial.md)（規則）、[`2026-08-21-advertorial-pipeline-design.md`](../specs/2026-08-21-advertorial-pipeline-design.md)（製片設計）、`scripts/bite_workbench.py`（既有前台先例：掐BITE工作台，非本 repo 內文件，記憶檔 `project_bite_workbench_handoff` 有交接紀錄）

## 一句話結論

**製片端**（盤點後的配音／剪接／上字／終檢）機械、確定性高，**可以**做成前台工作台，且已有 `scripts/production_advertorial/` 的 CLI 骨架可直接包成 API。**寫稿端**（讀需求單＋新聞稿、判斷停問、決定畫面取捨、口語改寫）需要 LLM 逐案判斷與大量停問互動，**不建議**做成純表單全自動，適合做成「AI 初稿＋人工線上編輯」的半自動介面，而不是一鍵產出。

## 現況盤點

業配全鏈目前的執行方式：使用者在 Claude Code 對話中交付案件資料夾，Claude 依 `common/19` 規則逐步問答、盤點、寫稿、驗證，最後手動呼叫 `scripts/production_advertorial/*.py` 串起製片。整條路徑**完全綁在對話 session 裡**，沒有獨立可執行的介面；換人操作等於要學會怎麼跟 Claude Code 下指令。

已有的可重用資產：

| 環節 | 現況 | 前台化難度 |
|---|---|---|
| 盤點（ASR＋分類＋編號） | 人工／Claude 呼叫 `video_analyze`，無現成腳本 | 中——邏輯簡單（列檔→ASR→分類），但目前是對話手動做，需另寫盤點腳本 |
| 寫稿 | 完全靠 Claude 讀需求單／新聞稿／素材清單，套 `common/19` 規則產出完成稿，中間常停問 | **高**——核心價值在「判斷」不在「產文字」：事實矛盾要停問、畫面取捨要對照素材、口語改寫要有品味，這些是 LLM-in-the-loop 的長對話，不是固定表單填一填就能出稿 |
| 製片（locate_sb→synth_os→build_video→make_subs→final_check） | 已是 5 支獨立 CLI 腳本，`sot_common.py` 有共用解析器，輸入輸出都是檔案／JSON，`final_check` 有明確 exit code | **低**——跟掐BITE工作台是同一類型：機械流程、有清楚成功/失敗判準，最適合先做前台 |

## 對照掐BITE工作台的先例

`scripts/bite_workbench.py`（FastAPI，port 8765）已證明「本機 Python CLI 腳本→瀏覽器工作台」這條路在本專案可行，且掐BITE／側錄初處理都是**機械式操作**（靜音偵測、OCR、裁切、播放核對），使用者用滑鼠點選就能完成，不需要 LLM 逐案判斷。業配的**製片端**性質跟這個先例幾乎一樣（丟檔案→跑腳本→看結果→下載），可以照同一套架構複製；業配的**寫稿端**性質完全不同（需要跨文件比對事實、需要跟人來回確認），硬套同一種「填表單→按執行」介面，等於把 Claude 現在做的判斷工作丟給沒有 LLM 輔助的前台去做，品質會明顯下降或大量卡在缺件/矛盾判斷上。

## 建議做法（分兩階段，不建議一次全包）

### 階段一：製片工作台（值得做，優先）

比照掐BITE工作台開一個新分頁／新服務：

- 輸入：完成文稿 `.txt`、素材清單 `.txt`＋原始影音（沿用案件資料夾結構）
- 後台依序呼叫 `locate_sb → synth_os → build_video → make_subs → final_check`，前台顯示每步進度與失敗原因（例如「OS 畫面總長 < 配音，已停手」）
- 輸出：完成帶下載連結＋`final_check` 結果
- 這段**不需要 LLM 判斷**，前台化後其他使用者可以自己重跑製片、修完稿重新產片，不必找 Claude
- 前提：先補上 spec 裡列的最小回歸測試（見 spec「測試」章節待辦），否則前台包出去後出錯不好排查

### 階段二：寫稿輔助台（可做，但範圍要縮小）

不做「上傳需求單就自動吐出完成稿」的全自動按鈕，改做：

1. 前台收需求單／新聞稿／散裝帶，跑盤點腳本（要先補寫，目前盤點是對話手動做），產出素材清單給人看
2. 呼叫 LLM（走現有 Claude API，非本機規則引擎）依 `common/19` 規則產生**初稿**＋列出所有「停問」項目，攤在畫面上讓使用者逐項回答／編輯，而不是在對話裡一來一回
3. 使用者確認或改稿後才進入階段一的製片流程
4. 這樣前台角色是「結構化呈現＋人工把關」，不是取代 Claude 的判斷，避免規則走樣（例如誤判「第二個訪問」、漏掉停問條件）

### 不建議

- 不建議把 `common/19` 的停問／事實比對邏輯寫死成前端規則引擎（if/else）——這類判斷情境多變（花蓮案例就出現 5 種以上停問情境），寫死很快就會漏case，且維護會跟寫稿規則本身脫鉤。
- 不建議跳過階段一測試缺口直接對外開放製片工作台，避免沒有回歸測試的腳本出包難排查。

## 工作量粗估（僅供排序參考，非精確估時）

| 項目 | 量級 |
|---|---|
| 製片工作台前端＋API（比照 bite_workbench 架構） | 中——大部分邏輯已在 CLI 腳本裡，主要是包 FastAPI＋做進度輪詢頁面 |
| 製片最小回歸測試（spec 待辦） | 小～中 |
| 盤點腳本化（目前無現成腳本，靠對話手動做） | 中 |
| 寫稿輔助台（LLM 初稿＋停問清單 UI） | 大——涉及呼叫 LLM API、設計停問互動介面、避免規則版本分叉 |

## 待使用者裁決

1. 是否同意先做「階段一：製片工作台」，寫稿仍留在 Claude Code 對話裡？
2. 若要做「階段二：寫稿輔助台」，是否接受它呼叫外部 LLM API（非本機規則引擎），連帶產生 token 成本？
3. 製片工作台要不要先補測試缺口，還是先出雛形讓你試用再補測試？
