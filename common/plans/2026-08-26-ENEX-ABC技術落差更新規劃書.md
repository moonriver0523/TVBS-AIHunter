### ENEX 時長問題：本次盤點已解決（原 §10 已知結構性缺口）

- 18 檔落差報告 §10 原記「ENEX 時長抓不到，三個候選解法都未定案」，其中一條路是查 `player.freecaster.com/embed/{uuid}.json`，但「uuid ↔ item 的對映尚未建立」。
- **2026-08-26 現場查證推翻此路線**：`player.freecaster.com` 只服務 ENEX LIVE 直播頻道，跟一般新聞素材（VOD）無關；不需要建立任何 uuid 對映。
- **實際解法**：ES `_search` 回應本身就帶 `videoLowResCdn`（CloudFront）／`videoLowRes`（S3）— 這是**公開、免登入、支援 Range 請求**的 mp4 直連網址。直接對它跑 `ffprobe -show_entries format=duration` 即可拿到精確時長，不需開瀏覽器、不需登入態、不需 cookie。
  - 驗證樣本：`_id=928358`，`ffprobe` 讀出 `duration=69.360000`，與瀏覽器 `<video>` 元素 `loadedmetadata` 讀到的 `69.36` 完全一致；`curl -I` 確認該 URL 對外公開（`200`／`Accept-Ranges: bytes`，非簽章網址）。
- **對規劃書的影響**：②`s2_batch_prep.py` 封裝時，時長欄位直接內建「拿 `videoLowResCdn` 跑 `ffprobe`」這一步即可，不必再等待或研究 uuid 對映；§10 這項缺口視為已解決，②項難度略降。

### ①登入態保活腳本：本次現場調查結果（ABC 已排除、ENEX 待長時觀察）

**ABC（`abcnews.extremereach.com`）：在已知手段下判定不可行，沒找到新解法。**

- 沿用 0811 已測過的結論：`ss-tok` 是 HttpOnly cookie，`document.cookie` 讀不到，載入頁面／打既有 4 支 XHR（`SearchMediaLoadFirst`／`SearchMedia`×2／`GetPriorityAlerts`）都不會觸發 `Set-Cookie`。
- **本次新查兩條路，都排除**：
  1. **登入頁有沒有「記住我」機制** → 沒有。表單只有 Username／Password／Recover Password 三個欄位，沒有 remember-me 選項，代表沒有「登入一次換長效憑證」這條路。
  2. **使用者指定測試 `https://abcnews.extremereach.com/adbridge/news/Delivery/NewsDeliveries`**（AdBridge 清單頁，就是 0810 計畫書 §A-1 端點契約鎖定的真實掃描目標頁）→ 一樣**沒有 `Set-Cookie`**，跟 CMS 首頁同一套 session 機制，沒有額外續期行為。
- **待查線索（非結論，未驗證用途）**：這個 AdBridge 頁面的 HTTP 回應多帶一個 `x-ab-username` header，內容是明碼帳號＋兩段疑似 token 的字串（`帳號;字串A;字串B`），例如 `k2ys0208@tvbs.com.tw;6FxauRhAtW6vRPyLPcEX;C5LeYeutnfeomZAgjON7`。**這是站方自己回傳的欄位，不是我方查探取得**，但沒查過這兩段字串是否可重複使用（例如當 API key 或短效簽章）。如果未來要繼續查保活這條路，下一步應該是追這個 header 在其他端點/情境下的行為，而不是重複測 Set-Cookie。
- **現階段結論**：ABC 保活在「被動續期」（載入頁面、打既有 API）這條路上判定不可行；剩下唯一選項是「定期真的重新登入」（存帳密自動化，非續期），這是使用者裁決題，本規劃書不建議動工。

📌 **2026-09-04 訂正（本節 ABC 結論作廢，ENEX 仍有效）**：0826 打的 4 支 XHR 是錯路徑（`/Media/SearchMedia`、`/Alert/GetPriorityAlerts`）。頁面真正打的是 `/Cms/SearchMedia/{customerId}?pageRegionId=…` 與 `/Notification/GetPriorityAlerts`。前者會 `Set-Cookie: ss-tok`（有冷卻）。NewsDeliveries 文件請求確實只動 `cmod`、不動 `ss-tok`——那一小段仍對。詳見 [0904 實測](2026-09-04-ABC保活ss-tok滑動續期實測.md)。

**ENEX（`members.enex.news`）：仍待長時觀察，本次未能定案。**

- Drupal 站台，重新整理頁面同樣不會回傳 `Set-Cookie`；但 Drupal session 常見是伺服器端依「最後存取時間」滑動計時，不一定要靠 `Set-Cookie` 才能延長效期——光看瀏覽器行為無法判斷是否滑動。
- 想直接讀 cookie 資料庫的 `expires_utc`／`is_persistent` 屬性來確認，但這個動作被系統分類器擋下（涉及登入憑證的本機檔案，判定為敏感操作，不強行繞過）。
- FAQ／Knowledgebase 頁面沒有記載 session 逾時時間。
- **結論**：ENEX 保活可行性**無法只靠這次即時查證定案**，需要實際放置一段夠長的時間（涵蓋懷疑的到期窗口）後再測試是否仍保持登入，才能判斷是滑動還是固定到期。
