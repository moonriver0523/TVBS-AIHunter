## 一、結論（先講，待實測確認）

**很可能可行，而且比 ENEX／ABC 那兩案單純**——因為 AP 的 API 在 `13b` §2 已經被打通過一次，
照片只是換一個 `mediaType`。三個沒把握的點都集中在「照片特有」的地方：

| # | 待確認 | 為什麼是關鍵 |
|---|--------|-------------|
| 1 | 關鍵字搜尋走哪支端點 | `13b` 打通的是 **topic**（Latest 清單）端點；照片流程是**關鍵字搜尋**，可能是另一支。`PageSize` 地雷是在 topic 端點實測出來的，**不可沿用結論** |
| 2 | `renditions` 有沒有可直接取用的 preview URL | 影片那邊 `renditions` 是雜訊大戶、規則寫「一律不取」；**照片這邊它就是本體**。有 preview URL 才做得到「先看圖再挑」 |
| 3 | ⬇ 下載是否計量 | 決定要抓 6 張全解析度、還是 preview 判讀後只下載 3 張 |

## 二、目前流程的痛點（為什麼要改）

現行 `06` §10／`ap/02` 是**純瀏覽器點擊流**：

1. `navigate` 到 `/home/search?query={kw}&mediaType=photo`
2. 讀列表卡片（`get_page_text` 或 snapshot）→ 判斷相關性
3. 逐張點卡片 ⬇ 圖示下載
4. 去 `D:\Downloads` 確認 `AP{ID}.jpg`
5. 改名成 `{簡短圖說}（圖／達志影像美聯社）.jpg`、搬到 `SOT自動寫稿測試\{SLUG}\`

痛點：

- **挑片是「讀文字」不是「看圖」**：目前靠 caption／標題文字判斷相關性，**agent 從沒真的看過那張照片**。
  構圖爛、主體不清、三張其實是同一個角度——這些只有看圖才判得出來，而 `06` §10 明文要求「三張要挑不同人物或不同場景」。
- **點擊流不穩**：`ap/02` 已記錄兩種已知失敗（點擊沒反應要去查 network log、媒體分頁會自己跳回 Video）。
- **改名是額外一步**：下載檔名固定 `AP{ID}.jpg`，要再對照哪個 ID 是哪張圖去改名。

## 三、目標流程（使用者設想 + 一處建議修改）

使用者設想：**API 一批抓 6 張以上 → 先下載 → AI 讀圖判斷對不對 → 挑最適合的 3 張 → 上傳資料夾**。

建議改成**兩段式**，其餘完全照使用者設想：

```
① 搜尋 API（1 次呼叫）
   └─ 回 N≥6 筆：editorialid / caption / 日期 / 限制欄位 / preview URL
② 下載 N 張 preview（低解析度，判讀用）
   └─ Read 工具逐張看圖 → 判相關性、主體、構圖、是否重複場景
③ 挑定 3 張 → 只對這 3 張下載全解析度
④ 直接用最終檔名落地 → 搬 SOT自動寫稿測試\{SLUG}\
```

> ✅ **2026-08-10 使用者已拍板採用兩段式**（「你的建議很好，照你建議做」）。以下保留原本的理由說明。

**為什麼是兩段式（原為建議，已獲裁示）**：
`ap/02` 已記錄兩種下載失敗都跟**額度／授權**有關（`MeterExpired_Shutdown`、
「content older than what you are allowed to download under your subscription」），
代表 AP 照片下載**是計量的**。若 6 張全抓全解析度，每篇稿的照片計量成本直接翻倍。
用 preview 判讀、只對選中的 3 張動用計量，可以**完整保留「先看圖再挑」的意圖，成本卻跟現在一樣**。

> ⚠️ **唯一的退場條件**：若 0-6 實測發現 preview 解析度低到判不出主體／構圖，兩段式就失去意義，
> 回到使用者原本的「直接抓 6 張全解析度」。
> （⬇ 若實測**不計量**，兩段式仍照跑——反正 preview 更省，只是不再有成本理由。）

## 四、不動的產出契約（API 版必須是 drop-in 替換）

以下全部沿用 `06` §10／`ap/02`，實作時不准簡化：

- 檔名 `{簡短圖說}（圖／達志影像美聯社）.jpg`（**不是** `{SLUG} #XX {來源}` 那套）
- 落地 `G:\我的雲端硬碟\Claude共用\SOT自動寫稿測試\{SLUG}\`
- 三張要**不同人物或不同場景**
- 找不到事件本身的照片 → 回報「無事件照片」，**不湊數**
- `MeterExpired_Shutdown` → **立即停止**，回報帳號授權問題，不換關鍵字重試
- 「content older than allowed」→ **不是**操作錯誤，換一張較新的候選，不重試同一張
- 關鍵字**要短**（1–2 字），0 結果才逐步拆解，不要一次疊多個限定詞
- 對話只回檔名 + 一句圖說 + 有無限制，不貼 Photo Metadata 全文

**API 版反而改善一處**：可以直接用最終檔名落地，省掉 `AP{ID}.jpg` → 改名那一步。

## 五、可沿用的既有事實（`13b` §2，影片實測所得）

- 端點主機 `https://api.newsroom.ap.org`，**cookie 驗證**（`session_user`，httpOnly，**7 天**）
  → 不需要讀 token，**沒有 NS 那種「token 不離開頁面 JS」的限制**，同源 `page.evaluate` fetch 即可
- 清單（topic）：`POST /v1/nrsearch/search/topic`
- 詳情：`POST /v1/nrsearch/search/item/details`，body `{"ItemIds":"{itemid}","mediaType":"video","IsNonSalable":false}`
  → **`mediaType` 是參數**，改 `"photo"` 很可能就是照片詳情
- 欄位：`_source.itemid`＝32 碼 GUID、`_source.editorialid`＝AP 編號（**裸數字，要自己補 `AP` 前綴**）、
  `caption.nitf`（一句話摘要，HTML）、`title`／`headline`／`dateline`／`firstcreated`
- **雜訊大戶** `renditions`／`filings`／`embeddings`：影片一律不取，**照片要重新評估**（見 §一 #2）
- 🔴 **`PageSize` 地雷**：topic 端點上「不論調大或調小都會靜默換掉排序」，只能照抄頁面的 `16`。
  **照片的搜尋端點是否有同樣行為未知**——一律「照抄頁面實際發出的 request body」，不要自己拼。

## 六、待實測清單（Phase 0，瀏覽器一空就跑）

按「從最緊的約束往外」排，**前一項沒過就不做下一項**：

- [ ] **0-1 登入態**：Playwright profile 是否還登著 AP。沒登就交給使用者手動登（agent 不得輸入帳密）。
- [ ] **0-2 抄請求**：開 `/home/search?query={短關鍵字}&mediaType=photo`，用 `browser_network_requests`
      抄下**實際發出的搜尋端點與完整 body**。確認是不是 `/search/topic`，還是另一支 keyword 端點。
- [ ] **0-3 分頁行為**：同一個 body 只改 `PageSize`（16 → 24），比對**回傳第一筆是否仍是最新**。
      若排序被靜默換掉 → 照抄 16 分批取；若穩定 → 一次取 N≥6 更省。
- [ ] **0-4 欄位盤點**：dump 一筆完整 `_source`，確認有沒有：
      - preview／thumbnail 的 rendition URL（**成敗關鍵**）
      - **限制欄位**（對應列表卡片的 ⚠️／Special Instructions）
        → 有的話，「無 ⚠️ 不開詳情頁」這條可以直接在 API 回應裡判掉，比現行流程更省
      - 型別欄位（`compositiontype` 之類）→ **PHOTO GALLERY 封面卡在 API 回應裡怎麼區分**
        （`ap/02` 記錄過搜尋只回一張紅底 GALLERY 標題卡的情形，那不是可用照片）
      - 攝影記者／`firstcreated`／`dateline`
- [ ] **0-5 preview 取得路徑**（決定架構，先試最便宜的）：
      1. 先試 **本機 curl 裸打** preview URL（不帶 cookie）。若 URL 自帶簽名參數就能取
         → 完全繞開跨網域取圖的問題，最乾淨。
      2. 不行才退回頁面內同源 fetch → base64 → 落地。
      - ⛔ **回傳值黑名單照舊**：`token`／`Bearer`／`Authorization`／完整 JWT／cookie 字串
        永遠不准出現在 `evaluate` 回傳值裡。圖片 URL、caption、編號是正常業務資料，照樣回傳。
- [ ] **0-6 preview 解析度夠不夠判讀**：實際 `Read` 一張 preview，確認判得出主體、人物、構圖。
      （判相關性／構圖大概 ~400px 就夠，但要實看確認，不要用猜的。）
- [ ] **0-7 ⬇ 打的是什麼請求 + 是否計量**：抓下載請求，確認可否在 API 流程重放。
      **測試下載壓在 1 張**——`ap/02` 本來就有「先測一張確認帳號能下載」的規則，直接拿它當本次實測額度。

## 七、導入計畫（分階段）

### Phase 0 — 上面那份清單（不改任何規則）
產出：把實測結果補進本檔附錄 A／B，端點契約定版。

### Phase 1 — 抽取白名單定版
照 `13b` 慣例寫 `slimPhoto()`，只留寫圖說與判讀需要的欄位。

- 工具呼叫次數與 token
- 計量消耗是否真的沒增加

### Phase 3 — 正式併入（**需使用者拍板才動規則**）
改 `ap/02-photo-search.md` 與 `common/06-auto-script-sot.md` §10，保留舊版 rollback 連結

## A-2 抽取白名單（草案）

```js
// ⏳ 欄位名全部待 0-4 dump 確認，現在是照影片版推的
const slimPhoto = (s) => ({
  id: 'AP' + s.editorialid,      // ⚠️ editorialid 是裸數字，一定要補 AP 前綴
  itemid: s.itemid,
  title: s.title,
  cap:  clean(s.caption && s.caption.nitf),   // 寫圖說用
  ts:   s.firstcreated,
  line: s.dateline,
  restrict: /* ⏳ 0-4 找限制欄位 */,
  preview:  /* ⏳ 0-4 找 preview rendition URL */,
  type:     s.compositiontype                  // ⏳ 用來排除 PHOTO GALLERY 封面卡
});
```

## A-3 Fallback 階梯（固定順序，不准跳步、不准重試同一步）

1. API 搜尋 → 取 preview 判讀 → 下載選中 3 張
2. API 搜尋成功但 preview 取不到 → 退回「用 caption 文字判讀 + 列表卡 ⬇」（＝現行流程）
3. API 搜尋整支失敗 → 完全退回 `ap/02` 現行點擊流
4. 出現 `MeterExpired_Shutdown` → **立刻停，不進下一階**，回報帳號授權問題
