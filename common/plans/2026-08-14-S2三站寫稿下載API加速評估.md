# 寫稿流程：三站成片下載能不能靠 API 加速

- 日期：2026-08-14
- 性質：**評估計畫，不是規則、不是授權實作**
- 範圍：現有「外電批次下載」／自動寫稿(SOT)／自動寫稿(CTV) 裡，**AP／RT／NS 整支成片**怎麼下
- 不包含：預覽片當成品、YouTube／X／DVIDS（那些已是 `yt-dlp`）、改收錄判準
- 對照：
  - 現行規則 [`reuters/05-batch-download.md`](../../reuters/05-batch-download.md)（2026-08-03 已訂 API 首選）
  - 今日預覽調查 [`2026-08-14-S2三站影片預覽API調查.md`](2026-08-14-S2三站影片預覽API調查.md)
- 這次**沒有**對成片 `tick`／點 NS Download／打 RT `/api/download/video` 真片

---

## 一、先講結論

**成片下載能再加速的空間不大，而且三站不一樣。**  
文稿定位 0803 已經 API 化；卡住的是「檔案本體怎麼離開網站」。今日把預覽通道摸清之後，**沒有挖到新的、可取代成片的 HTTP 直鏈。**

| 站 | 現行成片怎麼下 | 今日有沒有更快的 API | 寫稿能不能改用預覽片 |
|----|----------------|----------------------|----------------------|
| **AP** | 已是 API：`check` → `tick` → CloudFront 簽章 URL，合成點擊可用 | **沒有更快的。** 只能把多則 `Ticks` 一次送、平行拉 URL | 不行。預覽是 508p 浮水印 |
| **RT** | 文稿 API；**影片必須人手勢點 Download** | **沒有。** `/api/download/video` 仍不吃腳本點擊（回 ~8KB JSON） | 不行。`preview-url` 是播放器預覽，不是 HD |
| **NS** | 文稿 API；**影片走 Signiant**（`sig://`，無 HTTP 直鏈） | **沒有。** `videoPreviewUrl` 是 fusion 預覽 MP4，不是成片 | 不行。預覽≠上帶檔 |

最大的時間通常不在「找不到 API」，而在：**一支一支等數十～數百 MB 落地、RT／NS 還要真點按鈕、下完改名。**  
API 再挖一層，省不到「等檔案寫完」這段。

---

## 二、跟現行規則對齊（避免以為今天才發現）

`05-batch-download` 0803 已經寫死：

- **定位＋文稿**：三站 API 首選，失敗兩次退 UI。
- **AP 成片**：`downloadnr/check` 取 `ContentId`／`ContentRenditionId` → `tick` → `ClientMediaUrl`（約 15 分鐘有效）。合成 `a.click()` 可用。實測 96–188MB。
- **RT 成片**：同一支 `/api/download/video`，真點回影片、`evaluate` 裡 `a.click()` 回 transit JSON（缺 `Sec-Fetch-User`）。download 回應裡 `download-url`／`status-url` 是 `null`。
- **NS 成片**：`POST /api/v2/download` → `download/config/{id}` 給的是 Signiant，`transferapi.min.js` 搬檔。

今日調查**確認這三條結論仍成立**，並補上「預覽通道長什麼樣」，以免以後把預覽誤當成加速下載。

另：`05` 裡 AP「加大 PageSize」那段已過時，與 13c「PageSize 只能 16」衝突。這份評估**不改規則檔**；若修規則另開。

## 三、分站：還能動哪裡

### 3.1 AP — 已經是最快的一站

瓶頸不在找檔，在 **tick 之後等 MB 寫完**。

可做（低風險，未開工）：

1. **一次 `tick` 多則**：`Ticks` 本就是陣列（照片流程已這樣用）。寫稿一批 5–10 支可一次登錄，再平行 `fetch(ClientMediaUrl)`。要注意額度／`OverageAlert`。
2. **選對 rendition**：`check` 列出的是 HD Main（1080i50／i60／p，有的標題帶 Screener）。寫稿要 **Main 無浮水印**，不要拿今日的 `nrproxy` 508p overlay。
3. **不要**為了快去調 `PageSize`。

不可做：用預覽 MP4 充數；跳過 `tick`。

預估：一批 8 支，從「逐則 check+tick+等檔」改「一批 tick＋平行拉」，牆鐘或可少一半等待；**單檔傳輸時間差不多**。

### 3.2 RT — API 加速成片＝此路不通

今日補到的 `preview-url`（`/api/preview/video` → 簽章 CDN）是播放器用的。  
`renditions` 裡 `stream:700`／`2000`／`5128`／`1080` 的 url **全部是** `/api/download/video/…`，跟現在點的是同一扇門，腳本點仍會拿到假檔。

可做（不碰那扇門）：

1. 維持「文稿 API、下載真點」；點之前不要開多餘分頁。
2. 下完**必查檔案大小**（&lt;1MB＝假檔）——這條已是硬規則，執行面常被省。
3. 批次時一筆失敗就跳下一筆，不要重試合成 click。

不可做：再花一週挖 download 兩段式；用 700s／preview 當寫稿成片。

預估：**成片牆鐘幾乎省不下來**，除非以後站方改掉 trusted-click，或使用者接受預覽畫質（不建議）。

### 3.3 NS — 成片沒有 HTTP；預覽 URL 幫不上寫稿下載

今日確認清單就有 `videoPreviewUrl`（fusion `.mp4`）。那是 Preview 鈕在播的東西，**不是** Download／Signiant 成片。

可做：

1. 文稿繼續 stories API（記得用頁面那包 body，精簡包會 400）。
2. 成片仍點 Download，讓 Signiant 跑；不要幻想 fusion 直鏈是 HD 無浮水印母帶。

不可做：把 fusion 預覽當 `{SLUG} #XX CNN` 上傳片庫。

預估：下載本體無法 API 加速。省時間只在「少開 Preview modal 抓稿」（已經在省）。

## 四、寫稿流程裡真正還肥的（多半不是 API）

依 `05` 現行痛點，投報較高的是流程，不是新端點：

| 項目 | 為什麼肥 | 跟 API 的關係 |
|------|----------|----------------|
| 逐筆串行等下載 | 一支 100MB＋改名＋下一支 | AP 可平行拉；RT／NS 受按鈕／Signiant 限制 |
| RT 假檔重來 | 合成 click 靜默失敗 | API 救不了，只能驗大小 |
| 落點兩個資料夾 | PlaywrightMCP vs Downloads | 與 API 無關 |
| 改名 | 按鈕下載套不上自訂檔名 | AP `FileName` 可用；RT／NS 仍手改 |
| 開錯頁再搜一次 | `/home`→`/live`、RT 撞號 | 定位 API 已減，執行紀律問題 |

若要「整批寫稿變快」，優先序建議：

1. AP 批次 `tick`＋平行下載（唯一能明顯加速成片的）
2. 三站落地後自動驗大小＋改名腳本（不碰網站）
3. RT／NS 維持真點，不要再立 API 下載專案

---

## 五、預覽 vs 成片（寫進計畫以免以後搞混）

| | 預覽 | 成片（寫稿／上帶） |
|---|------|-------------------|
| AP | `nrproxy/getMAPIUrl` 508p overlay | `tick` Role=Main |
| RT | `/api/preview/video` | 真點 Download → `/api/download/video` |
| NS | `videoPreviewUrl` fusion | Signiant Download |
| 浮水印 | 通常有 | 通常無 |
| 計量 | 預覽通道不在 tick／download 目錄 | AP tick；RT／NS 下載動作 |

掐 BITE、對 TC、上傳片庫：**只用成片。**  
「先看畫面再決定要不要下」才用預覽——那是掃帶／選材，不是這份下載加速。

---

## 六、建議（未裁定不動工）

1. **AP**：可以排一小段「批次 tick＋平行拉＋驗 MB」的寫稿輔助腳本；沿用 `05` 的 check／tick 契約。
2. **RT／NS 成片 API**：標成 **不做**（與 0803 結論相同，今日再確認）。
3. **`05` PageSize 過時段**：另案改規則文字，避免下個 agent 為了下載去調 PageSize。
4. 預覽 API 留在掃帶／認畫面，不要接進 `{SLUG} #XX` 下載檔名。

要你拍板：AP 批次平行下載要不要做；RT／NS 是否接受「維持現況、只加強驗檔改名」。
