## 一、先講結論

S2 已不是「沒有自動化」，而是**外殼、狀態、渲染與稽核高度自動化，但三站資料進到狀態檔之前，仍有大量由 agent 即席搬 JSON、查欄位、拆卸載檔與寫臨時 `python -c` 的工作**。

目前最值得做的不是再縮一次規則，也不是直接寫三站全自動 collector，而是補齊兩個中間層：

1. **原始資料工具層**：把「卸載結果解包、欄位檢視、依 ID 篩選、產清單快照、轉 batch」收進 `s2_batch_prep.py`。
2. **輪次契約層**：用薄薄的 preflight／postflight 指令，將現有 `s2_state`、`s2_audit`、`s2_render` 串成可機械驗證的輪次狀態；不另做第二套 state parser。

最新兩輪顯示這個缺口很大：

| 輪次 | 新增 | 工具呼叫 | cache read | `python -c` | TaskCreate＋TaskUpdate |
|---|---:|---:|---:|---:|---:|
| 0812-1200 | 57 | 90 | 23.96M | 6 | 0 |
| 0812-1600 | 66 | 177 | 54.31M | 30 | 26 |
| 0812-1800 | 62 | 203 | 56.92M | 54 | 17 |

`s2_batch_prep.py` 已在 16:00／18:00 被呼叫 5／2 次，但臨時 `python -c` 反而升到 30／54 次，證明目前的 `dump`／`build` 只補到一部分。兩輪的 `python -c` 加 Task 工具分別占 **31.6%／35.0%** 的全部呼叫；而近兩輪每次工具呼叫約重讀 0.28M～0.31M cache token。這是眼前最大的可消除區塊。

## 二、S2 現行端到端流程

```text
Windows 工作排程器
  ├─ S2掃帶.xml ──> s2_scan.ps1 ──> Claude Code 工作 agent
  ├─ S2-NS保活.xml ──> s2_keepalive.ps1/js
  └─ 看門狗 ──> s2_watchdog.ps1 ──> 必要時代打 s2_scan.ps1

工作 agent
  1. 讀 13（內容規格）＋13c（現行執行規格）
  2. resume／scratch-dir／pending／needs-review
  3. 固定 NS → AP → RT 擷取清單與全文
  4. 原始回應瘦身、落 raw JSON、與 state 做 diff
  5. agent 做不可機械化的編輯判斷
  6. batch prep → add-batch／update-entry／set-category
  7. 整併人工投餵來源、分類收斂、標記已入庫
  8. 三站清單對帳＋audit＋topic review
  9. render txt＋HTML，自動 validate＋topic dedupe
 10. 最後摸 NS、關瀏覽器、寫 metrics、推播

狀態檔（唯一真相源）
  └─ {MMDD}-s2-state.json ──> {MMDD}晚班交接.txt／.html
```

### 2.1 排程與建檔

- 現行 9 輪：`01:00 / 04:30 / 07:30 / 10:00 / 12:00 / 16:00 / 18:00 / 20:00 / 22:00`。
- [`../../scripts/s2_scan.ps1`](../../scripts/s2_scan.ps1) 負責互斥鎖、checkpoint、16:00 建新 state、歸檔前一班、啟動 agent、收工檢查、metrics 與通知。
- 互斥鎖採 OS 獨佔檔案握把；撞鎖跳過不排隊。
- 16:00 的 `New-ShiftState` 已把建檔、前班產物歸檔、暫存歸檔、`_待整併` 舊檔歸檔機械化。

### 2.2 開工前狀態

- [`../../scripts/s2_state.py`](../../scripts/s2_state.py) 的 `resume` 回報總數、pending、上次 render 後變動、待人工與最近 checkpoint。
- `scratch-dir` 建立本輪中間檔目錄。
- agent 仍要判斷上一輪是否整站失守、pending 是否要補、是否有人工投餵檔。

### 2.3 三站擷取

| 站 | 首選路徑 | 必要的人類／LLM 判斷 | 主要脆弱點 |
|---|---|---|---|
| NS | landing 取 token；stories API 抓清單與全文 | GRAPHIC／形式、摘要、BITE、分類 | 1 小時 token、profile 互鎖、錯網址 |
| AP | Latest request body；`PageSize=16`；details 用 `Promise.all` | SNTV 例外、初稿、摘要、BITE、分類 | PageSize 靜默換排序、分頁／TopicId |
| RT | DOM 清單拿 guid／Edit No；item API 批次拿全文 | 舊稿重上、限制語、摘要、BITE、分類 | SPA 清單、回應格式漂移、超長整理包 |

正常路徑是 API／DOM 先瘦身再把必要欄位交給 agent；失敗則單向退階到 DOM 或 UI，不能在同一層反覆重試。

### 2.4 原始資料轉入 state

目前的實際鏈路是：

```text
browser_evaluate 結果
  ├─ 小：直接成 raw.json
  └─ 大：工具卸載成 tool-result 檔，agent 自行解包成 raw.json

raw.json
  ├─ s2_state diff
  ├─ s2_batch_prep dump（機械欄位盤點）
  ├─ agent 寫 entries.json（中文三段式＋判斷）
  └─ s2_batch_prep build → batch.json → s2_state add-batch
```

`entries.json` 的新聞摘要、BITE 翻譯、分類文字仍必須由 agent 做；這是合理的 LLM 核心。問題出在它前後的 JSON 搬運仍未完全腳本化。

### 2.5 整併與品質

- `s2_state.py` 已有批次新增、批次更新、批次分類、側錄、重大、已播、needs-review、精簡 show 等操作。
- [`../../scripts/s2_parse.py`](../../scripts/s2_parse.py) 自動推導結構化欄位。
- [`../../scripts/s2_audit.py`](../../scripts/s2_audit.py) 做 checkpoint、時段標記、BITE、分類、暫存、結構化欄位、品質掃及三站清單對帳。
- [`../../scripts/s2_topic_review.py`](../../scripts/s2_topic_review.py) 提供中／小分題視圖；語意合併仍由 agent 決定。
- [`../../scripts/s2_render.py`](../../scripts/s2_render.py) 從 state 全量原子渲染 txt，檢查手改、前後則數、reconcile、品質與跨分類重複，並呼叫 HTML 渲染。

### 2.6 收工與復原

- `s2_scan.ps1` 檢查本輪新增數、txt 是否存在、頂層 checkpoint 是否落後。
- [`../../scripts/s2_token_metrics.py`](../../scripts/s2_token_metrics.py) 從 session transcript 計 requests、工具呼叫、cache 與 output。
- [`../../scripts/s2_notify.ps1`](../../scripts/s2_notify.ps1) 與 keepalive 共用通知邏輯。
- [`../../scripts/s2_keepalive.ps1`](../../scripts/s2_keepalive.ps1)／`.js` 每 30 分鐘維持三站登入態，和掃帶共用鎖，連續跳過才警報。
- [`../../scripts/s2_watchdog.ps1`](../../scripts/s2_watchdog.ps1) 只處理「該輪根本沒開始」；目前不處理「已 START 但中途死亡」。

## 四、仍在浪費時間／Token 的位置

### 4.1 工具卸載檔沒有正式解包入口

18:00 輪遇到 browser 結果卸載後，先後用多次 `python -c` 試讀長度、前段、JSON 外殼與編碼，再轉成 raw。規則已說明三步怎麼做，但**知道步驟不等於已有工具**。

建議把它收成 `s2_batch_prep.py unwrap`：輸入 tool-result 路徑與站別，輸出規範化 raw JSON；失敗時回報外層格式與原始錯誤，不靜默吞掉。

### 4.2 raw JSON 缺少精準查詢介面

兩輪大量臨時指令是在做：列 keys、只看某幾個 ID、找某欄、印稿件前 N 字、檢查某字樣、取清單代碼、產稽核快照、比對 raw 與 batch。

`dump` 目前偏向一次印整批；資料一大，agent 就重新寫 `python -c`。應補：

- `inspect --ids … --fields … --limit …`
- `search --contains … --field script|story|head`
- `snapshot --out _audit_{site}_{HHMM}.txt`
- `compare --raw … --batch …`（只印缺 ID／欄位差）

### 4.3 state 的 `show` 還有查詢缺口

`show` 已能依 ids／分類／checkpoint 查，但兩輪仍直接讀完整 state 查 `source`、status、缺欄位、alert、前班資料。可補 `--source`、`--status`、`--id-prefix`、`--unclassified`、`--missing-field`、`--contains`，並讓 `resume --json` 可供其他工具組合。

### 4.4 固定輪仍使用不必要的 Task 工具

16:00 輪 `TaskCreate＋TaskUpdate=26`，18:00 輪為 17；掃帶 prompt 已禁止把工作轉包，但沒有阻止 agent 自建任務清單。這些呼叫不產生 S2 交付物。

在既有 Task 2 A0→A3 完成後，新增一個獨立 A4：**只排除 Agent／TaskCreate／TaskUpdate 類工具**，保留 Read／Write／Bash／browser。先跑輕量測試，再跑 TestMode；不要一次順便砍其他工具。

### 4.5 遙測分類仍有盲區

16:00／18:00 分別有 19／11 個 `s2_state:?`，無法知道它們是必要操作還是重複操作；全部 `python -c` 也只被放在同一桶。

先擴充 metrics：

- 認齊 `resume/pending/scratch-dir/set-top/needs-review/remove/set-mark/set-aired` 等子指令。
- 將 `python -c` 依用途分成 `read-state / inspect-raw / unwrap-tool-result / write-json / length-check / time-convert / other`。
- 依 NS／AP／RT／state／finalize 分階段計呼叫與時間。
- 每輪記 `prompt_sha`、`13_sha`、`13c_sha`、launcher flags，避免規則或啟動旗標改了卻誤判為腳本效益。

### 4.6 收工步驟有工具、沒有單一機械閘門

目前 agent 要自行依序跑 mark-ingested、audit、topic review、render、最後摸 NS。`render` 會警告 reconcile 缺漏，但外殼只檢查新增數與 txt，不知道 audit 是否完整跑過、三站 snapshot 是否為本輪、last render 是否晚於最後 state mutation。

建議新增**唯讀優先**的 `s2_round_gate.py`，只匯入現有模組，不重寫解析器：

- preflight：state 路徑、班次日、掃描窗、pending、needs-review、scratch、待整併檔、既有中主題。
- postflight：頂層 checkpoint、三站 reconcile、本輪 snapshot、未結案嚴重項、last render、txt/html/hash、對帳差異。
- 初版只產 JSON／文字報告，不自動修、不自動 render；穩定後才評估是否讓 launcher 依結果決定通知級別。

### 4.7 看門狗看不到「開了但死在中途」

現行看門狗以 run log 存不存在判斷未啟動。只要已 START／已建立 log，後面即使外殼或 agent 中途死掉，也不會代打。

候選做法：從 `_輪次紀錄.txt` 找 `START` 無 `DONE/CRASH` 且超過上限的 checkpoint，再確認互斥鎖已釋放、transcript mtime 已停止、state 未完成 postflight；先推播，第二階段才考慮用原 checkpoint 代打。不可只看 0-byte run log，也不可在鎖仍被占用時重跑。

### 4.8 排程資料有多個真相源

時刻同時存在於 `S2掃帶.xml` 與 `s2_watchdog.ps1 $Slots`；model／TestMode 也在主排程與看門狗各存一次。現在靠人工同步，曾發生取消輪次被看門狗補跑的風險。

先做 `s2_schedule_check.py` 唯讀比對即可，不急著重構排程：檢查 slots、model、TestMode、ExecutionTimeLimit、腳本路徑是否一致，任何差異回非零。

## 五、建議計畫（不含改規則）

### Phase 0：先把量測看清楚（0.5～1 天，零行為風險）

1. 擴充 `s2_token_metrics.py` 的子指令、臨時指令、站別／階段分類。
2. 新增 `s2_metrics_report.py`，讀既有 JSONL 產每輪／每站／每類工具趨勢。
3. 用 0030、0430、0730、1000、1200、1600、1800 歷史 transcript replay，確認分類總數與原工具呼叫數相等。

**驗收**：`s2_state:?` 降到 0；`python -c other` 低於 10%；報表能解釋 16:00／18:00 多出的呼叫去了哪裡。

### Phase 1：補 raw 工具層（1～2 天，低風險、最高投報率）

1. 在 `s2_batch_prep.py` 加 `unwrap/inspect/search/snapshot/compare`。
2. 所有新子指令只讀或寫 scratch，不直接動 state。
3. 用 16:00／18:00 已保存的 raw、tool-result、batch 做 replay。

**驗收**：

- 同一輸入 byte-level 重跑結果一致。
- raw → batch 的 ID／status／entry 與現有結果一致。
- tool-result 卸載檔只需 1 次 `unwrap`，不再探索編碼／外殼。
- `python -c` 由 30／54 降到 ≤10／≤15；格式與 audit 不退步。

**保守預估**：省 10～22% 工具呼叫；不是保證值，以上線後三輪 metrics 為準。

### Phase 2：補 state 查詢與輪次閘門（1～2 天，低至中風險）

1. 擴充 `s2_state show` 篩選，不增加第二套 parser。
2. 新增 `s2_round_gate.py` 唯讀 preflight／postflight。
3. launcher 先只記 gate 結果，不以 gate 阻斷正式輪。

**驗收**：agent 不再直接讀整份 state；preflight 可取代至少 3 個開工查詢；postflight 對歷史正常輪全通過、對 0811-1800／2200 類異常能命中。

### Phase 3：啟動工具最小化（併既有 Task 2，0.5～1 天）

1. 既有 A0→A3 照原計畫測。
2. 新增 A4，只排除 Agent／TaskCreate／TaskUpdate。
3. 一次只上一個變因，先輕量驗證，再 TestMode，再一輪正式輪。

**驗收**：Task 類呼叫歸零；必需 browser／Read／Write／Bash 仍可用；state delta、BITE、pending、audit 與基準一致。

**保守預估**：另省 8～15% 工具呼叫；不可與 Phase 1 百分比直接相加。

### Phase 4：排程一致性與中途死亡偵測（1～2 天，可靠性優先）

1. 先上 `s2_schedule_check.py`，只報不改。
2. 看門狗新增「START 無 DONE」偵測，第一版只通知。
3. 累積三次真實樣本後，才決定是否自動代打。

**驗收**：XML／watchdog 故意改一個 slot 時檢查必失敗；慢輪不誤判；鎖被占時絕不重跑。

### Phase 5：需使用者另行裁定的選項

- **無變動快速路徑**：三站 diff=0、pending=0、待整併=0、上一輪無失守時，是否允許跳過語意分類與全量 topic review，只做機械 reconcile／gate。這會改變現行執行行為，不能自行上線。
- **S2b C 通道排程化**：使用者已明確要求先人工跑幾天；觀察期未結束前不接進 22:00。
- **三站 collector**：既有修訂版已決定延後。API 漂移會造成靜默漏收；在 raw 工具層與 gate 穩定前不做。
- **規則分片**：沿用既有 Task 4，不在本計畫另造第二套。

## 六、哪些工作不該腳本自動決定

以下可以由腳本提供證據與候選，但不應直接替 agent 決定：

- 新聞是否收錄的編輯判斷（白名單／明確排除除外）。
- 中文一句摘要與三段式內容。
- BITE 的中文翻譯與講者敘述；`sb_count` 只能判斷「有沒有」，不能代寫內容。
- 大分類／中主題／小分題的語意歸位與同義合併。
- 🔴／🟡 重大程度。
- 登入帳密處理、站方限制語疑義、無法確定的來源內容。

省 Token 的正確邊界是：**腳本搬資料、算差集、驗格式、留證據；LLM 只做語意與編輯判斷。**
