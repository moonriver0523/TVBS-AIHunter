- 性質：**評估報告，不是規則、不是授權實作**（使用者當下明示「先別動手」）
- 觸發：使用者提案「機動 T 分類是否應該獨立出來，變成一組新的分類 TAG（也就是我們討論過的議題包分類），獨立於 T／C 之外，考量以後要延伸 AI 整理稿單、報稿，獨立出來也方便擴充」

## 一、先講結論

**方向正確，而且比提案本身更正確——`s2_special_t.json` 早就不是一個標籤了，它已經長成一個有生命週期的物件，只是還被塞在 T 這個純標籤的欄位裡。但如果三週內不會真的動 AI 整稿單，現在拆只是把補丁換個位置放。**

建議節奏：**現在只補資料欄位（零風險）→ 要做稿單時才拆資料層（P1）→ 稿單形狀定了再處理顯示層（P2）。**

判準一句話：**三週內會動 AI 整稿單就照 P1 拆；不會就只補欄位，其餘等。**

## 二、現況：機動 T 已經不是標籤了

`scripts/s2_special_t.json` 目前的形狀：

```json
{"name": "颱風", "charter": "颱風相關：路徑預報、災情、撤離收容…",
 "opened": "2026-08-25", "status": "active"}
```

`charter`（收什麼）、`opened`（何時開）、`status`（開／退場）——**這三個欄位沒有一個是標籤會有的東西**。固定 11 類的 T 不需要它們：政治永遠存在、不需要被誰開啟、也不會退場。

換句話說，機動 T 在資料上已經是一個 **story 物件**，只是被當標籤用。三個症狀已經浮上來：

### 症狀 ①：語義層級不同，統計因此不可比

T 是**封閉分類法**——11 類、跨日可比、每則必有其一。機動 T 是**事件實例**——會開會關、跨天延續、只有部分素材有。

兩者混在同一排 chip 上，於是「天災天氣 32 則」與「颱風 8 則」並列。它們不是同一個問題的答案：前者回答「這則是什麼類型的新聞」，後者回答「這則屬於哪一起正在發展的事件」。而且**後者是前者的子集**（0825 實測：颱風 8 則全部同時掛天災天氣），並列會讓總數看起來像是可以相加的，實際不能。

### 症狀 ②：`T_MAX` 需要一條豁免才成立

2026-08-25 上線的 T 數量上限（見 `TC-字典.md`「T 最多掛 3 個」那段）不得不寫進第 ④ 條：**機動 T 不佔這 3 格**。

理由當時記在 `s2_state.py` 的 `T_MAX` 註解裡：不豁免的話，已掛 3 個固定 T 的素材被 `_special_t_sweep` 點名「加掛颱風、原本的 T 要留著」，就會被自己的機制逼去違規。

**這條豁免是補丁。** 如果機動 T 本來就是另一條軸，它根本不需要存在——不同軸之間本來就不互相佔格。

### 症狀 ③：矩陣的第一格是硬排進去的

`s2_render_matrix.py` 的 `t_list` 把 📌 那幾格塞在固定 11 類**之前**，並且要額外處理「retired 但本頁仍有素材掛著」的情形（不處理那些素材會無格可放）。這段特例邏輯的存在，本身就是「它不屬於這條軸」的證據。

## 三、與 2026-08-19 議題包評估的關係

**這不是兩個提案，是同一個資料結構的兩種來源。**

[0819 那份](2026-08-19-S2報稿AI助理-議題包功能評估.md) 評估的是 **AI 事後生成**的議題包：收工前跑一次、用 entity 重疊粗篩＋LLM 判讀，把當天散在各分類的相關素材聚成「野火肆虐」這樣的包。

今天的提案是 **人工預先開設**的議題包：使用者當天下令開「颱風」，掃帶輪即時掛。

| | 0819：AI 生成 | 0825：人工開設（機動 T） |
|---|---|---|
| 誰決定有哪些包 | LLM 看完全天素材後判斷 | 使用者下令，⛔ agent 不自行新增 |
| 何時產生 | 收工前批次一次 | 掃帶當下逐則掛 |
| 準確度 | 靠粗篩＋語意判斷，會有偽陽 | 人工開的 charter，準 |
| 涵蓋率 | 高（沒人想到的也找得到） | 只涵蓋使用者當天想到要開的 |
| 現況 | 未實作 | **已上線，0825 起跑「颱風」** |

兩者的**輸出結構完全相同**：一個有名稱、有 charter、有成員 id 清單、有生命週期的物件。

所以真正的結論是：**S 軸不是為了今天的機動 T 而設，是為了讓人工開設與 AI 生成的議題包共用同一個容器。** 先有容器，AI 生成才有地方落地；沒有容器，0819 那份提到的「獨立議題包.json」跟現在的 `s2_special_t.json` 會變成兩份各說各話的東西。

這也回頭修正 0819 §3c 的建議：那時建議「走獨立檔案，比照 `s2_resident_topics.json`」——現在看，那個獨立檔案**就應該是 `s2_special_t.json` 的後繼**，不是另開一份。

## 四、獨立成軸的代價

### 4a. 顯示層有個沒答案的問題

矩陣是二維的（T×C）。S 是第三軸，**沒有地方放**。三個選項：

- **當篩選 chip**（側欄多一組）——最便宜，但失去矩陣的「一眼看出熱區」優勢。
- **另開一張表**（S×C 或 S×T）——資訊量足，但頁面變長，而且大多數日子只有 0–2 個 story，一張表為兩列而存在。
- **切換模式**（矩陣列首在 T 與 S 之間切）——最完整，工作量最大。

**這個決定得等你知道稿單長什麼樣才好下**，現在硬選會選錯。

### 4b. 交件端規則要再改一次

`14`（側錄）的 `→ T:… → C:…` 與 `17`（韓聯社／CNA／YT）的檔尾 `id=T/C;…` 都得再加一段 S。

⚠️ 但 `17` 那條產線的 T/C **到 0825 為止一次都還沒實跑過**（0816–0825 全部狀態檔零則 YNA／CNA）。**在還沒驗過的規則上疊新語法，等於同時開兩個未知數**——出問題時分不清是新語法壞了還是原規則本來就沒生效。

### 4c. 規則檔改動的節奏成本

2026-08-25 當天已經改了兩次必讀規則（T 併類與改名、T 上限）。同一批檔案一天內第三次改，對 agent 的遵守率有代價——當天光是「載入 ≠ 遵守」就踩了三次（T10、機動 T 漏標、`17` §10b）。

### 4d. 呼叫成本（可控，但有一個陷阱）

⛔ **不要開 `set-story` 這個新指令。** 每輪多一次工具呼叫 ≈ $0.11，一天 9 輪 ≈ **$1／日**。

✅ 正解：併進 `set-tc` 的同一批，格式擴充成 `id=T/C/S`（第三段可省略）。這樣呼叫次數完全不變、`TC_CALLS_PER_CHECKPOINT` 的上限也不必動。

### 4e. 既有資料要搬

0825 的狀態檔已有素材把「颱風」掛在 `tc.T` 裡。拆軸時要一次性搬到 `tc.S`。

⚠️ 搬的時候要留意 `s2_render_matrix.py` 對舊狀態檔的相容——比照墨西哥併桶那次的教訓：**歷史狀態檔重 render 時，被移走的值在矩陣上會無格可放**。所以 render 端要保留一段「T 裡出現 story 名稱時視同 S」的相容改寫，就像現在的 `normalize_t()` 那樣。

## 五、建議路線

### P0：現在就做（零風險，不動任何規則與流程）

只補 `s2_special_t.json` 的欄位，**不改任何程式行為**：

- `aliases`：`["納里", "浣熊"]`——0825 實測，`_special_t_sweep` 只比對名稱，所以「納里颱風」這種寫法掃不到，得靠 agent 自己想到。有了別名，漏標掃描的命中率直接提升。
- `related_mids`：關聯中主題（`["廣西水患"]`），未來 AI 整稿單的現成輸入。
- `closed`：退場日期（現在只有 `status`，看不出何時結束）。

**這一步的價值不在功能，在於資料先長成 story 該有的樣子**——等真要拆的時候，歷史資料已經在了，不必回頭補。⛔ 且不要回頭改舊資料（0802 那條鐵律）。

### P1：要做稿單時才做（只動資料層，顯示層零改動）

1. 狀態檔的 `tc` 加 `S` 欄（`{"T": [...], "C": [...], "S": [...]}`）。
2. `set-tc --pairs` 語法擴充成 `id=T/C/S`，**併在同一次呼叫**（見 4d）。
3. `T_MAX` 的機動 T 豁免**刪掉**——不同軸不佔格，補丁自然消失。
4. 顯示層**完全不動**：`s2_render_matrix.py` 照舊把 S 當 T 的第一格畫（現在就是這樣）。
5. `s2_special_t.json` 升格為 story 定義檔（改名與否再議；⚠️ 改名要同步 `load_special_t()` 與所有引用點）。

這樣可以先跑一週看標得準不準，**頁面零風險**。

### P2：稿單形狀定了之後

處理 4a 的顯示層選擇，並與 0819 §4 的三個 UI 選項合流評估（那份建議「選項 A 短期、選項 C 終局」，但那是在還沒有網頁矩陣頁的時候寫的——現在矩陣頁已經上線，選項 C 的前提其實已經成立了，屆時要重新評估）。
