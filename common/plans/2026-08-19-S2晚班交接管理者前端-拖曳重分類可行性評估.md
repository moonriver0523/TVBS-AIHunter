# S2 晚班交接管理者前端網頁版——拖曳重分類可行性評估

- 日期：2026-08-19
- 性質：**評估報告，不是規則、不是授權實作**——結論為「可行但要分階段，且要排在既有裁決之後」，實作時程由使用者裁定
- 觸發：使用者提案「分類難題可否用人工介入排序解決——搭建管理者前端網頁版，列出大中小分類，用拖曳方式重新分類，SAVE 後重新 RENDER 晚班交接」
- 範圍：只評估「拖曳重分類前端」這個提案本身的可行性、架構影響、與既有計畫的依賴關係
- 不包含：UI 視覺設計、實際開發、資料庫 schema 細節

---

## 一、先講結論

**可行，但不是一個獨立專案——它是兩份既有評估／規劃的交集，且會撞到既有的一條鐵律。**

三個已存在的參考點：

1. [[project_s2_wp1_render_pipeline]]：狀態檔是唯一真相源，`render` 永遠是**單向投影**（狀態 → 文字/HTML），從未設計成反向寫入。
2. `2026-08-16-S2晚班交接網頁版-CloudRun部署評估.md`：已經評估過「把 render 結果搬上雲端網頁」，但那份是**唯讀**（Cloud Run 摸不到本機狀態檔，只能讀一份投影）。
3. `2026-08-18-S2分類系統化規劃.md`（A10）：**順序鐵律**——「檢討完成前，不做任何分類的機械檢查或自動修正」，P0 裁決包沒結案前只准做 P0。

這個提案的本質是「把 (2) 從唯讀升級成可寫入，寫入內容是 (3) 想解決的分類問題」。三者疊在一起看，才是完整的可行性圖像。

## 二、跟既有唯讀網頁評估的關鍵差異：這次要「寫」

0816 評估的缺口是「狀態資料在本機，Cloud Run 摸不到」，當時只需要解決**讀**。這次多一個維度：**編輯要能把拖曳結果送回去，變成下一次 render 的輸入**。這改變了風險等級：

| | 唯讀（0816 已評估） | 拖曳寫入（本提案） |
|---|---|---|
| 資料流向 | 狀態檔 → 雲端展示，單向 | 雲端操作 → 要寫回狀態檔，雙向 |
| 併發風險 | 無（只是多一個讀者） | **有**——掃帶輪同時在跑會寫狀態檔，網頁編輯若同時寫，是 lost update |
| 真相源 | 不變，狀態檔仍是唯一真相源 | 若直接讓雲端寫本機檔，會出現「兩個入口都能改真相源」，違反現行「agent 禁止直讀寫、統一走 `s2_state.py`」的存取層原則 |
| 現成護欄可用？ | 可直接沿用 0816 方案 A（GCS 同步） | **不能直接沿用**——護欄明文「收斂 agent 不寫狀態檔（無鎖，lost update），只產建議檔由掃帶輪套用」，這條原則對「拖曳前端」同樣適用 |

## 三、併發問題：不是新問題，是既有護欄要不要延伸

MASTER 護欄已經處理過同一類問題——收斂 agent（`s2_reclass_prompt.md`）**不直接寫狀態檔**，而是產出「建議檔」，由掃帶輪收工前吃進去套用。這是因為狀態檔沒有鎖，兩邊同時寫會互相覆蓋。

拖曳前端要嘛遵守同一模式，要嘛承擔重新設計鎖機制的成本：

- **方案甲（沿用建議檔模式，風險最低）**：拖曳的結果不直接寫狀態檔，而是產生一份「重分類建議檔」（格式比照 `s2_apply_reclass.py` 吃的那種），由下一次掃帶輪或一個獨立的「套用」步驟消化。編輯 SAVE 之後不是「立刻重新 render」，而是「進佇列，等下一次套用時機」。
  - 優點：零併發風險、不用碰狀態檔的存取層、跟 A10 P1/P2 已經規劃的「收斂制度化」是同一條路，可以合流。
  - 缺點：不是使用者要的「SAVE 後直接重新 RENDER」——有延遲，不是即時生效。
- **方案乙（即時寫回，需要鎖）**：拖曳操作即時呼叫 `s2_state.py set-category` 等價的 API，SAVE 後立刻觸發 `s2_render.py` 重跑。
  - 要新增：檔案鎖或版本號（樂觀鎖，SAVE 前比對版本，衝突就要求重新整理）、一個常駐服務把雲端請求轉譯成本機 `s2_state.py` 呼叫（見下一節）、「網頁編輯」與「掃帶輪」的時間窗規則（例如只在兩輪之間的空檔開放編輯，避免正在組批次時被改）。
  - 優點：符合使用者原始體驗期待。
  - 缺點：改動範圍明顯更大，且直接觸及「唯一真相源」的存取層——這正是 0816 §五特別強調「不要讓兩邊各自演化」的那條線。

## 四、架構影響：需要新增的東西（不是大改，是新增一層）

不需要重寫 `group_items`／`render_item`／`cat_of` 這些既有邏輯——它們是純函式，輸入輸出不變，可以原樣沿用。真正要新增的是**寫入通道**：

1. **一個服務層**：把「雲端網頁的拖曳操作」轉成「本機 `s2_state.py set-category` 呼叫」。因為 Cloud Run 容器摸不到本機檔案（0816 §三已證），這一層勢必要跑在能碰到狀態檔的地方——可能是本機常駐一個小型 API（供 Cloud Run 網頁呼叫）、或走 0816 提過的 Firestore／Cloud SQL 路線（狀態本身搬上雲端，本機與雲端讀寫同一份）。
2. **拖曳 UI 的資料來源**：大中小分類清單本來就在狀態檔的 `category` 結構裡（`s2_render.py:cat_of`），`list-topics` 已經有印出機制，改成 JSON API 輸出不難。
3. **SAVE 後重新 render**：技術上就是呼叫既有的 `s2_render.py`／`s2_render_html.py`，這段完全是現成的，不算新架構。

## 五、跟 A10（分類系統化規劃）的依賴關係——這是最容易被忽略的阻塞點

A10 的順序鐵律寫得很明確：「檢討完成前，不做任何分類的機械檢查或自動修正」，P0（歷史語料分析＋裁決包）沒結案前只准做 P0。

拖曳重分類前端**本質上就是一種「分類的機械修正介面」**——即使是人工操作而非自動化，它仍然是在 P0 裁決（大分類層級模型、社會/話題定位、命名軸）**定案之前**就先蓋好一個可以隨手改分類的工具。這有兩個風險：

- 沒有決策卡當底，編輯用這個工具糾正的分類可能跟 P0 之後定案的規則衝突，等於白做。
- A10 §4b 已經規劃「分類判例庫」——人工糾正要自動落判例，晉升進決策卡例外表。**拖曳前端如果做出來，正好是最自然的判例輸入介面**（比現在的口令改分類更直覺）——但要先有判例庫的資料結構（P1）才接得上，不然拖曳操作留下的糾正紀錄無處可去，又要事後補接。

**結論：拖曳前端不是不能做，而是應該排在 A10 P0 裁決之後、最好能跟 P1（登記簿＋判例庫）合流設計**，讓「拖曳一次」同時完成「改分類」＋「餵判例庫」兩件事，而不是先做一個之後要重接的孤立工具。

## 六、建議的階段順序（不代表已核准，僅供裁決參考）

1. **先完成既有阻塞項**：0816 方案 A/B/C 裁決（唯讀網頁怎麼上雲端）＋ A10 P0 裁決包（分類規則怎麼定案）。這兩個沒定案，拖曳前端無論做哪個方案都可能要推倒重做。
2. **Phase 1（低風險起步）**：唯讀網頁先上線（0816 方案 A），編輯能在瀏覽器看到現況分類。
3. **Phase 2（方案甲，建議先做這個）**：唯讀網頁加一個「提出重分類建議」按鈕，操作方式可以做成拖曳，但送出後走**建議檔模式**（跟收斂 agent 同一條路），不即時寫狀態檔。這一步可以跟 A10 P2「收斂制度化」的介面需求合流——本來 P2 就要有人審建議檔，拖曳前端可以是那個審核介面的視覺化版本。
4. **Phase 3（方案乙，觀察 Phase 2 一段時間再議）**：如果建議檔模式的延遲成為實際痛點，再評估即時寫回＋鎖機制的投資是否划算。

## 七、成本量級（粗估，供裁決參考，不是報價）

- Phase 1：已有 0816 評估打底，屬「小」。
- Phase 2：拖曳 UI＋輸出建議檔格式＋（若要）串接 A10 P1 判例庫欄位，屬「中」——多數工作量在前端互動，後端只是把既有 `set-category`／建議檔格式包一層 API。
- Phase 3：常駐服務＋鎖機制＋跟本機排程的時間窗協調，屬「中大」——這是唯一真正牽動存取層架構的部分。

## 八、待辦（不代表已核准實作，需使用者明示才能動工）

- [ ] 裁定要不要先做 Phase 1（唯讀網頁）——若做，併入 0816 待辦一起排
- [ ] A10 P0 裁決包完成前，本項不啟動 Phase 2 以上
- [ ] Phase 2 若啟動：建議檔格式要跟 A10 P1 判例庫欄位（`{素材摘要一句, 錯放, 正解, 日期}`）對齊，避免重複設計
- [ ] Phase 3 若啟動：鎖機制與時間窗規則需另立護欄，比照 MASTER「一次一項、replay→shadow→TestMode→正式輪」節奏上線
