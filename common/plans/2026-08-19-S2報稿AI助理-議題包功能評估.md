# S2 報稿AI助理——「議題包」功能評估

- 日期：2026-08-19
- 性質：**評估報告，不是規則、不是授權實作**
- 觸發：使用者提案「未來新增報稿AI助理，自動把相似議題的所有素材整理為『議題包』（如『野火肆虐』把當天所有跟野火有關的新聞列出來），議題包本身也由 AI 判斷當天哪些是重大議題」
- 範圍：評估①議題包這個概念跟現有分類架構的關係②生成機制設計③前端 UI 放置位置建議
- 不包含：實際實作、UI 視覺稿

---

## 一、先講結論

**議題包不是「重新命名中主題」，是新增一層跨分類的橫向聚合視圖——現有的大／中／小分類是「這則稿子歸哪一格」的縱向歸位，議題包要回答的是「這些稿子其實在講同一件事，即使它們被分到不同格」，兩者維度不同、不衝突，但不能用同一套機制做。**

短期最便宜的落點：**在晚班交接單最上方加一段「今日重大議題」摘要區塊**，零架構變更（只是 render 多印一段），中長期如果 Q3 的網頁化前端做出來，議題包才有資格變成一個真正的 facet 篩選維度。

## 二、為什麼議題包不等於中主題

現行中主題的產生方式：**掃帶輪當下**，agent 看到一則新素材，決定它掛進既有中主題還是開新的（A10 §4a 正在補的 charter 機制就是為了讓這個「掛哪」判斷有據可查）。它的範圍侷限在**同一個大分類底下**（`group_items` 的階層是大分類→中主題→小分題），且是**逐則、即時**的判斷。

議題包不一樣：

1. **可能跨大分類**——「野火肆虐」的素材可能同時落在「國際」的某個中主題、也可能有一則因為畫面特殊被歸進「話題」。中主題結構限制在單一大分類底下，天生框不住這種跨格聚合。
2. **是事後、批次的判斷**——「今天有沒有重大跨主題議題」這件事，要看過當天全部素材才回答得出來，不是逐則掃帶當下能判斷的（單則到貨時，agent 看不到後面還會不會有更多同主題素材進來）。
3. **產生的東西不一樣**——中主題是「素材的歸屬」（每則素材恰好屬於一個中主題），議題包是「素材的引用清單」（一則素材可以同時出現在原本的分類位置，又被列進某個議題包的摘要裡，不是搬家）。

這個差異決定了技術做法：**議題包不能改動既有分類欄位，只能是唯讀衍生的一層標註**（比照 render 是狀態檔的單向投影這個既有原則——議題包同樣該是「素材清單的單向投影」，不能反過來覆寫 `category`）。

## 三、生成機制建議

### 3a. 觸發時機

比照收斂 agent（`s2_reclass_prompt.md`）的定位——**收工前跑一次**（例如 23:00 那輪之後，或建檔輪），不是每輪都跑。理由：

- 議題包要看「當天全貌」才準，跑太早（例如 18:00）看不到後面才進的相關素材，跑出來的包不完整。
- 跟 A10 §9 的不變式一致：「量大的內容給收斂 agent 讀不給掃帶輪讀」——彙整全天素材屬於高 token 動作，塞進每輪的掃帶 prompt 會拖垮省 Token 的既有成果（T 系列項目），應該獨立跑。

### 3b. 產生依據——沿用既有機制，不重新發明相似度演算法

A10 已經因為「小分題接連」這個相鄰問題，實測過字面相似度無效（白海豚案）、LCS 對自然語句失效，並得出「不加回內文模糊比對」的不變式。議題包生成如果重新發明一套跨主題相似度演算法，等於重蹈覆轍。建議直接借用兩個已規劃或已存在的機制：

- **entity 重疊粗篩**：A10 §4c 的 `find-similar` 是「新素材進來時，拿它跟既有小分題比對地名／人名／機構名重疊」；議題包生成用的是同一套實體比對邏輯，只是方向反過來——**拿當天全部素材的 entity 做一次全域分群**，而不是單則跟既有清單比對。技術上是同一個粗篩函式的另一種呼叫方式，不是新演算法。
- **charter 當輸入**：A10 §4a 的中主題 charter（一句話「這格收什麼」）如果已經上線，議題包生成 agent 可以直接讀 charter 而不必重新讀每則的完整內容，省下大量 token——這是 charter 機制的一個額外收益，原規劃書沒提到但值得記一筆。
- **最終判斷仍交給 LLM**：粗篩（entity 重疊）機械做，篩出候選集合後，用一次 LLM 呼叫判斷「這些候選是不是真的同一議題、算不算今天的重大議題」，跟 `dedup-check` 的「機械只回答比對結果，要不要合併是編輯判斷」原則同構——這裡是「機械只回答候選集合，是不是重大議題交給 LLM 語意判斷」。

### 3c. 輸出格式（建議，供裁決參考）

議題包不寫回狀態檔的 `category`，另立一個欄位或獨立清單，例如狀態檔新增 `topic_bundles: [{name, summary, item_ids: [...]}]`，或完全獨立一份 `議題包.json`（比照 `s2_resident_topics.json` 的獨立檔案模式，不動主狀態結構）。**建議走獨立檔案**——理由同 A10 的護欄「收斂 agent 不寫狀態檔」，議題包生成也是事後衍生產物，不該跟掃帶輪主線寫入路徑搶同一份檔案的鎖。

### 3d. Token 成本量級

比照 A10 P0 對「歷史語料分析」的態度——這是「屬於高 token 動作的批次工作」，啟動前應先向使用者報價。粗估：全天素材若 50–100 則、每則精簡摘要（非全文）約 30–50 字，彙整輸入約 3–5K tokens，加一次 LLM 判讀輸出，單次跑量級可控，只要**真的只在收工時跑一次**（不是每輪），對既有省 Token 成果（T 系列）近乎中性。

## 四、前端 UI 放置位置建議

### 選項 A：晚班交接單最上方，大分類清單之前（建議短期先做這個）

新增「今日重大議題」區塊，列出議題包名稱＋一句話摘要＋成員清單的錨點連結（連到各成員原本在下方大／中／小分類清單裡的位置，不是另開一份清單）。

- 優點：零架構變更，`s2_render.py` 只是多印一段（讀 3c 的獨立議題包檔案），不影響 `group_items` 主邏輯；使用者現在看的仍是同一份 txt/html，議題包是加值不是替換。
- 缺點：純文字清單，議題包多的時候（例如同時有 3–4 個重大議題）版面會變長；沒有互動性，看完摘要還是要往下翻找原文。

### 選項 B：獨立於晚班交接單的另一份產出

例如另存一份「議題摘要.txt」，或未來議題包網頁版的獨立分頁。

- 優點：不干擾現有交接單版面，議題包可以做得比較豐富（例如每個議題包附時間軸）。
- 缺點：多一份檔案要維護同步；編輯要多開一個東西看，跟「晚班交接單是唯一入口」的現行習慣不一致。

### 選項 C：併入 Q3 拖曳前端的網頁版 UI，做成篩選 facet

如果 Q3 的管理者前端網頁版做出來，議題包可以是其中一種 facet 篩選（比照 A10 §6 標籤化終局提到的「HTML facet 篩選後排序問題消失」的構想）——編輯可以直接點「野火肆虐」這個議題包標籤，篩出所有相關素材，不管它們原本分在哪個大／中／小分類。

- 優點：這是議題包概念最自然的終局位置——它本來就是跨分類維度，只有脫離線性文字排版、走互動式篩選介面才能真正發揮。
- 缺點：依賴 Q3 前端先存在，屬於較長期的規劃。

### 建議順序

**選項 A 短期先做**（成本最低、跟現有 render 管線相容），**選項 C 是終局位置**（等 Q3 前端與 A10 標籤化都到位後合流），**選項 B 不建議**——它兩邊都不討好，多一份檔案的維護成本沒有換到選項 C 的互動性優勢。

## 五、與既有規劃的關係圖

```
A10 §4a charter 機制 ──提供輸入──→ 議題包生成（本提案）
A10 §4c find-similar 粗篩 ──同一套 entity 比對邏輯──→ 議題包生成的候選篩選
議題包生成 ──短期輸出──→ 選項 A（交接單頂部區塊）
議題包生成 ──長期輸出──→ 選項 C（併入 Q3 拖曳前端的 facet 篩選）
```

**議題包不是獨立於 A10 之外的新專案，是 A10 基礎設施（charter／entity 比對）建好之後，很自然的下一層應用。** 這意味著本提案的合理啟動時機是 A10 P1 上線之後，不是現在——沒有 charter，議題包生成 agent 就得跟現在的收斂 agent 一樣，每次都重新讀全部素材原文才能判斷，成本高很多。

## 六、待辦（不代表已核准實作，需使用者明示才能動工）

- [ ] 裁定議題包資料是寫進狀態檔新欄位還是獨立檔案（建議獨立檔案，見 §3c）
- [ ] 裁定啟動時機：現在就做（成本較高，逐則讀原文）還是等 A10 P1 charter 上線後做（成本較低）
- [ ] 選項 A 若先做：`s2_render.py` 需求規格（區塊位置、錨點連結格式）
- [ ] 觸發節奏若定案：併入既有「收工前流程」清單，比照收斂 agent 的既有節奏，不新增獨立排程項
- [ ] 高 token 動作照例先向使用者報價確認
