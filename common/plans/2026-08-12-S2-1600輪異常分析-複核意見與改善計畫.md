## 三、七個問題逐項複核

### 1. `mark_for()` 的 day==0 一律 △ 是否合理？

**結論：規則本身合理，5a 修正方向對，但 audit 實作仍需再修。**

`common/13c` 與 `s2_render.py:158-183` 都明定：晚班起始日 16:00～23:00 屬同一值班區間，一律 △；隔日才依 01:00／07:00／09:00 分成 ▲／■／◆。所以剛建檔的 16:00 輪全是 △ 正常。

目前 audit 的問題：

- 它用 `day>=1 and mk=='△'` 判錯，會把合法的 `set-mark △` override 也報成異常。
- `checkpoint_time()` 與 `mark_for()` 同源；若 parser 本身把畸形 checkpoint 判成 day 0，audit 也會一起相信它，形成「同一函式自證」。
- 顯示文字「本班還在同一天（16:00～23:00）」只看 marks，沒有確認頂層 checkpoint 真在這段。

**建議判準**：

1. 先由 checkpoint 格式稽核確認含可辨識 MMDD＋HHMM。
2. 對沒有手動 override 的項目，比較 `stored/effective mark` 與 `mark_for()` 預期值。
3. 有合法 `mark` override 的項目列為「覆寫 N 筆」，不報錯。
4. 補測：同日 16/23、隔日 01/07/09/13、畸形 checkpoint、合法 set-mark override。

### 2. `...[TRUNCATED]` 是否最好？

**結論：保留 ASCII 標記比直接硬切好，但目前長度算法錯。**

保留截斷訊號有實際價值：離線查證者知道內容不完整，不會把 4000 字尾端誤認為站方全文結束。ASCII 也避開 CJK 污染判準。

但 `s[:limit] + marker` 使輸出超過上限。應改為：

```python
marker = "...[TRUNCATED]"
return s if len(s) <= limit else s[:limit - len(marker)] + marker
```

另建議：

- 若 `limit < len(marker)`，安全退化為 `marker[:limit]` 或直接 `s[:limit]`。
- 加單元測試驗證長度永遠 `<= limit`、ASCII-only、未截斷文字逐字不變。
- 13c §0-1 的「整理包 3000 字＋中文標記」是另一條資料路徑；不要混入 `src_text`，否則同樣踩 CJK 判準。規則文件需明確區分「entry 備註」與「src_text 截斷標記」。

### 3. `s2_audit.py` 還有其他 `[:N]` 藏問題嗎？

**結論：有，而且同類型紅／黃診斷應統一處理。**

目前至少還有：

- 已裁定不收 `hit[:8]`
- 窗內漏收 `inw[:12]`
- 窗外 `after[:8]`
- `missing_ids[:20]` 寫回 reconcile log
- checkpoint 誤標 `mis_tagged[:10]`

不是所有截斷都要把全部印出來；終端機輸出需要上限。但只要是**需要人或 agent 逐筆處理的診斷**，就必須同時提供：

- 總數
- 本次顯示數

### 4. 四筆 BITE 缺逐字稿應怎麼處理？

**結論：照收＋needs_review 正確；不應大膽標 BITE 留白。現行可暫時維持「無BITE」作相容輸出，但長期應改成正式的待聽帶狀態。**

三種狀態要分開：

1. `BITE_CONFIRMED`：有可引用原文，可正式標 `(BITE)`。
2. `NO_BITE_CONFIRMED`：已確認沒有可用引言，正式標「無BITE」。
3. `BITE_REVIEW_REQUIRED`：機械訊號顯示可能／通常有，但逐字稿不足，待人工聽帶。

四筆 PO 素材屬第 3 種。目前用「無BITE＋備註」會讓正式交接文字傳達錯誤的確定性，也讓 audit 每輪永久紅；但現行 `s2_validate.py` 又強制每則必須有「無BITE」或完整 `▎BITE：`，所以**不能只改 entry 文字**，否則會製造新的品質紅燈。

短期相容做法：

- 暫時維持現行可通過 validator 的「無BITE」，第一括號明確寫「BUTTED SOTS／站方未附逐字稿／待人工聽帶」，並保留 `needs_review`。
- 為 BITE finding 建立結構化 code／fingerprint（至少含規則代碼、素材 id、footage_type、entry/source_facts 版本）；只有完全相同 finding 已留痕時，才列「待人工未結案」而不算新紅。
- finding 依資料改變重新計算；若 `footage_type`、entry 或原文更新，不能讓舊備註遮住新問題。

長期需同步新增結構化 `bite_status`、render 顯示、parser 與 validator 規則，之後才能移除「無BITE」這個相容占位。

0812-1600 三小時窗口內，新收資料只明確命中：

- `IN-16WE`：VO 版
- `PY-03WE`：PKG 版

同一份 0812 RT list 還可看到多個哥倫比亞強震代碼：`RT3609`、`RT4771`、`RT4797`、`RT3605`、`RT4780`、`RT4772`、`RT4774`、`RT4773`。但它們時間均早於 13:00，而且多數已在 `0811-s2-state.json` 收錄；因此不屬 0812 建檔輪的新收窗口。

這顯示原本只搜「哥倫比亞強震」中文關鍵字不夠，應以事件族群查：

- **跨班參考完整性**：前一班已有的重要素材是否應用參考／沿用方式呈現，而不是重複入庫。

### 6. `new_item()` 歷史 bug 要不要回填？修復是否漏路徑？

**結論：0812 新契約的修復只完成一半；歷史缺欄範圍很大，但不能全部稱為 bug 造成的資料遺失，也不建議全面回填。**

盤點顯示 0812 前的狀態檔幾乎都沒有這兩個欄位：

- 3,875 筆素材中 3,808 筆缺 `src_text`。
- 1,442 筆 NS 中 1,416 筆缺 `footage_type`。

這組數字代表「舊 state 不具新欄位」，不是等同「3,808 筆都被 `new_item()` 丟失」：原先 13c 明寫 `src_text` 留在 batch、`add-batch` 忽略未知欄位；把它提升成狀態檔唯一真相源是 0812 才明確採用的新契約。`dd0e95f` 的 bug 是新契約已要求保存，但程式沒有接住。

現行 13c §2b 又明訂不做全面歷史誤判清查；歷史狀態多為交接後不再使用，全面改 3,800+ 筆成本高、同步風險大，而且 raw/batch 暫存並非每輪都有完整資料。

建議：

- **不建立全面歷史回填專案**。
- 若有實際查證或 dashboard 需求，先用一次性 dry-run inventory 回答指定日期的可回填率，不先改檔。
- 只回填：當日活檔、仍有 pending/needs_review、或使用者明確指定且仍有用途的日期。
- 回填必須 idempotent，只補空欄、不蓋既有值，並做 render hash 不變驗證。

修復漏掉的路徑：

- `cmd_add` 與 `cmd_add_batch` 已傳入 `new_item()`，新增路徑已修。
- `apply_update()` 接受 `footage_type` 只拿來跑 `bite_doubt()`，沒有寫回 `it['footage_type']`。
- `update-entry` 完全沒有 `src_text` 參數，pending 轉正後無法更新原文。
- `update-entry --batch` 同樣缺 `src_text`。
- 側錄的 `new_item()` 呼叫不需這兩欄，屬不同資料類型，不算漏。

較佳設計不是繼續擴充 7 個 positional/primitive 參數，而是將機械事實集中成一個 `source_facts`／mapping，新增與更新共用同一個 merge 函式。

### 7. 正常三站掃描還能怎麼優化？

**結論：確定仍有可優化方向，但目前證據不足以把 NS 16 分、AP 4 分、RT 8 分直接解讀成各站純掃描耗時；優先應補「階段耗時」遙測。**

Review 記錄的站別時間點可能混有摘要生成、批次檔整備、分類與補正；本次又無權重算 transcript 時間軸，因此不能斷言正常三站合計就是 28 分或本身偏長。現有優化方向（固定 AP PageSize、`s2_batch_prep.py`、批次 update）有既有基線支持，但 1600 輪混入新工具上線與大量修正，必須先分段量測才能判定下一個瓶頸。

建議增加每輪 phase metrics：

- startup/resume
- NS list/detail/write
- AP list/detail/write
- RT list/detail/write
- pending refresh
- classify/apply
- render
- audit
- audit remediation
- retries/errors

每段記：開始、結束、tool calls、new item 數、retry 數、錯誤類別。這樣下一次可直接回答「NS 真慢，還是 NS 後處理慢」。

掃站優化優先序：

1. NS：開工前登入檢查一次；null token 只允許一次固定重整重試，第二次即 degraded，不進自由探索。
2. AP：固定 `PageSize:16`，清單 query 1 次為目標，真的跨頁才增加；禁止調 PageSize 試探。
3. RT：清單快照必落地；API/列表取得完成後一次 diff，避免重讀頁面。
4. 三站：`dump`＋`build` 固定各一次；送出前校驗，站末修正累積成一次 batch update。
5. audit：同一 finding 若資料未變，不可要求 agent 再查一次；以 finding fingerprint＋needs_review 狀態去重。

## 四、建議方案比較

### 方案 A：只補眼前小洞

內容：修 truncate 長度、補其他 `[:N]` 提示、補幾個測試。

- 優點：快、風險低。
- 缺點：BITE 永久紅燈、update 契約、phase 遙測都沒解；下次仍可能再進除錯迴圈。

### 方案 B：契約硬化＋稽核冪等化＋分段遙測（建議）

- 優點：直接對準本輪耗時根因；能防止同一問題重複消耗；保持現行流程架構。
- 缺點：需改 3–5 支腳本與測試，約一個小型工作包。

### 方案 C：全面歷史回填＋重構 state schema

內容：回填所有歷史 state，全面改用新 schema。

- 優點：資料最整齊。
- 缺點：成本最高、Drive 寫入風險大、來源不完整，且違反現行「歷史只修仍在用資料」原則。

**推薦方案 B。**

## 五、分階段改善計畫

### P0：先止血（下一輪前）

1. **先修 RT 對帳鍵值**：
   - RT 不得只用 Edit No 判斷歷史收過；清單快照需保留 headline／guid，對帳至少以 `Edit No + headline`，能用 guid 時優先用 guid。

3. 修 audit ②：
   - 尊重合法 `set-mark` override。
   - 無 override 才比較自動預期值。
   - 畸形 checkpoint 必須由格式檢查報出，不能被 day0 放過。
4. 建立結構化 audit finding code／fingerprint，再修 BITE 重複紅燈：
   - 完全相同 finding 已留痕 → 顯示「待人工未結案」，不列新紅。
   - 資料版本或 finding 內容改變 → 仍視為新紅。
   - 未留痕 → 紅。
5. audit 所有可行動清單都補 `shown/total/more`；至少紅燈不得靜默截斷。
6. 讓 `s2_audit.py --json-report` 輸出完整 finding；終端摘要不再叫 agent 直接呼叫內部函式。

**驗收**：

- 用「歷史 RT3609＝以黎談判、本輪 RT3609＝哥倫比亞強震」案例，對帳必須判為不同素材，不得列成前幾天收過。

- 人為建立一筆隔日錯標、合法 override、畸形 checkpoint，三種各自正確分類。
- truncate 所有輸出長度 `<=4000`。

### P1：資料契約硬化（1–2 個工作日）

1. 將新增與更新共用 `merge_source_facts()`：
   - `sb_count`
   - `src_text`
   - `footage_type`
2. `update-entry` 單筆／批次新增 `src_text`，且 `footage_type` 真正寫回。
3. 明定 merge semantics：
   - 未帶＝保留舊值。
   - 明確空值是否代表清除，需用獨立 `--clear-*`，不可把空字串混同未帶。
4. 引入 `bite_status` 三態，並**同步**修改 render、parser、validator；完成前維持「無BITE＋待聽帶備註」的相容輸出。
5. 同步修正 13c 文件中「add-batch 忽略 src_text」的過時描述；目前程式已改成存進 state，規格必須一致。

**驗收**：

### P2：效能可觀測性（1 個工作日）

1. 在 `s2_scan.ps1` 或固定 wrapper 記 phase timestamps。
2. `_token_metrics.jsonl` 增加 phase durations／errors／retries／items。
3. audit remediation 單獨計時，不與正常掃站混在一起。
4. 建立門檻：
   - audit remediation > 3 分鐘 → 記異常。
   - 同 finding 重跑超過 1 次 → 記 duplicate-work。
   - 單站比最近 5 輪中位數高 50% → 標示站別異常。

**驗收**：下一輪回報能直接列出 NS/AP/RT/render/audit/remediation 各自分鐘數，不再從 transcript 手算。

### P3：指定需求才做歷史修復

不主動建立全面 inventory／回填工作包。只有當 dashboard、查證或使用者明確指定某日期需要這些欄位時，才：

1. 對該日期先 dry-run，不寫檔。
2. 只補有可靠 batch/raw 來源且目前為空的欄位。
3. 每檔回填前後比對：
   - item 數不變
   - `raw_entry/category` 不變
   - render txt hash 不變
4. 無可靠來源的欄位保持缺失，不猜值。

**驗收**：指定日期有可回填／不可回填原因報表；沒有全面改寫 Archive。

### P4：兩輪觀察與收斂

連續觀察至少兩輪：

- audit 新紅數與已留痕待辦分開。
- 正常掃站時間與 remediation 時間分開。
- `update-entry` 次數是否收斂至每站 0–1 次 batch。
- AP 清單 query 是否 1–2 次。
- 無同一 finding 重複查證。

達標後再決定是否進 Task 2 最小 Claude Code 啟動設定，避免多項優化同時上線、無法歸因。

## 八、最終評語

這次修復不是「修錯」，而是**修對了第一層，尚未把資料契約與稽核生命週期補完整**。最值得保留的原則有三個：

1. 狀態檔是唯一真相源。
2. 疑慮照收入庫並留痕，不靜默丟資料。
3. 重複誤報會把警告訓練成雜訊。

下一步應把第 3 點真正落到 audit：**同一 finding fingerprint 一旦已留痕，就不再每輪當新故障重查；資料或規則輸入改變時則必須重新升級。** 是否再依逾時升級，應等實際值班需求定義明確 SLA 後才加入，不能先用任意天數。這會比單純再省幾次 browser call，更直接地避免下一個 37 分鐘異常輪。
