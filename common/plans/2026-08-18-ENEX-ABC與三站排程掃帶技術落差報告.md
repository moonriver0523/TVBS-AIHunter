# ENEX／ABC 交換平台整併　vs　三站（AP／RT／NS）排程掃帶　技術落差報告

> 建立 2026-08-18。範圍：純技術盤點——三站排程掃帶已有的腳本化／自動化機制，ENEX／ABC 交換平台整併現況缺少哪些。不含優先序排序或時程建議，那是使用者裁決的事；本檔只負責把落差講清楚。
>
> 方法：逐檔核實（見文末「查證依據」），凡三站與 ENEX/ABC 兩邊都有找到對應機制的項目，本檔如實標「無落差」，不因為要湊「落後」的敘事而誇大差距。

---

## 一句話結論

**三站是一套會自己跑、自己顧登入態、自己抓漏、自己收尾的系統；ENEX／ABC 是一份「規則寫得很仔細的操作手冊」，每一步都靠 agent 現場臨場發揮，沒有任何專屬程式碼撐著。** 兩邊共用的部分（`s2_state.py`、`s2_render.py`、`s2_validate.py`、`s2_mark_ingested.py`）技術上是相容的，但那些工具是為三站設計，ENEX/ABC 只是「剛好能用」，不是「有為它設計過」。

---

## 逐項落差

### 1. 排程觸發——三站全自動，ENEX/ABC 純人工一次性

| | 三站 | ENEX／ABC |
|---|---|---|
| 觸發方式 | Windows 工作排程器，每 2 小時固定觸發（`scripts/S2掃帶.xml`；⚠️ 文件間對觸發點數量有出入，`13-S2-定時掃帶.md` 寫 12 個檢查點、XML 快照顯示 9 個，未核實何者才是目前生效版本，本身就是一個該補的稽核項） | 完全靠使用者一句話下令，一次性執行 |
| 互斥 | `s2_scan.ps1` 用 OS 檔案獨佔握把當鎖（`.s2-scan.lock`），撞鎖直接跳過不排隊 | 無鎖，理論上兩個人同時下令會互相搶同一個瀏覽器 profile |
| checkpoint | 腳本自動算，不寫死 | 無此機制，這次是我手動指定窗口 |
| 建檔／歸檔 | `New-ShiftState`（`s2_scan.ps1`）16:00 那輪自動建當日狀態檔＋把上一班歸檔＋把 `_待整併/` 過期殘檔一併歸檔 | 無對應機制，`_待整併/` 裡的候選檔全靠人工或 `s2_mark_ingested.py` 個別清理 |
| 補漏／代打 | `s2_watchdog.ps1`：偵測整輪沒跑就自動代打；另有「START 無 DONE」中途死亡偵測（只推播，代打邏輯本身還在使用者裁決中） | 無，忘記跑就是沒跑，沒有任何東西會提醒 |

**缺少的腳本／功能**：ENEX／ABC 沒有排程外殼、沒有鎖、沒有補漏機制——這三者目前都是「刻意選擇不要」（18 檔 §0 明文：人工下令才跑，不進固定排程），不是遺漏，但如果未來要提高頻率就得從零補起。

### 2. 登入態維護——三站有專屬保活腳本，ENEX/ABC 完全沒有

三站有 `s2_keepalive.ps1`＋`s2_keepalive.js`：獨立排程每 30 分鐘跑一次，直接讀 NS 的 JWT 到期時間，零 token；還有一支目前停用但架構完整的 `s2_alerts.js`（AP/RT 快訊守護，90 秒輪詢）。三站的認證機制也各自被記錄清楚（NS 1 小時滑動 JWT、AP 7 天 cookie、RT 23 小時 cookie）。

ENEX／ABC：**查無任何對應腳本**。這次任務前 ENEX／ABC 的登入是我手動開瀏覽器、叫使用者現場登入完成的，全專案找不到 `*enex*`／`*abc*`／`*platform*` 開頭有實際邏輯的腳本（只有一份純文字的 `s2_platform_prompt.md`）。

**缺少的腳本**：`s2_keepalive` 等級的 ENEX／ABC 保活腳本。⚠️ 但這不是「還沒做」這麼單純——ABC 的可行性計畫書已經實測過「比照 NS 單純載入頁面續期」這條路走不通（該站請求完全沒有 `Set-Cookie` 回傳），要幫 ABC 做保活得先找到一個新的續期方式，目前沒有任何已驗證可行的解法。ENEX 則完全沒調查過保活可行性。

---

### 3. 資料擷取層——三站有共用工具腳本，ENEX/ABC 每次都是 agent 現場手刻

三站有 `scripts/s2_batch_prep.py`（`inspect`／`unwrap`／`search`／`snapshot`／`compare`／`dedup-check` 等子指令，2026-08-13 上線後列為「一律必用」，取代逐輪即興寫的臨時檢查），加上三站各自的抽取白名單、逐字保真驗證函式、`sb_count`／`footage_type` 機械判準，全部是文件規格＋可重複執行的程式碼兩者都有。

ENEX／ABC：兩份可行性計畫書（`2026-08-09-ENEX-...`、`2026-08-10-ABC-...`）裡寫的端點、查詢、抽取白名單、逐字保真驗證方法**只存在於文件裡，repo 找不到對應的 `.js`／`.py` 實作**，也沒有像三站那樣的 `test_s2_parse.py` 級測試檔。18 檔 §1 安全條款雖然照抄了三站「token/CSRF/fetch/parse 必須同一段 `page.evaluate()` 內完成」的規則，但那只是文字規則的重申，**沒有共用腳本把這套邏輯封裝起來**——所以每次掃 ENEX／ABC，agent 都得在 `browser_evaluate` 裡從零手刻整套 fetch＋parse＋抽取邏輯，這次任務也是這樣做的。

**缺少的腳本**：ENEX／ABC 版的 `s2_batch_prep.py`，把已經在計畫書裡寫好的端點規格、抽取白名單、逐字保真驗證封裝成可重複呼叫的程式碼，而不是每次讓 agent 憑記憶重寫一次規格書裡的 JS。

### 4. 入庫寫入層——三站直寫、ENEX/ABC 兩階段，且候選檔→正式狀態檔這一步完全沒有工具

三站的 agent 用 `s2_state.py add-batch`／`update-entry`／`set-category` 等指令直接寫進正式狀態檔。

ENEX／ABC 因為 `s2_state.py` 的 `os.replace` 寫入沒有檔案鎖、跟每 2 小時一輪的掃帶輪同時寫會互相蓋掉（18 檔 §0 記錄過 2026-08-10 一次 44 處差點被無聲覆蓋的實例），所以規則明文禁止外部 agent 直接碰狀態檔，改走「候選檔（`_待整併/`）→人工／主線整併」兩階段。

**這一步「候選檔 JSON → `add-batch` 的 entries／`set-category` 的 pairs」目前完全沒有工具**：三站好歹有 `s2_batch_prep.py` 做「raw→batch.json」的類似轉換；ENEX/ABC 這邊，包括這次 0817 那批 42 則的整併，都是我自己現場手寫一支一次性 Python script 讀候選 JSON、組出 entries 陣列跟 category pairs 字串再呼叫 `s2_state.py`。**這是本報告核實後確認、且與最初推測相符的一個明確落差**：三站有共用轉換層，ENEX/ABC 沒有，每次整併都要重新手刻。

**缺少的腳本**：一支 `s2_merge_platform.py`（或類似名稱），吃 `_待整併/{MMDD}-{站}-state.json`，自動組出 `add-batch --entries`／`set-category --pairs` 需要的檔案，甚至直接呼叫這兩個指令完成整併，取代人工現場手寫轉換腳本。

---

### 5. 對帳／稽核——三站有機械化清單對帳，ENEX/ABC 完全沒有

三站有 `scripts/s2_audit.py`（8 項離線檢查，其中「清單對帳」是抓「窗內漏收」的唯一機械化手段，0805 曾靠它抓到 47 則漏收），對帳結果會留痕進狀態檔，render 每輪還會檢查「這輪有沒有做對帳」，沒做就跳出警告（本次 0817 整併輪就吃到這個警告，因為手動整併輪本來就沒有三站清單可比對，已用 `needs-review add` 記錄原因）。

ENEX／ABC：候選 JSON 裡的 `counts:{掃描/收錄/排除}` 完全是 agent 自己宣稱的數字，**沒有任何機制去驗證「窗內是不是真的全撈到了」**。三站的漏收是靠清單快照跟狀態檔比對這種機械手段抓出來的；ENEX/ABC 目前唯一的把關是 agent 自己回報，沒有第二層驗證。

**缺少的腳本／機制**：ENEX/ABC 版的清單對帳——例如掃完之後再打一次輕量的「這個時間窗總共有幾則」健康檢查查詢（ENEX 附錄 A 已經有一個「健康檢查」查詢範本可以延伸），跟候選 JSON 的 `counts.掃描` 比對，抓出「agent 自己少算了」的落差。

---

### 6. 入庫標記／收尾——兩邊共用同一支腳本，技術上相容，但候選檔命名慣例會讓它誤判

`s2_mark_ingested.py` 兩站共用，且解析邏輯（正則比對代碼＋讀 JSON `items[].id`）對來源無感，技術上三站跟 ENEX/ABC 都吃得下。**這項本身沒有落差**。

但實測會踩兩個雷，都跟「這支工具是照三站的假設寫的」有關：
1. 文件裡已經記過一次「手動改檔名沒照腳本認的 `已入庫_{原檔名}` 前綴，等於沒改」的實錯（0816 側錄候選）。
2. 這次任務也遇到一個文件裡還沒記錄過的新案例：ABC 候選 txt 裡列出的「排除清單」項目（`skipped` 裡那些故意不收的代碼）也被 `s2_mark_ingested.py` 的通用代碼比對邏輯認成「這個代碼沒進狀態檔＝還沒入庫」，因而整份檔案被判定「有缺」不給改名，得靠人工介入手動改名。三站沒有這個問題，因為三站的「排除」是走 `needs_review`／機械判斷，不會把排除掉的代碼留在最終交付的 txt 裡跟收錄的代碼混在一起讓通用比對器誤判。

**缺少的功能**：`s2_mark_ingested.py` 需要認得「候選檔裡的排除清單區塊」跟正文分開比對，或者候選檔格式本身要把排除清單移出可能被誤判的區域。

---

### 7. 品質掃／格式檢查——進入正式狀態檔之後兩邊共用，候選檔階段之前 ENEX/ABC 完全沒有

`s2_validate.py` 透過 `s2_render.py` 每輪自動跑，只要素材進了正式狀態檔就會被檢查到，且驗證器的代碼正則已經認得 `ENEX\d{4,8}`／`ABC\d{6,16}`——**這一段沒有落差**。

落差在候選檔階段：三站的資料在寫進狀態檔之前，本來就是照 `add-batch` 的機械檢查（缺欄位、格式錯誤會擋下或警告）過濾過一輪；ENEX/ABC 的候選檔在交件的當下**完全沒有任何格式檢查工具**，18 檔 §4 那張格式規則表（第一括號、`(BITE)`一致性、150字摘要上限、`▎畫面：`必填）只能靠 agent「寫完自己對一遍」，18 檔自己都承認 0810 那批 38 個品質掃 HIT 裡 ABC 佔 12、ENEX 佔 3——這些問題都是等它被吃進正式狀態檔之後才被抓到，不是候選檔交件當下就攔住。

**缺少的腳本**：一支候選檔專用的輕量 lint（比照 18 檔 §4 那張表），在交件前就把常見的三種錯誤（缺畫面段、行尾掛時間碼、摘要超字數）攔下來，而不是等進了正式狀態檔才被 `s2_validate.py` 抓到。

---

### 8. 分類輔助——三站有三層防重複機制，ENEX/ABC 文件只要求了第一層

三站有：①開新主題前查現有清單（`list-topics`）②`s2_topic_review.py`（抓同義不同名／同事件被拆多主題）③`s2_topic_dedupe.py`（render 前抓5類問題：同名小分題跨大分類、跨天延續故事換了大分類、備註洩漏進分類名、零小分題、純形式標籤）④獨立於掃帶輪之外的「分類收斂 agent」機制搭配 `s2_apply_reclass.py` 可以機械套用建議。

ENEX／ABC：18 檔 §7 只明文要求了第①層（開新主題前跑 `list-topics`），完全沒提到②③④——這次任務就是實例：我在整併時另外手動跑了一次全量分類複核（使用者下的「把分類全部REVIEW一次」指令），才抓出 3 筆該搬大分類的素材，如果沒有這道額外人工複核，這些問題本來就不會被任何工具攔下來，因為 ENEX/ABC 流程本來就沒有内建②③④這三層。

**缺少的功能**：不是要新工具，是 18 檔的流程規則應該明文要求 ENEX/ABC 整併完之後也要跑一次 `s2_topic_dedupe.py`（工具本身無來源限制，直接可用），把它從「三站專屬習慣」變成「兩邊都要做的收尾步驟」。

### 9. 結構化欄位——三站有 `fields`／`parse_ok`／`src_text`，ENEX/ABC 候選 schema 缺兩項

| 欄位 | 三站 | ENEX／ABC 候選 schema |
|---|---|---|
| `sb_count` | 有，機械數 SOUNDBITE | **有**（18 檔 §2 範例已含 `"sb_count": 3`，核實後確認並非落差） |
| `fields`／`parse_ok` | 有（`s2_parse.derive()` 自動推導，`13b §2c`） | **沒有**，候選 schema 完全沒有這兩個鍵 |
| `footage_type` | 有（NS 判準） | **沒有**，18 檔 §6 自己也寫「ABC沒有SOUNDBITE也沒有footageType」，只能人工判斷 |
| `src_text` | 有，且文件明講「是事後離線查證的唯一依據」（`13b §2`） | **沒有**，候選 schema 只有 `enex`／`abc` 站別物件存識別碼，不是原文快照 |

**缺少的欄位**：`src_text` 是最該補的一項——三站已經因為缺這個欄位吃過連續四輪 BITE 誤判的虧（RT4131 實例）才補上，ENEX/ABC 候選 schema 從一開始設計時就沒有，等於三站已經用實錯換來的教訓，ENEX/ABC 這邊還沒吸收到。`fields`／`parse_ok` 屬於錦上添花（供未來 dashboard 查詢用），優先度低於 `src_text`。

---

### 10. 已知結構性缺口（文件已承認、尚未有腳本層解法）

- **ENEX 時長抓不到**：18 檔 §4 明寫留白，三個候選解法都未定案。
- **ABC 清單端點日期參數只精確到「日」**：計畫書明寫格式是 `M/D/YYYY`，沒有時分；這次任務就是靠「改用清單頁分鐘級時間戳前端過濾」這個變通法繞過，不是端點本身解決了。

這兩項都是站方 API 本身的限制，不是本專案的程式沒寫好，但目前也沒有任何 workaround 腳本把「前端過濾」這個變通法固定下來——每次都得靠 agent 臨場想。
