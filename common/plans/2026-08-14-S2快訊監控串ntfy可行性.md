# AP／RT 快訊（NOTIFICATION）串 ntfy 可行性

- 日期：2026-08-14
- 性質：**可行性調查，不是規則、不是授權實作**
- 問題：AP、RT 快訊跳出時，能不能用 API 監看並轉到現有 ntfy
- 相關：[`2026-08-03-RT即時快訊API.txt`](../investigation-logs/2026-08-03-RT即時快訊API.txt)（RT 鈴鐺，今日仍通）；[`scripts/s2_notify.ps1`](../../scripts/s2_notify.ps1) 的 `Send-Ntfy`（頻道在 `%USERPROFILE%\.s2-ntfy-topic`，不進版控）

> 本檔不寫 ticket、cookie、userId。這次沒把任一則標成已讀、沒改使用者鈴鐺狀態。

---

## 一、先講結論

**可以串 ntfy，但做不到「彈窗的同一毫秒推過來」。**  
實務是：**開著已登入的 Playwright 頁面，輪詢官方快訊 API，新 ID 就呼叫現成的 `Send-Ntfy`。**

| | RT（鈴鐺 breaking-news） | AP（NewsAlert） |
|---|--------------------------|-----------------|
| 今日端點還在？ | 是，200 | 是，200 |
| 一次拿到什麼 | 近 24 小時inbox，今日 **65 則** 全是 `breaking-news` | **目前生效中的快訊清單 11 則**（`slugline=AP-US-APNewsAlert`） |
| 去重鍵 | `messageId` | `itemid` |
| 頁內 `evaluate`+`fetch` | 跨域擋（0803 已踩、120 秒） | 今日重放 **403**（缺頁面那組 header） |
| 正確讀法 | 讓頁面自己打，再讀 network；或長連 socket（**未測**） | 同上，讀 `nr_breaking_news` 的 network 回應 |
| 真・即時 push | `ws-active`／socket.io **未測** | 本頁沒看到 websocket |
| ntfy | 現成 `Send-Ntfy`，掃帶／保活已在用 | 同左 |

「每當快訊跳出」若是指 **OS／網頁 toast 同一瞬間**：兩邊都還沒驗到穩定的長連通道。  
若是指 **一兩分鐘內推到手機**：輪詢就夠，而且 RT 快訊本來就比影片早（0803：直升機 21:32 快訊、影片更晚）。

**不要做**：獨立 HTTP collector（RT 要 ticket、AP 要特殊 header，一漂就靜默沒快訊）。

## 二、RT（今日複驗 0803 配方）

```
GET https://ap-northeast-1.rcp-api.reutersconnect.com/ws-active/messages/user
    ?_type=breaking-news,calendar-event,account-alert
```

驗證：頁面先 `POST …/ws-active/auth-ticket/issue`，再用 ticket。  
今日另見 `GET /api/ad-hoc-notifications/active`＝產品 webinar 廣告，**不要當快訊、不要推 ntfy**。

回應（與 0803 相同）：`{ success, messages[] }`  
每則：`msg`（全大寫一句）、`created`（unix 秒）、`ttl`（約 +24h）、`is_read`、`sourceEventId`、`_type`、`messageId`。

今日樣本：65 則、時間約 03:20–23:55（台北）、**全部 unread**、類型全是 `breaking-news`。  
例：美再派航母赴中東、法官駁回告哈佛案、利比亞氣井——密度很高。

注意：

- **24 小時後 API 就沒了**，要留存得自己存。
- 不要打 `messages/set-read/user`（今日 network 有這支；一標已讀鈴鐺就沒了）。
- 65 則／20 小時若每則都 ntfy，會把頻道訓成雜訊。要關鍵字／只推未讀增量／合併「同一事件連發」。

長連：0803 寫 socket.io 理論可聽、**仍未測**。第一版用輪詢即可（每 60–120 秒，或掛在現有 30 分鐘保活上——保活對快訊太疏）。

## 三、AP

頁面載入會打：

```
GET /v1/nrsubscription/alerts/nr_breaking_news?cacheBuster=…
GET /v1/nrproxy/broadcast_message?app=apnr_14&cacheBuster=…
```

`broadcast_message` 今日是空的產品廣播（date=2026-06-18），**不是快訊**。

`nr_breaking_news` 今日是 **11 筆陣列**，每則只有四欄：

| 欄 | 例 |
|----|----|
| `itemid` | 32 碼 hex |
| `slugline` | `AP-US-APNewsAlert` |
| `arrivaldatetime` | `2026-08-13T19:12:51Z` |
| `headline` | 一句快訊（含 “AP source says” 這種） |

這是「此刻看板」不是 RT 那種 24h inbox。新快訊＝清單裡多一個 `itemid`；過期／撤下＝從清單消失。  
推 ntfy 用 **itemid 去重**；headline 當 body。

頁內自己 `fetch` 這支今日 **403**。跟 RT 一樣：不要自己組請求，讀頁面已發出的那筆。

沒看到 websocket。要「跳出就推」只能 **短間隔輪詢**（建議 30–60 秒），或之後再挖 AP 有沒有 SignalR（本頁沒發）。

`/home` 仍可能先掉到 Live；監控腳本應停在 Latest 或直接打 API（若之後找出可重放的 header）。

## 四、怎麼接到現有 ntfy（建議形狀，未開工）

現成件：

- `Send-Ntfy`：Title ASCII、中文放 body、curl.exe、失敗不炸主流程
- topic 檔：`%USERPROFILE%\.s2-ntfy-topic`

建議獨立小守護（**不要塞進掃帶 agent**，以免每輪燒 token）：

```
Playwright 持久 profile（與掃帶同一 user-data-dir）
  ├─ 分頁常駐 RT /all?media-types=vid
  ├─ 分頁常駐 AP Latest
  ├─ 每 60s：等頁面自己打 messages/user、nr_breaking_news
  ├─ 讀 network 回應 → 與本地已推 ID 比
  └─ 新 ID → Send-Ntfy（Priority 可對 breaking 提高）
鎖：掃帶持有 .s2-scan.lock 時，監控暫停或只讀、不搶 profile
```

過濾（建議第一版就做，否則 RT 會洗版）：

1. 只推 `breaking-news`／`AP-US-APNewsAlert`
2. 同一 `sourceEventId` 或 headline 前 40 字 10 分鐘內合併
3. 可選關鍵字白名單（台／中／美／戰爭／空難…）— **要你拍板**
4. 已推 ID 落小檔，重開不死灰復燃

**不要**：evaluate 把 ticket `return` 出來；用獨立 collector 硬打 rcp-api；把快訊寫進晚班交接素材行（那是另一條規則，MASTER 沒裁定）。

## 五、和「彈窗當下」的落差

| 期望 | 現況 |
|------|------|
| toast 一出現就推 | 未驗到可用長連；輪詢有 30–120 秒延遲 |
| 跟鈴鐺未讀同步 | RT 可看 `is_read`，但不要改它 |
| 取代 S2 掃帶 | 不行。快訊是文字先行指標，影片／三段式仍要掃帶 |
| 掛在 30 分鐘保活 | 太疏，會漏一串快訊 |

保活繼續管「登入死了沒」；快訊監控是另一條、更密的心跳。
