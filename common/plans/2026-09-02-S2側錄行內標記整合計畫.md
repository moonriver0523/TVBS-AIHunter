## 0. 背景

`scripts/s2_state.py` 的 `patch_marks()`（約 L751–810）是 `patch-entry --alert` 的核心函式，
負責在素材行上插入／替換 🔴／🟡／⭐／🔖 前綴。目前 **L763 明確排除側錄行**：

```python
_, bare = sv.strip_mark(first)
if sv.SIDE_RE.match(bare) or not sv.LINE_RE.match(bare):
    return None, "非素材行（側錄／兩行式），不套標記格式"
```

排除原因不是技術不可行，是兩件事沒接上：

1. **格式不同**：通訊社三段式素材行是單行、有括號結構（`(來源 形式) (BITE) ▎…`）；
   側錄是兩行式（TC行＋SUPER、內容另起一行），逐字不摘要、不設字數上限、不用 `▎` 分段。
   `patch_marks()` 目前的拆解／組裝邏輯是照三段式括號結構設計的。
2. **判斷單位不對齊**：通訊社標記是「一行＝一則編輯判斷」；側錄常態被切成十幾個 TC 段落，
   要合併成「一則」才有意義（`side_units()` / `fold_side()` 的既有分組邏輯），
   標記該下在哪一段沒有定案——**本次使用者已裁定：首段**。

已有兩個佐證顯示技術路徑可行、不是重新發明：

- **時段標記（▲●◆）已經證明同一套「行首插記號」機制能套到側錄 TC 行**
  （`common/14-S2b-側錄轉譯摘要.md` C-0：「隔夜側錄的標記沿用通訊社那套……加在
  `CNN 160106` 這類 TC 行行首」；`s2_validate.py` 的 `MARK_RE`／`RED_RE`／`SUBALERT_RE`／
  `STAR_RE`／`AIRED_RE`／`HILITE_RE`（L80–113）本身是**通用**的前綴正則，不分素材行/側錄行）。
- **檔頭 🔴 重大提醒行已經能指向側錄 TC 碼**（`s2_validate.py` ~L460–464：
  「檔頭重大也可以指向側錄」），代表「重大」語意在檔頭層級已經半整合。

## 1. 裁定：首段代表整組

- **側錄單元**的定義**沿用既有分組邏輯，不新造一套**：連續、同來源（`SIDE_CNN`／`SIDE_NHK`）、
  同三層歸位（大／中／小分類）的 TC 段落算一組。這個定義目前有兩份獨立實作、行為一致：
  - `side_units()`（`s2_validate.py:265`，txt 文字層，供品質掃與檔頭「側錄 N 則」統計用）
  - `fold_side()`（`s2_render_matrix.py:109`，rows 層，供 T/C 矩陣渲染用，
    且已經處理過「單元 vs 首段」的概念——`tc_id` 就是「單元內第一個有 T/C 的段」，
    與本計畫「首段代表整組」的精神一致，可直接參照其寫法）。
- 🔴／🟡／⭐／🔖 **只寫在該單元的第一段（依收錄順序最早出現的那個 TC 段）**，
  其餘段落不重複寫，也不允許誤標在非首段。
- render 端摺疊整組成一列時（`fold_side` 行為），標記自然只需要讀首段——**這點如果查證屬實，
  render 端理論上不用改**，見下方 §4e。

## 3. 待查證（動工前必須先確認，不可用臆測代替）

1. **`state.json` 的 `items[]` 儲存順序，是否已經等同「同單元彼此相鄰」？**
   `side_units()`／`fold_side()` 目前都是在**已渲染的 rows/txt**上做分組，那時資料已經按
   大／中／小分類排序過。但 `patch_marks()` 操作的是 **state.json 的原始 items 列表**
   （`add-side` 逐段 append 進去的順序），這份順序未必等於渲染後的分類相鄰順序——
   尤其是「舊格式先入庫、事後用 `set-tc` 補標」「同一單元跨兩輪 `add-side` 交錯寫入」
   這幾種混合情形（`join_tc()` 的 docstring 已點名這類邊界案例）。
   **這條沒查清楚，「找同一單元的第一段」這個判斷式就不能亂寫**——必須先抓一批真實生產
   `{MMDD}-s2-state.json`，離線核對 items 順序與渲染後的單元分組是否一致，不一致的比例有多高。
2. **首段要用「TC 時間序」還是「入庫（add-side 呼叫）順序」定義？**
   理論上兩者該一致，但候選檔跨天/跨輪次分批 `add-side`、或事後補件時可能不同。
   需要先看清楚兩者何時會分歧、分歧時要用哪一個。
3. **`patch-entry` 對「非首段」的擋法要怎麼回報**：擋下後要不要直接印出「本單元首段是 `{id}`，
   請改標那個」，讓 agent 一次就能重下對的指令（比照 `s2_platform_merge.py:110-115` 那種
   「帶原始值明確失敗」的既有風格），還是只回一句「非首段不可標」讓呼叫端自己去查。

## 4. 實作步驟（草案，依 §3 查證結果可能調整順序或做法）

### 4a. `s2_state.py`：擴充 `patch_marks()`
- 移除 L763 對 `SIDE_RE` 的早退，改成**分流**而不是直接拒絕。
- 側錄行沒有括號結構，`tail` 就是 `{來源} {MM-DD}? {TC}[（SUPER）]` 那段；
  `--bite` 對側錄無意義（側錄沒有 `(BITE)` 第二括號機制），要**直接拒絕**並回報
  「側錄無 BITE 括號可補」，不要讓它靜默不生效。
- prefix 插入點沿用現有機制（`period + new_alert + aired + hilite` 一律插在 `tail` 之前）——
  這個插入點已經被時段標記（▲●◆）驗證過能正確套用在側錄 TC 行首，不需要重新設計。

### 4b. 新增「首段判定」helper（暫名 `side_unit_head(state, item_id)`）
- 依 §3 查證結果決定實作方式。**最小風險版本**（若 items 順序確認可靠）：
  在同一批 `items[]` 裡，依陣列出現順序找同 `(source, category)` 的第一筆 id 作為首段；
  傳入的 `item_id` 若不等於該首段 id，一律拒絕並附上正確首段 id。
- 若 §3-1 查出 items 順序不可靠，本節要改設計（例如落地時就同步記一個 `unit_head_id` 欄位，
  由 `add-side` 寫入當下直接算好，不倚賴事後從陣列順序反推）——**這是查證會改變實作路徑的
  分水嶺，先查證再定案，不要兩條路都先寫**。

### 4c. `patch-entry` CLI 護欄
- `--alert` 對側錄非首段 id：拒絕，錯誤訊息帶正確首段 id。
- `--bite` 對側錄任何 id：拒絕，錯誤訊息說明側錄沒有 BITE 括號機制。

### 4d. `s2_validate.py` 品質掃新增檢查
- 用同一套單元分組邏輯反查：若標記出現在非首段（例如舊資料或人工誤改），
  品質掃要能命中回報——防止「裁定跑掉」卻沒人發現（比照 R19「畫面好誤標」的
  處理精神：先讓判準能捕捉到，再回頭檢討要不要收緊）。

### 4e. render 端驗證（**大機率不用改動，但必須實測，不能只憑邏輯推論**）
- `fold_side()` 摺疊單元時 `cur = dict(r)` 取的就是第一列的完整內容，
  理論上首段若帶了標記前綴，摺疊後那一列應該直接帶著標記顯示。
  但這只是讀程式碼的推論，**要用真實測資跑一次，確認摺疊後的顯示結果符合預期**，
  尤其要驗證舊版 `s2_render.py`（非矩陣版）那條路徑是否也一樣正確處理。

## 6. 風險與回滾

| 風險 | 緩解 |
|---|---|
| `patch_marks()` 是通訊社／側錄共用的函式，側錄分支寫壞可能連帶影響既有通訊社標記功能 | 維持既有 `LINE_RE` 判斷分支不變，只新增 `elif SIDE_RE` 分支；兩分支各自獨立測試 |

| 回滾成本 | 純函式改動＋純資料前綴文字，git revert 即可，沒有不可逆的資料結構遷移 |
