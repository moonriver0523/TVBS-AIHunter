## 0. 背景

`scripts/s2_state.py` 的 `patch_marks()`（約 L751–810）是 `patch-entry --alert` 的核心函式，
負責在素材行上插入／替換 🔴／🟡／⭐／🔖 前綴。目前 **L763 明確排除側錄行**：

```python
_, bare = sv.strip_mark(first)
if sv.SIDE_RE.match(bare) or not sv.LINE_RE.match(bare):
    return None, "非素材行（側錄／兩行式），不套標記格式"
```

排除原因不是技術不可行，是兩件事沒接上：

1. **格式不同**：通訊社三段式素材行是單行、有括號結構（`(來源 形式) (BITE) ▎…`）；
   側錄是兩行式（TC行＋SUPER、內容另起一行），逐字不摘要、不設字數上限、不用 `▎` 分段。
   `patch_marks()` 目前的拆解／組裝邏輯是照三段式括號結構設計的。
2. **判斷單位不對齊**：通訊社標記是「一行＝一則編輯判斷」；側錄常態被切成十幾個 TC 段落，
   要合併成「一則」才有意義（`side_units()` / `fold_side()` 的既有分組邏輯），
   標記該下在哪一段沒有定案——**本次使用者已裁定：首段**。

已有兩個佐證顯示技術路徑可行、不是重新發明：

- **時段標記（▲●◆）已經證明同一套「行首插記號」機制能套到側錄 TC 行**
  （`common/14-S2b-側錄轉譯摘要.md` C-0：「隔夜側錄的標記沿用通訊社那套……加在
  `CNN 160106` 這類 TC 行行首」；`s2_validate.py` 的 `MARK_RE`／`RED_RE`／`SUBALERT_RE`／
  `STAR_RE`／`AIRED_RE`／`HILITE_RE`（L80–113）本身是**通用**的前綴正則，不分素材行/側錄行）。
- **檔頭 🔴 重大提醒行已經能指向側錄 TC 碼**（`s2_validate.py` ~L460–464：
  「檔頭重大也可以指向側錄」），代表「重大」語意在檔頭層級已經半整合。

## 1. 裁定：首段代表整組

- **側錄單元**的定義**沿用既有分組邏輯，不新造一套**：連續、同來源（`SIDE_CNN`／`SIDE_NHK`）、
  同三層歸位（大／中／小分類）的 TC 段落算一組。這個定義目前有兩份獨立實作、行為一致：
  - `side_units()`（`s2_validate.py:265`，txt 文字層，供品質掃與檔頭「側錄 N 則」統計用）
  - `fold_side()`（`s2_render_matrix.py:109`，rows 層，供 T/C 矩陣渲染用，
    且已經處理過「單元 vs 首段」的概念——`tc_id` 就是「單元內第一個有 T/C 的段」，
    與本計畫「首段代表整組」的精神一致，可直接參照其寫法）。
- 🔴／🟡／⭐／🔖 **只寫在該單元的第一段（依收錄順序最早出現的那個 TC 段）**，
  其餘段落不重複寫，也不允許誤標在非首段。
- render 端摺疊整組成一列時（`fold_side` 行為），標記自然只需要讀首段——**這點如果查證屬實，
  render 端理論上不用改**，見下方 §4e。

## 3. 待查證（動工前必須先確認，不可用臆測代替）—— ✅ 2026-09-02 已查清

1. **`state.json` 的 `items[]` 儲存順序，是否已經等同「同單元彼此相鄰」？**
   **✅ 查證結論（用 `0902-s2-state.json` 複本實測）：不等同。** 213 則側錄項目、45 個
   distinct `(source, category)` 分組，但陣列位置上同一分組會被拆成多個不連續區塊
   （例：`SIDE_CNN` 某分類拆成 3 段不連續區塊、`SIDE_NHK` 某分類拆成 2 段），因為
   CNN／NHK 兩條側錄常在同一批候選檔裡交錯 `add-side` 寫入。**因此「陣列裡第一次
   出現」不能當首段判準**——已改成跨整份 `items`（不要求相鄰）依 `(source, category)`
   分組、比較 id 帶的 TC 取最早者，實測 45 個真實分組全部正確判出首段（見
   `side_unit_head_id()`，`s2_state.py:751-780`）。
2. **首段要用「TC 時間序」還是「入庫（add-side 呼叫）順序」定義？**
   **✅ 已定案：TC 時間序**——這個選擇同時解掉查證 1 的陣列不相鄰問題（不必管陣列
   位置，只比 id 帶的 `MM-DD`＋6碼 TC）。**已知限制**：同單元裡若混了缺日期的舊格式
   段落（2026-08-09 前的側錄資料），無法排序，`side_unit_head_id()` 明確回傳 `None`
   讓呼叫端停下，不用猜的（測試已覆蓋此案例）。
3. **`patch-entry` 對「非首段」的擋法要怎麼回報**：**✅ 已採用「帶原始值明確失敗」**——
   擋下時直接印出「非本單元首段，標記只能下在首段 `{正確id}`」，讓 agent 一次就能
   重下對的指令。**過程中連帶發現並修掉一個既有缺口**：`cmd_patch_entry` 的
   `unchanged` 清單原本只收集理由、從未印出來（`s2_state.py` 舊版 L890-891 只印
   `done`），本次補上輸出，否則新護欄的訊息會被吞掉、白擋。

## 4. 實作步驟

### 4a. ✅ `s2_state.py`：擴充 `patch_marks()`（`d03cbf9`）
- 移除舊 L763 對 `SIDE_RE` 的早退，改成分流：`is_side = SIDE_RE.match(bare)`，
  非側錄非素材行才拒絕。
- `--bite` 對側錄行直接拒絕（「側錄沒有 (BITE) 括號機制，--bite 對側錄無效」），
  不讓它靜默不生效。
- prefix 插入點沿用既有機制（`period + new_alert + aired + hilite` 插在 `tail` 之前），
  不需重新設計——實測確認可正確套用在側錄 TC 行首。

### 4b. ✅ 新增「首段判定」`side_unit_head_id(state, item_id)`（`d03cbf9`）
- §3 查證證實 items 陣列順序不可靠，**改採 TC 時間序**：跨整份 `items` 依
  `(source, category)` 分組（不要求相鄰），取 id 帶的 TC 最早者為首段。
- 分組裡有段落缺日期／TC 格式認不得 → 回傳 `None`，呼叫端停下不猜。

### 4c. ✅ `patch-entry` CLI 護欄（`d03cbf9`，`cmd_patch_entry`）
- `--alert` 對側錄非首段 id：拒絕，錯誤訊息帶正確首段 id
  （「非本單元首段，標記只能下在首段 `{id}`」）。
- `--alert` 對「單元裡有段落無法排序」：拒絕並說明原因，不猜。
- `--bite` 對側錄任何 id：在 `patch_marks()` 層級已拒絕（4a）。
- 連帶修復：`unchanged` 清單原本收集了理由卻從未印出（既有缺口，非本次引入），
  已補上輸出，否則本節新增的擋法訊息會被吞掉。

### 4d. ⬜ 尚未動工：`s2_validate.py` 品質掃新增檢查
- 用 §4b 的同一套單元分組邏輯反查：若標記出現在非首段（例如舊資料或人工誤改
  raw_entry），品質掃要能命中回報——防止「裁定跑掉」卻沒人發現（比照 R19
  「畫面好誤標」的處理精神：先讓判準能捕捉到，再回頭檢討要不要收緊）。
- 目前風險有限：唯一能寫入標記的入口是 `patch-entry`，而 4c 的護欄已經擋住
  「透過這個入口誤標非首段」；缺口只在「有人手改 JSON 或用其他指令繞過」，
  優先度低於 4e。

### 4e. ⬜ 尚未動工：render 端顯示驗證
- `fold_side()`（`s2_render_matrix.py:109`）摺疊單元時 `cur = dict(r)` 取的是
  第一列的完整內容，理論上首段帶了標記前綴、摺疊後應該直接帶著顯示——但這只是
  讀程式碼的推論，**沒有實測過**。待做：真實標一則側錄首段、跑 render、確認
  矩陣版與舊版 `s2_render.py`（非矩陣）兩條路徑摺疊後都正確顯示標記。
- **一個尚待釐清的設計張力**（留給 4e 實測時一併確認，不是本次臆測的答案）：
  `side_unit_head_id()` 的分組跨整份 `items`、不要求陣列相鄰；`fold_side()`／
  `side_units()` 的分組建立在**已渲染的 rows**（依 `======大分類====== →
  【中主題】 → 小分題` 標頭排序後，同分類本來就會被排在一起）。工作假設是：
  render 對同一標頭底下的段落會依 TC 序排列，所以兩套分組在渲染後應該收斂到
  同一個結果——但這只是假設，4e 要用真實資料驗證，不能只憑推論就當作成立。

## 6. 風險與回滾

| 風險 | 緩解 |
|---|---|
| `patch_marks()` 是通訊社／側錄共用的函式，側錄分支寫壞可能連帶影響既有通訊社標記功能 | 維持既有 `LINE_RE` 判斷分支不變，只新增 `elif SIDE_RE` 分支；兩分支各自獨立測試 |
| §3 查證結果推翻「items 順序可靠」假設，4b 要改設計 | 本計畫書已把 4b 明確標成「依查證結果可能改路徑」，不是查完才發現要整份重寫 |
| 回滾成本 | 純函式改動＋純資料前綴文字，git revert 即可，沒有不可逆的資料結構遷移 |
