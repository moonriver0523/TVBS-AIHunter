## 2. 目標與非目標

| 目標 | 可驗證結果 |
|---|---|
| 跨日找得到素材 | 一次查指定素材日期範圍、關鍵字、T/C、來源、中主題，不需逐日開交接頁 |
| 日期不誤導 | 每筆顯示素材日及其依據、首次入庫輪、所屬班次；未知或估計有明確標示 |
| 身份與版本可追溯 | 同一來源項目跨班重遇有 observation；更新內容有版本；不同來源同事件維持各自素材 |

## 3. 資料模型：身份、三種日期、版本與引用

### 3.1 三種日期的正式定義

| 概念 | 建議欄位 | 定義與規則 |
|---|---|---|
| 班次日 | `shift_id="s2:2026-09-30"`、`shift_date`、`window_start_at / window_end_at` | 交接工作班次，完整年月日；`MMDD` 只作舊檔顯示。窗口可跨曆日，不能充當素材日 |
| 素材日 | `material_date`、`material_at_utc`、`material_date_basis`、`date_quality / date_confidence` | **依來源原稿內嵌日期／來源中繼資料決定素材自身日期，不用班次日。** AP／RT 優先採可明確辨認的主素材 shotlist／dateline 日期；其他來源依下表。日期與時刻分開，並非一律等於發布時間 |
| 入庫時間 | `first_seen_at_utc / first_seen_precision`；observation 的 `checkpoint / run_id` | 全庫最早已知正式入庫輪；歷史只有 checkpoint 時，precision=`checkpoint_anchor`，不假裝是實際落檔秒數 |

使用者 2026-10-02 已確認 R45 的方向，故本輪修正前稿「一律以發布日為主、是否用內嵌日期另裁」的建議。**來源日期優先、不得用班次日替代，已是本案約束；同等主日期採最早候選且保留 ambiguous，亦已裁定。未知日期的預設查詢行為仍待後續介面裁決。** 來源的發布、傳送、到站、更新、拍攝、事件日期仍分欄，不能把 shotlist 日期寫進 `source_published_at_utc`。

共同擷取契約：`content_dates[]` 每筆存 `kind=filmed/event/published/unknown`、`raw_value`、`date_start / date_end`、`source_timezone`、原文區段位置／證據片段、`extractor_version`。固定解析器只處理已定義的來源區段與格式，不對全文取第一個日期。`date_confidence=high/medium/low/unknown` 與 `date_quality=structured_source/embedded_verified/inferred/inferred_recording/ambiguous/ingestion_fallback/unknown` 分開；衝突另有 `date_issues[]`，不只用一個分數掩蓋。

- **R45 驗收案例**：MASTER 記載 `APcns007383` 為 12 Sept、`AP4684892` 為 10 Sept，在 09/16 晚班收錄。若原稿確認其為主素材日期與2026年，分別歸 09/12、09/10，班次仍是09/16，首次入庫仍保留0916檢查點。這是帳本查證紀錄，**本次未取得0916原始state，不能宣稱重新解析驗證**。
- **反例必測**：R45 已訂正 `AP4684982` 抓到2021年歷史畫面、`APcctv079619` 抓錯內文日期的誤判。0930 的 `AP4687838.src_text` 含 `30 July 2026` 也只能先保留證據，未辨明主素材前不自動改歸07/30。PageSize 增大導致舊稿的早期因果推測已被帳本訂正，本案不沿用。
- **多日期（D-候選1，2026-10-02 已裁定）**：有明確主日期採主日期，其餘保存；多個同等主日期無主次時，`material_date` 採**最早候選日期**，仍標 `date_quality="ambiguous"`，`material_date_range` 與 `content_dates[]` 保存完整候選範圍及證據，供後續重判。日期索引可查最早日，另可選候選範圍相交查詢；不得把暫列的最早日呈現成已確認的唯一主日期。未辨認為主素材的內文／歷史日期不因本裁決自動升格為候選主日期。
- **來源日期全缺**：採最早可靠正式入庫輪，basis=`ingestion_fallback`，介面顯示「依入庫日暫列」；連入庫日期都不可靠則 null。0930 的833筆一般素材缺結構化發布時間，但有 `src_text` 可擷取；實際退路筆數須跑解析器後量測，**不再斷言833筆全走入庫退路**。

精確時間以 RFC 3339 UTC 保存、介面轉 `Asia/Taipei`。ET 使用 `America/New_York` 處理夏令時間；已在臺灣時區的值不再加八小時。只有日期的 shotlist 以來源當地曆日及 `precision=date` 保存，`material_at_utc=null`，**不虛構午夜後轉換日期**；時區不明或可能跨日則提供範圍與標記。`material_date` 因而是有依據的日期索引：有時刻者換算臺灣曆日，只有日期者明示「來源日期，無時刻」。

另存 `source_published_at_utc / source_transmitted_at_utc / source_updated_at_utc / source_created_at_utc / source_arrived_at_utc / recorded_at_utc` 及 `time_evidence`。`entry_updated_ts` 無 offset 時須標本機推定，不能取代來源時間；`warehouse_ingested_at_utc` 不取代歷史 first_seen；`platform.candidate_checkpoint` 不提早正式入庫（R47）。同一素材日可跨多班、同班可含多個素材日；`material ↔ shift` 以 observations 多對多連結。

### 3.2 身份方案：穩定主鍵與日期索引分開

**全庫主鍵是穩定 `material_id`；按日查詢／實體匯出鍵是 `(material_date, material_id)`。** 日期校正不能讓素材身份改變，班次不進入強身份鍵。這同時滿足「按素材日存放」與「跨日更新仍是同一素材」。

**文件落差已確認**：[common/17-網址素材整併.md](../17-網址素材整併.md) 第47、53、188、194行仍示範 `YNA01` 並描述每日歸零，與 D23 新制不一致；這是舊文件待修，不是新版 ID 仍會每日撞號。歷史流水號確有跨日碰撞風險：`legacy:2026-09-30:YNA:YNA01` 與 `legacy:2026-10-01:YNA:YNA01` 必須是不同暫定鍵。日期來源是完整班次日，不能只用 MMDD。本文不修改該規則文件。

### 3.5 去重、更新、日期校正與刪除

| 情況 | 決策 |
|---|---|
| 同一快照重匯 | receipt 命中後零新增；不增加素材、版本或重複 observation |
| 同來源強身份跨班再遇、內容相同 | 保留一筆 material，新增班次 observation；全庫 first_seen 取最早可靠值 |
| 同身份原文／文稿更新 | 保存新 revision；舊版仍能查。`pending→has_script` 有明確轉換紀錄，不覆蓋前版 |
| 原文不變，只改中文摘要／分類／T/C | 記 editorial 或 metadata revision，不冒充來源改稿；來源內容 hash 與編輯 hash 分開 |
| 只有 last_checked 或 renderer timestamp 改變 | 可更新觀測資訊，不為每輪製造完整內容版本；控制年增量 |
| 舊快照晚於新快照匯入 | 來源版本／可信更新時間優先；再用快照原始時間排序，不按匯入順序蓋 current。無法判斷先後時標 conflict，保留兩版，不任選較新匯入者 |
| 確認來源主素材日／發布日早於暫列入庫日 | 同一 material 校正日期並記 date revision；重建受影響的新舊日索引。舊日分片撤出該 current 指標，永久引用仍以 material ID 解析 |
| 從後續班次 state 消失 | 不等於刪除；換班原本就清空。撤稿／隱藏要有明確 tombstone 與理由，不能靠集合差推論 |
| 雙來源報同事件／同一畫面轉供 | 保留各自素材與限制；建立相關關係，不能以摘要相似當身份相同 |

歷史 Archive 多半只有班次最後版本，**無法還原已被 `apply_update()` 覆蓋的所有中間稿**。回填標 `history_completeness="final_snapshot_only"`；新影子匯入也只能保存實際觀測到的版本，兩次快照間的修改不保證完整。若未來要逐筆完整事件史，另案裁定事件出口，不在第一版假稱已具備。

### 3.6 與登記簿、T/C、大分類、素材包的關係

大／中／小分類回答交接歸位；T 是議題類型，C 是地緣，皆可複選；主題登記簿管理名稱、別名與收納範圍；素材包回答「這次製作選哪些素材」。四者分開，不用大分類機械推定 T，也不替使用者增刪正式 T/C 字典。

登記簿目前沒有永久 `topic_uid`。建議先在外電庫建立持久對照表，記住首次對應的 canonical 名、後續 alias 與 registry 快照；改名不能每次重新雜湊產生新題 ID。匹配不明或歷史名稱不在現行登記簿時保留 `unresolved`，不自動開新題。此對照及版本需備份，才能在重建資料庫時保住素材包引用。登記簿 `first_seen` 是題名歷程，**不是成員素材的發布日**。

側錄合「則」屬交接顯示規則：目前依相鄰 `(src, 大, 中, 小)` 摺疊。外電庫保留每段身份與原文，另存 `shift_display_group` 供追溯；不把 224 個顯示群組當成永久素材 ID，也不跨日期僅因同分類就黏成一則。

### 3.7 A7：把「刻意去重」與「真正未處理」分開

[master-detail/A.md](master-detail/A.md) 的 A7 記載 AP5467678／80／81／82 與7677／7679為同內容不同剪輯／直式版本，部分以 note＋needs_review 保留。**目前程式已不完全等同早期「所有 missing 無法分辨」的描述**：[scripts/s2_audit.py](../../scripts/s2_audit.py) `reconcile()` 第214～335行，已比對前班 ID，並在第277～286行以 `needs_review` 的「不收／重複／排除／未收／跳過」文字排除一部分項目；但 note ID 在 state 集合內也會被算進 got。回傳值沒有結構化保留對象、去重理由與證據，文字抑制不能證明完整處置。

### 4.2 三案比較與單一推薦

## 5. 寫入路徑與 Archive 回填

### 5.1 單向鏡射，先影子執行

```text
既有來源／側錄／網址交件
          ↓
既有 S2 單一寫入路徑 → 每班 state → 權威 txt → 每班 HTML
                            │
                            └─ 唯讀快照 → 待匯入收據 → S3 匯入器
                                                        ↓
                                               本機 SQLite／版本
                                                        ↓
                                            分片匯出 → 驗證 → 發布
```

這裡的「雙寫」是**原流程完成後的非交易性鏡射**，不是要求 state 與資料庫同時成功。S3 的 upsert 只作用於 S3，不把現行 `add-batch` 的「既有 ID 跳過，更新另走 update-entry」改成 upsert。

| 階段 | 明確行為與失敗隔離 |
|---|---|
| 最初 | 手動指定唯讀複本與輸出目錄；不接正式 launcher、不跑來源抓取、不占用掃帶瀏覽器 |
| 取快照 | 完整讀一次 bytes、計算 hash、解析並留不可變複本；不在同次匯入反覆讀 live state。讀取期間變更或歸檔移走就稍後重試，不接管 `.s2-scan.lock` |
| 判斷可用 | 分清「觀測快照」與「完成交接快照」；不能只以行程 exit 0 判定完整。後者核對對應 txt 的 `last_render_sha` 與 state 內容一致性／收據；無法證實時保留 provisional 標示 |
| 匯入 | 外電庫自己的單一 writer；短交易、來源快照冪等。壞列隔離並列出數量；全檔損壞不取代前版。狀態為 `complete / partial / failed`，不得用成功訊息掩蓋部分失敗 |
| 後續接線 | 待裁決後，既有收工尾端最多做有上限的通知／快照交付，網路上傳與全文索引在掃帶之外執行。通知超時、磁碟滿或匯入器停止，只留待補紀錄，不改掃帶成功狀態 |
| 補漏 | 以 live＋Archive 內容 hash 對帳補收，通知遺失可重建。若正式接線仍可能影響輪次，直接停用通知回到手動匯入 |
| 更新延遲 | 介面同時顯示「來源班次最後更新」「外電庫最後匯入」「目前發布版本」；不可只印 HTML 產生時間讓使用者誤認資料最新 |

初版不新增排程，不引進第二個 state writer，符合 D24。未來如何喚起匯入／發布作業列為 D-候選，不在本計畫偷渡成已核准背景服務。必要的短期一致性護欄放在匯入邊界，不要求先完成 A45 全套重構。

### 5.1a A45 與外電庫的責任接縫

**A45 處理上游 S2：執行環境、五站抓取、規則／腳本、state 與收工；本案處理下游 S3：已提交輸出的跨班保存、檢索與包引用。** 交付點在既有單一 writer 已提交 state、權威 txt 已完成之後；HTML 仍照原流程執行，其失敗不取消 txt 或 S3 待處理交付。S3 不讀正在拼裝的 batch 當可用素材，也不要求改成 state＋DB 分散式交易。

建議交付 envelope 含 `handoff_schema_version / run_id / checkpoint / shift_id / state_sha256 / state_bytes / txt_sha256 / producer_version / completed_at / completion_status / raw_receipt_refs / candidate_disposition_refs`。**這是擬議契約，現行檔案未必已有完整 envelope。** 初期工具從唯讀複本建立可驗證欄位；缺少來源收據或完成證據即標 unknown／partial，不由 agent 補造。來源收據缺失不阻止已觀測素材進影子庫，但必須限制 coverage 宣稱。

| 與 A45 的重疊 | 單一責任與避免衝突 |
|---|---|
| F3／P0b：來源收據可信度 | S2 擁有 `run_id / site / checkpoint / fetched_at / schema / hash / row_count` 與原始來源收據；S3 只驗證、引用，不自行抓站或另造相互矛盾收據。雜湊能驗完整性，不能獨自證明來源真實 |
| F4／P2：機械工作腳本化 | S2 的 typed raw receipt／decision patch 與 S3 的 ingest 契約分開版本化；可共用純 schema，但不把資料庫匯入藏進 LLM 決策階段 |
| F5：讀取副作用 | S3 使用顯式路徑的純讀取器，不 import 會自動選檔／觸發初始化的 state CLI 入口 |
| F7／P3：完成與覆蓋率 | S2 的 complete／degraded／aborted 原樣保存，與 S3 的 complete／partial／failed 匯入狀態分欄；exit 0、DONE、txt 存在都不是來源全覆蓋證明。A7 處置表接收明確理由與引用 |
| F8：單一 writer | 掃帶鎖與 state 寫入權留在 S2；S3 自己序列化 DB 寫入，不取得第二份 state 寫入權，不延長掃帶鎖等待網路或索引 |
| F10／P4：相容投影、不改 state／核心 DB | txt 與既有 renderer 不改，S3 使用下游投影；A45 不建議把 S2 改成 DB 的限制，與本案建立獨立 S3 庫並不衝突 |

A45 §7.3 亦未建議重啟固定抓取器作全面解方；後續 D24 又裁定不做核心重寫、新排程／併發 writer。因此本案不以「對齊 A45」為由重開那些方案。共同欄位與收據演進需協調，**A45 全套提案不是 Phase 0～2 前置條件**。

### 5.1b E9：固定寫入工具與上游抓取共用化的界線

[master-detail/E.md](master-detail/E.md) E9 已記規則禁止每輪手寫 fetch／parse，並已有 `s2_batch_prep.py`、`s2_platform_extract*` 等解析工具。A47 最新追記確認09-20的0100輪仍出現13支一次性腳本、10/02已清除；使用者補充事件涵蓋09/20～21及 `parse_ap_list_0100.py`、`generate_ap_entries_0100.py`、`verify_rt_details_0100.py`、`test_fetch_one.js` 等名稱。**目前 repo 沒有這13支原檔／完整當輪紀錄，不能重新驗證逐支內容或釐清兩日的精確輪次；數量與清除日期有 A47 支持，不能誤稱 E.md 已記載整起新事件。**

結論是規則文字與工具存在仍不足以阻止繞路。外電庫自 Phase 0 起就採固定、版本控制中的唯一匯入程式，例如擬議 `scripts/s3_warehouse.py ingest-snapshot --manifest … --db …`；輸入 envelope、日期抽取、來源辨識、canonical ID、source_link、upsert、receipt 全由工具組成。代理只能提交允許的參數／經驗證的決策欄位，不能手拼生產 JSON、直接執行 SQL，或為某一輪寫 `import_0100.py` 代替正式工具。解析器未知格式送隔離，透過正式版本更新修復，不在輪次內插入任意程式。

落地需有可測的限制：唯一 writer 的固定入口、schema／版本拒收、允許的輸入根與輸出根、交易與冪等、產生器版本收據；正式 DB 寫入權盡可能只給匯入服務帳號。若同一代理仍有相同作業系統帳號的任意檔案／shell 權限，**僅工具白名單與 `generated_by` 欄位無法形成硬隔離**，必須揭露剩餘繞過風險；正式接線前測試未授權直接寫入會被拒絕，或至少被完整性監測發現並阻止發布。這不是再多寫一句「禁止」就算完成。

E9 所提 `s2_fetch.js --site X --checkpoint Y` **目前未實作，不列為離線庫、回填與影子接線的強制前置**；否則會把下游價值綁上來源驗證與 D24 未准的上游改造。它可作獨立 E9 改善案，與 A45 的收據契約對齊；只有未來要求「候選完整對帳／新來源自動抓取」時，相應來源才必須先提供可靠抓取入口與覆蓋證據，不一定非用這個檔名。另列 D-候選14，原 E9 的約一小時估計不能當成完整上線工期。

若核准抓取共用工具，最低條件如下：

- 沿用 [scripts/s2_mcp.json](../../scripts/s2_mcp.json) 的 `C:\Users\User\.playwright-s2-profile-v4`、**headed** 瀏覽器；禁止另開 daily profile、偷偷切 headless。除設定檔外，也要驗證實際啟動參數／連線身分。
- 遵守 [scripts/s2_scan.ps1](../../scripts/s2_scan.ps1) 第104、485～487、514～517行的 `.s2-scan.lock` 與 headless 檢查。現行鎖採 FileStream、`FileShare.Read`；獨立入口需取得同一互斥權，已由 launcher 持鎖的子程序須驗證繼承的持鎖生命週期，不能重拿鎖造成自我死鎖，也不能只看 lock 檔存在就假稱已持鎖。
- 站別差異保留在 adapter；NS 的頁內權杖、AP cookie、RT 動態端點不能改成任意獨立 HTTP 猜路徑。工具不得新增並行瀏覽器／state writer，不得藉此重啟先前否決的全面固定抓取器。

### 5.2 回填步驟與可信程度

1. **列清冊，不搬檔。** 枚舉 `Archive/{YYYYMMDD}/{MMDD}-s2-state.json`，另納入 live 明確指定班次。記完整路徑、雲端 ID（可取得時）、大小、hash、年月日來源、讀取結果。只有 txt／rtf 的舊資料列入缺 state 清單，不默默當零素材。
2. **解班次年份。** Archive 資料夾年月日優先，交叉核對 `window_start`、checkpoint 與檔名；live 複本以有年份的窗口與使用者提供班次確認。禁止用執行當年硬補所有檔。現行 `New-ShiftState` 部分日期仍取 `Get-Date`，render 亦有取當年邏輯，因此不能呼叫它們重製歷史後再據此認定年份。
3. **解每筆日期與身份。** checkpoint 年份以該班窗口附近的完整日期解析，處理 12/31→01/01、跨月、閏日；相距不合理、來源時間在未來、缺 offset、壞 checkpoint 全列問題。依§3.1逐來源政策檢查 state 中繼資料與 `src_text` 主日期，再唯讀查同班 `_暫存` 的來源快照補強；不把 shotlist 日期寫成發布時間。新制 YNA／CNA ID 直接保留；舊流水號必加完整班次命名空間，不能用同名跨日覆蓋。連結由同一版本化工具生成。
4. **逐班匯入暫存資料庫。** 先三個相鄰班，再擴至清冊全部；可中斷續跑。每班報原始筆數、有內容、note、強身份、暫定身份、日期依據、隔離筆數；對帳為「輸入＝已處理＋隔離」，不要求去重後 material 數等於輸入筆數。若有原始候選收據，再獨立重建§3.7處置表；沒有就標候選覆蓋未知，不從25筆 note 猜出完整排除清單。
5. **驗證跨班關係。** 同 video ID 只一個 material、多 observations；RT 同短碼不同來源鍵保留兩筆；來源時間與班次不同仍落正確素材日；未知日期可查。真實跨班案例不足時以明確標示的合成測試補邊界，不能假稱已實證。
6. **發布與追溯。** 產生覆蓋清單：哪些班次已納入、缺哪些 state、日期暫列比例、隔離原因。先切外電庫自己的 active generation，原 Archive 和每班 HTML 完全不動。

回填只能重建「當時保存下來的資料」。不自動重抓缺失的 `src_text`，不重做 D8／R11 已裁定不補的舊資料；txt-only 復原若要做，另建 `legacy_text` adapter 與裁決，保留原行號／不確定身份，不混充 state 高可信回填。

## 6. 跨日讀取、檢索與手機體驗

### 6.1 查詢契約與索引

```text
search_materials(
  material_date_from, material_date_to, query,
  T[], C[], sources[], topic_ids[], kinds[],
  date_basis[], date_confidence[], include_unknown_date, include_uncertain_overlap, shift_ids[],
  text_scope, page_size, cursor, snapshot_id
) → items[], next_cursor, coverage, total_status, snapshot_id

get_material(material_id, revision_id?) → 詳情、日期證據、版本、班次、來源限制
```

日期查詢 `from` 含起日、`to` 含迄日，直接比對§3.1的素材日期索引。有精確時刻者按臺灣時區轉換，時間型查詢用下一日00:00前的半開區間；只有來源日期者按原曆日比對並顯示「無時刻」，不補假午夜。`include_uncertain_overlap` 另納入日期範圍相交的不確定項目，`include_unknown_date` 納入完全未知者，兩者不得冒充日期已確認。預設近七日，含「依入庫日暫列」並清楚標示；可切只看有來源日期。T 內多選 OR、C 內多選 OR、不同維度 AND，沿用目前互動語意；主題查詢先做 registry alias 解析。

預設關鍵字搜尋 ID／alias、主題、完整中文 `raw_entry` 與已存摘要，不使用目前 HTML `q[:400]` 當全部搜尋內容。進階「含來源原文」才搜尋 `src_text`，仍完整保留可取回。英數比對可忽略大小寫，但 material ID 原值不可改大小寫；中文字面檢索支援兩字詞，不承諾自動翻譯或語意同義。

本機先以日期／來源／標籤縮小集合，參數化查詢全文；FTS5 trigram 可加速部分子字串，但少於三個 Unicode 字元的全文匹配有限制，故「日本」「核電」等兩字詞要有明確的日期範圍內子字串退路，並以真實語料驗證。[SQLite FTS5 文件](https://www.sqlite.org/fts5.html)

Drive 發布版將搜尋文字與精簡欄位分片，詳情另載；要提供「含來源原文」時再匯出對應的文字索引片。Apps Script 執行同一查詢語意，不必執行 SQLite：先用日期／來源／T/C／topic 分片目錄，再做文字比對。未做好的搜尋範圍應停用並說明，不得讓「全文搜尋」實際只搜預覽。

**任意跨日範圍可續查，不靠一次跑完全年度。** 每次伺服端讀取有 byte／時間預算，初值 8 MiB 或 5 秒、先到即停止，回傳已掃日期與續查 cursor；每頁 50 筆，最大 100 筆。cursor 綁定 generation、查詢 hash、日期／分片／列位置，防混版與重複；排序固定素材日倒序、material ID。此階段全歷史可能分多次完成，尚未掃完顯示「已搜尋至某日」，不能顯示假完整總數或「沒有素材」。只有 coverage 完整才給 exact total。

### 6.2 兩個入口各自保留用途

| 晚班交接頁 | 外電資料庫頁 |
|---|---|
| 「這班新收到什麼、哪些重大、最新一輪有哪些」 | 「指定素材日期與議題，我們手上有哪些」 |
| 班次日與原時段標記、現有 T/C 互動 | 素材日＋日期依據、全庫最早入庫、所有相關班次 |
| 每班單檔照常產出，失敗隔離原則不變 | 一個固定入口、分頁取資料、顯示覆蓋範圍 |
| 保留現行 `?date=MMDD` 的相容路徑 | 新路由完整 `YYYY-MM-DD`，例如 `?view=warehouse&from=2026-09-29&to=2026-10-01` |

先讓新頁有「回到晚班交接」連結；反向加入口待 UI 階段核准再動 HTML。歷史素材連回指定班次時，需新增有年份、受資料夾／file ID 清冊約束的班次解析路徑，或由新入口唯讀開對應已驗證的歷史 HTML；**不把完整日期再截成 MMDD 丟回舊路由而假裝無跨年問題**。未取得唯一檔案時顯示班次資訊及找不到原因，不導向錯班。

手機預設是清單而非年度大矩陣：日期捷徑「近七日／近三十日／自訂」、固定搜尋列、可收合篩選面板、已選條件籤、來源與日期小標，以及「主素材日期／發布／到站／依入庫暫列」依據與信心提示；原文日期證據可展開。來源按鈕讀§3.8的腳本結果，缺連結顯示原因。沿用現有「點 T/C 加選、再點取消」行為，保留焦點與捲動位置。正文按需展開，側錄顯示原段與母帶線索；複製取完整指定版本文字，不能複製截斷預覽。

「加入素材包」先進暫存選取清單，不立即下載。返回搜尋須還原日期、條件、頁碼與位置。驗收涵蓋 Android Chrome、iPhone Safari、Google 登入到期、複製失敗的手動選取退路、低速網路、部分分片缺失；本次尚未實測。

## 7. 素材包：從引用清單逐步走向製作交付

### 7.1 包的定義與兩種用途

**素材包是一份有版本、可追溯的選材清單。** 一個素材可被多包引用；包不搬動素材、不重新分類原素材，也不代表已核准使用。

| 類型 | 邊界 | 例子 |
|---|---|---|
| 跨日議題包 `topic` | 可跨數日、多個中主題與大分類；有查詢條件與人工／AI選材理由 | 「核電投資」可引用 0930 班內、素材日為 10/01 的 `YNA-buGW2sCr_do`，再納入其他日期素材 |
| 稿單素材包 `rundown` | 針對一則稿或一版 rundown；帶 `rundown_id / story_id / slug`，成員與版本固定 | S4 選定切角後，交 S5 編號、S6 下載的清單 |

先做**資訊包**：`manifest.json`＋可閱讀清單／HTML＋來源與限制＋缺口。後續才做**實體媒體包**：S6 下載收據、檔案 hash、時長、素材編號、BITE／字幕／文稿連結。不要把「已列入包」顯示成「影音已下載」。

### 7.2 輸入、輸出與版本

| 項目 | 契約 |
|---|---|
| 輸入 | 固定的查詢快照、topic IDs／日期範圍或手選 material IDs、用途、需保留的互補畫面／訪問、可用權限範圍 |
| 包身份 | `package_id` 永久不變，`package_revision` 遞增；狀態 `draft / reviewed / approved / superseded`，操作留紀錄 |
| 成員 | `material_id + revision_id`、順序、選用理由、角色（背景／最新進展／畫面／訪問）、來源限制、缺資料提示 |
| 可重現性 | 保存 selection query、`snapshot_id`、建立方式與版本；固定成員不因新素材到來偷偷改變。訂閱式議題包可另建新 revision、提示新增，舊版仍可還原 |
| 限制 | `rights_status=unknown/restricted/cleared` 及原文證據；unknown 不等於可播。D23 未裁的正式使用限制繼續擋住相應下游動作 |
| 摘要 | AI 生成部分逐點附 material／revision 引用；標示是彙整稿，不把 `fields.bite` 的摘要當原文逐字 BITE |
| 下載成果 | `download_status`、file reference、hash、失敗理由；部分成功明列缺件，不交付假完整 ZIP |

**A33 與08/19評估需要重評，不能直接當新庫的前置規格。** [scripts/s2_rundown_propose.py](../../scripts/s2_rundown_propose.py) 第260～311行一次只載入一個 state，按 canonical 題名跨大分類聚合、評分、取前12題，輸出 `{MMDD}-稿單候選.json/.txt`；第57、86行等機制限制每題未標記素材12筆，重要標記全列，並回報 `items_omitted`。它已具題名整合與評分能力，**尚不是跨日候選引擎，也不是完整素材包**。

| 處置選項 | 得失 | 建議 |
|---|---|---|
| 全部併入素材包單一程式 | 入口少，但把庫存查詢、候選排序、製作選擇綁在一起 | 不採 |
| **拆分責任、共用包契約** | 保留可驗證的題名／評分機制；資料來源改由 S3 查詢快照，候選與已核准包分開 | **推薦，D-候選13** |
| 全面取代 A33／08/19方案 | 可重做跨日邏輯，但需重驗所有既有產物與消費端，過早丟棄已做能力 | 無證據前不採 |

推薦分工：S3 提供完整候選與固定版本 → 候選產生器按 topic 聚合、評分、列缺口 → 包建置器保存可重現的 `package_revision` → S4 人工決定切角與核准。A33 的評分程式可抽取重用，但要重驗跨日新鮮度、版本更新、不同班次重遇是否重複加分、單一長期議題是否霸榜；不是原分數直接搬過來就算完成。`items_omitted` 是顯示截斷，不能當完整庫存；包成員必由完整查詢結果或明確手選產生，顯示截斷另存。

08/19評估保留跨分類引用、缺口與獨立產物的構想；以單日交接／較小資料量為中心的輸入假設，改由跨日庫契約取代，txt頂部摘要提案仍受D17限制。Phase 4 先盤點 A33 JSON／txt 消費端，以相容介面並行重播；確認引用與候選品質後才裁定是否停用舊 CLI，不能現在標 A33 已完成或已被取代。記者分派仍受 D16 名單限制，不因產包自動解鎖。

### 7.3 接往 S4、S4c 與 S5+

| 消費端 | 接收與回寫邊界 |
|---|---|
| S4 稿單 | 讀議題包與候選，決定切角與成員；決策寫在稿單／包，不回寫素材原文 |

| S6 下載 | 以來源永久鍵、可用連結、限制與版次派送既有來源 adapter；下載結果新增附件，不覆蓋來源身份 |
| S7 掐 BITE | 取指定版本原文、母帶與時間碼；側錄摘要或 S2 濃縮 BITE 不冒充逐字原文 |
| S8／S9 | 消費已審閱的包、稿單與附件；產出的稿／影片另有 artifact ID，保存使用了哪些素材版本 |

自動整理先做確定性「按已選條件產出引用清單」，再評估 AI 跨題選材。AI 只讀精簡候選，按需取全文，有取樣／截斷必回報；費用預算、觸發時機與人工審閱另裁，不把高 token 工作塞回每輪掃帶。

## 8. 擴充介面與 schema 演進

| 介面 | 輸入／輸出 | 防止耦合的規則 |
|---|---|---|
| `ingest_snapshot` | 明確來源路徑、bytes hash、班次證據、adapter 版本 → receipt | 不自選最新正式 state、不改來源檔；只此處處理舊欄位差異 |
| `normalize_material` | 原始 item＋上下文 → material、revision、observation、issues | 純轉換；身份與時間政策集中，不能每個 UI／AI 各自推年月日 |
| `resolve_identity` | namespace＋來源鍵／legacy alias → material ID＋品質 | 模糊同題只回候選，不自動合併 |
| `search_materials / get_material` | §6 查詢契約 → 有覆蓋範圍的分頁結果／完整指定版 | 第一版 CLI／Apps Script，未來 HTTP 或 AI 工具仍共用契約；不暴露 SQL／任意檔案讀取 |
| `export_generation` | 一致性讀取快照 → 不可變分片、manifest | 匯出與發布分開；版本未驗證不切 active |
| `build_package` | 固定素材版本清單＋選材條件 → 包版本 | 不重新抓來源、不自行核准使用；下載為另一個可重試工作 |
| `attach_artifact` | material／package version＋附件收據 → 關聯 | 新來源、照片、音訊、字幕、S9 成品都可擴充，二進位內容不塞主表 |

新來源實作獨立 adapter：明訂永久鍵、時區、時間欄位語義、內容格式與限制來源。重用 `s2_material_schema.py` 的唯讀來源辨識概念，但目前其中 `material_uid` 只是回報欄位且固定為 null，**不是已有全域身份服務**。擴充可用 `extensions.<provider>` 保留特有欄位，公共查詢欄位仍有固定型態。

來源連結生成沿用 A16 方向，以已驗證 ID／URL 與固定模板由腳本處理，零 LLM；沒有永久鍵就回傳「連結待補」，不請模型猜網址。E9 的抓取端共用化仍屬上游待辦；本案先確保快照匯入、身份解析與發布均由可重跑的正式工具承擔，避免再由每輪 agent 手寫外電庫寫入腳本。

版本至少分四層：`schema_version`（交換格式）、`adapter_version`（來源轉換政策）、`vocabulary_revision`（分類字典快照）、`generation_id`（發布快照）。加可選欄位可相容；刪欄／改語義升主版本。讀者遇不支援主版本須明確拒絕並留前一可讀版，不用空結果掩蓋；遷移先寫新庫、驗證後切換，不就地毀掉舊庫。

AI 查詢預設唯讀、有限頁數、回傳 provenance 與未完成查詢訊號；來源正文視為資料，不作工具指令。可加語意索引，但必須能回到固定 material／revision，不能用向量相近結果作為唯一去重證據。後續需要共同編輯時，另增經授權的 package 寫入 API；不讓 AI 直接寫外電庫底層檔案。

### 8.1 D11 實例：AP／RT Live 節目表如何接入

依 [2026-08-23-AP與RT-Live節目表API可行性評估.md](2026-08-23-AP與RT-Live節目表API可行性評估.md) 設計以下契約；**D11 仍延後，本段是擴充示例，不授權開始抓取**。報告反映08/23觀測，未驗證10/02端點仍可用。

| 步驟 | AP／RT 具體映射 | 共同契約 |
|---|---|---|
| 擷取 | AP 同源登入環境的 `/v1/nrlive/events`，有 `startDateTimeUtc / isStartTimeTBA / storyNumber / channelId / isCancelled / restrictions`；RT 當時為 WebSocket＋變動中的 Next Server Action，可讀載入後 DOM 的開始／結束／狀態與詳情 newsml ID | 獨立 `live_schedule` adapter，傳來源收據、取得時間、schema版本；遵守§5.1b profile／headed／掃帶鎖，不自建未授權排程 |
| 身份 | AP 優先已驗證的原生 event ID；`storyNumber` 是否永久唯一尚待查。RT 可用已確認 newsml／USN 證據，保留版本部分 | `scheduled_event_id` 與 material ID 分開；未知永久鍵用暫定身份，**不能用開始時間作主鍵**，避免延後就變新事件 |
| 日期 | 報告示例08/23 18:00 UTC＝臺灣08/24 02:00；RT 的 `-1` 日偏移與 TBD 須保留，不能只抓 HH:mm | `scheduled_start_at_utc / scheduled_end_at_utc / schedule_precision / observed_at_utc`；尚未成為可用影音時 `material_date=null`，不拿節目表時間冒充已播素材日 |
| 更新 | 同事件延後、取消、恢復、限制修訂皆新增 event revision | `status=scheduled/live/ended/cancelled/unknown`；查詢預設把節目表與可用素材分區，取消不刪歷史 |
| 接包／製作 | 議題包可引用「預期直播」作補素材計畫；實際 VOD／錄製檔到達再走素材 adapter | 以 `related_event_id` 連結新 material／revision；節目表有連結不等於有影音可下載，未取得素材與限制證據不送 S6 |

例如上述02:00活動延後至03:00，保持 event ID、只增版本；若取消，包內顯示取消與缺口。真正錄製檔在03:20入庫時，有自己的錄製起點／素材日與 first_seen，並引用原事件。這示範「新來源加入契約」不必修改 S2 state 主模型、txt 或現有素材身份。正式啟用時點、來源範圍另列 D-候選15。
