## 3. ENEX／ABC 實測記錄（供日後對照）

**ENEX**
- ES `_search` 不加 `_source` 白名單，`_source` 全欄位：`status／published／thumb／editorsChoice／title／subject／description／location／region／country／language／partner／start／category／lastModified／publishedDate／pictureDate／creationDate／newslinkId／tags／videoLowRes／videoLowResCdn／editStatus／editStatusSort／contributor／filename／ntscTranscodingStatus／sortDate`（＋5 個 `*Suggest`）。**沒有任何高解析度網址欄位**，全解析度只能從 `/download/{id}` 拿。
- `/download/929921` → `302` → `https://enexfeed.s3.eu-west-1.amazonaws.com/{filename}?X-Amz-Algorithm=AWS4-HMAC-SHA256&…&X-Amz-Expires=600&X-Amz-Signature=…&check_logged_in=1`。帶 `check_logged_in=1` 打：`403 SignatureDoesNotMatch`；拿掉：`206 Partial Content`、`bytes 0-0/522565697`、`video/mp4`。`HEAD` 一律 403（簽章綁 GET）。
- 頁內 `fetch('/download/…')` → `TypeError: Failed to fetch`（S3 無 CORS）。

  `fileGroupId`（＝`content.bitcentral.fileGroupId`）與 `videoId`（＝`alternateIds.bitcentralFusionId`）**都已經在 `POST /api/v3/stories` 的清單回應裡**，可用的下載格式列在 `content.bitcentral.newDownloadableFormats`（含 `H264 HD NTSC`）——**完全不必開任何詳情頁／Preview modal 就能組出下載請求**。UI 觸發後，`D:\Downloads` 在數十秒內出現 `BHDN_SE-008SU_FL_ AMAZON PLANE INCI_{guid}.mp4`（22,158KB／23,228,332 bytes，與 11 秒 SOT 合理）；檔名與 `config.files` 裡的 `sig://` 路徑最後一段完全一致（僅去掉 `sig://bucket/…/` 前綴）。
- **API 純重放（`SE-007SU`，全程一個 `browser_evaluate`，未點任何 Download 按鈕）**：照抄上表三個呼叫，一次成功——`POST /api/v2/download` 回 200＋`downloadIds`；`getDownloadStatus` 先回 `"created"`、幾秒後再查回 `"ready"`（與 UI 那次拿到的狀態相同）；`GET /config/{id}` 回 200＋完整 `server`／`apiKey`／`trustCertificate`／`sig://` 路徑，形狀與 UI 那次一模一樣。**但輪詢 `D:\Downloads`（每 20 秒一次，共 280 秒／4 分 40 秒）全程沒有任何檔案或暫存檔（`#chkpt_file#…`／`#work_file#…`）出現**，`getDownloadStatus` 停在 `"ready"` 不再前進。
- **關鍵差異**：`browser_network_requests` 顯示 UI 那次在點開下載對話框時多打了一支純 API 重放完全沒出現的請求——`GET https://messaging-config-service.services.cloud.signiant.com/channel?pubname={…}&subname={…}&apiversion=2.9.3`。`transferapi.min.js`（Signiant 的瀏覽器端傳輸客戶端）雖然頁面一載入就全域載入（不是點 Download 才載），但**實際啟動傳輸要靠網站自己的前端邏輯呼叫這支 client library 去訂閱這條 pub/sub channel**，這一步只在 UI 互動裡發生，純 `fetch()` 重放三支 REST 端點拿不到這個訂閱，Signiant 端沒有任何 client 在監聽這筆 `downloadId`，檔案自然不會搬。
- **結論 (b)：API 回成功、有完整 Signiant 憑證，但檔案不會落地。** `/api/v2/download` 一路到 `/config/{id}` 都是「排隊」而不是「搬檔」，真正搬檔的是網站前端呼叫 Signiant client library 建立的 pub/sub 訂閱，這段不是公開文件化的 REST 呼叫，用瀏覽器 JS 重放做不到（沒有逆向 `transferapi.min.js` 的內部 API 就無法補上這一步，且逆向该客戶端已超出「省一段 UI」的投資報酬）。**維持步驟 2 現行 UI 點按鈕做法，不要再攻。**
