## 一、問題定義

V2 省 token 的代價是「慢」，慢的來源拆成三段，各有各的藥：

| 瓶頸 | 慢的本質 | 對策 | 狀態 |
|---|---|---|---|
| 狀態檔操作 | 工具呼叫次數（每次一個模型往返） | **WP0** batch 熱修 | 已實作，待 0802 定版後上線 |
| 整併改寫 txt | agent 輸出 token（逐字重吐幾千字） | **WP1** 腳本渲染 | 本計劃 |
| 逐則開詳情頁 | 目錄頁往返＋modal 不穩重試 | **WP2** AP 整批開分頁 | 本計劃 |

## 二、量化目標與量測方法

- **量測基準**：WP0 上線後先跑一輪真實掃帶，從狀態檔 `updated_at`／檢查點時間戳回推「批次擷取段」與「整併段」各自耗時，並數該輪工具呼叫次數。**這是 WP1/WP2 的 go/no-go 依據**——量出來整併段只佔一輪的一成，WP1 就降優先。
- **目標**：整併段耗時降 50% 以上（WP1）；AP 批次擷取每則平均呼叫次數由 4–6 次降到 2 次左右、modal 相關重試趨近 0（WP2）。

## 三、WP1：晚班交接 txt 改腳本渲染

**核心**：狀態 JSON 在 WP0 後已含全部產出材料（`raw_entry` 全文、`category` 物件、`script_status`）。加 `render` 子命令（掛 `s2_validate.py` 或獨立 `s2_render.py`），從狀態檔生成整份 txt：檔頭三行（`stats` 邏輯現成）→ 按 大分類→中主題 排序 → 素材行原樣輸出。整併流程變為：

```
to-compile 拿增量 → set-category --pairs 批次設分類 → render（agent 輸出 ≈ 0）→ mark-compiled
```

> 🟢 **2026-08-03 使用者裁定，三個前提全部簡化**——WP1 從「中等工程量＋高風險」降為「低工程量、低風險」。go/no-go＝**GO**（量測見文末附錄）。

**前提一：人工編輯反向同步 → ❌ 不需要（風險消除）**
使用者確認 **txt 完全由 AI 編寫、人工不會手改**。所以狀態檔是唯一真相源，render 就是它的**單向投影**，不需要 diff3 回寫、不需要「手改存活測試」。原本 WP1 最大的風險與工作量整段砍掉。

**前提二：側錄必須入狀態檔、統一 render（不是 passthrough）**
使用者關鍵洞察（2026-08-03）：render 是狀態檔的單向投影，**隔夜續掃重生成 txt 時，狀態檔裡沒有的東西會被刪掉**。側錄若只用 append／passthrough，晚班已寫進 txt 的側錄會在隔夜 render 時消失。所以：
1. 側錄以 `source: "SIDE_CNN"／"SIDE_NHK"`（封閉字彙已有）**入狀態檔**——22:00 前使用者給的側錄 TXT，最後整理輪由 agent parse 成狀態檔項目（一個 side parser）。
2. `raw_entry` 存側錄的兩行式原文（TC 行＋內容行，含冒號 TC）。
3. **render 按 `source` 分流排版**：通訊社走三段式、側錄走兩行式（不用 `▎` 分段、不壓縮、不設字數上限——沿用 `14-S2b` 現行格式）。
4. 側錄**不計入檔頭則數**（既有規則，`stats` 已排除）。

**前提三：時段標記由 render 按輪次自動補（2026-08-03 使用者採此案）**
不依賴 `raw_entry` 存不存標記（現有 85 則早期資料沒帶標記）。render 時腳本按每則的 `first_seen_checkpoint` 自動推算並補上 `△`／`▲`／`●`：23:00 前＝`△`、23:00–07:00＝`▲`、07:00–09:00＝`●`（判準沿用 `13` 隔夜續掃節）。**好處**：標記永遠正確、狀態檔存不存都不管、輪次改名也不影響。🔴 重大標記則從 `raw_entry`／狀態欄位取（永久保留規則，render 照帶）。

**render 生成順序**（單一真相源 → txt）：
1. 檔頭：`stats` 邏輯現成（基本三行＋標記圖例＋沿用的 🔴 重大提醒行）。
2. 大分類：照樣板 16 格順序，空格也保留。
3. 每格內按 中主題→素材排序，逐則輸出：`{render補的時段標記} {🔴若有} {raw_entry}`。
4. 側錄段：按 source 分流、兩行式，插到既有位置。

**驗收條件**
- [ ] 用最近一天真實狀態檔做迴歸：render 產物與 agent 手寫的現行 txt diff，**素材行內容零差異**（僅允許排序／空行差異）。
- [ ] **時段標記正確性**：那 85 則無標記的舊資料，render 後標記與 `first_seen_checkpoint` 一致（△/▲/● 全對）。
- [ ] **側錄往返**：側錄 TXT → parse 入狀態檔 → render → 與原側錄 byte 級一致（不壓縮、TC 冒號格式保留）；**隔夜再 render 一次側錄不消失**（前提二的核心驗證）。
- [ ] 🔴 標過的則 render 後仍帶 🔴（永久保留）。
- [ ] `s2_validate.py check` 對 render 產物 0 命中。

**整併流程變為**：`to-compile` 拿增量 → `set-category --pairs` 批次設分類 → **`render`（agent 輸出 ≈ 0）** → `mark-compiled`。

**流程**：與 WP0 相同——scratchpad 副本實作 → 真實檔迴歸（上列驗收）→ 避開掃帶時段 commit → 同步改 `13b` §2 整併流程＋ `14-S2b` 側錄入庫。

## 附錄：WP1 go/no-go 量測（2026-08-03）

**GO。** 整併段是一輪裡最大的單一輸出成本，render 切在正確的地方。

- 定版 txt：**858 行 / 67,530 字元**（中文密集，字元數約等於輸出 token 數）。
- 整併是**全量重寫**：新素材要按大分類插到中間、要歸位、檔頭每輪重算，Edit 局部改做不到；diff3 三方比對機制的存在本身佐證「重寫整份→比對 snapshot」。
- 一晚整併約 **9 次**（16/18/20/22/23＋隔夜 01/05/07/09），0802 的 compiled 批次分布印證每輪都有整併。
- **一晚整併段輸出約 30–50 萬字元**（早輪小後輪大，平均每次 3–5 萬）。這是純輸出 token、模型逐字生成最慢的部分；render 下 agent 輸出趨近 0。
- 呼叫次數維度看不出這個成本（一次全量 Write 只算 1 次呼叫，但吐 5–6 萬 token）——這正是 00:00 實驗輪「52 次呼叫」報告沒暴露它的原因。

## 四、WP2：AP 先 diff 後整批開分頁

**核心**：批次擷取不再「開一則→讀→回目錄頁→再開下一則」，改成目錄頁 diff 出全部新素材後，一次開好分頁、逐分頁收錄。消掉 AP 三個已知坑的發生場景（modal Close 不乾淨、點到舊 modal、清單即時插隊推位）。

**步驟 1——驗證加強版（先測，收益最大）**：AP 目錄頁 DOM 是否露出詳情頁直接 href、或網址可否由素材編號拼出。可行 → diff 出新 ID 後**直接用網址開分頁，modal 全跳過**，目錄頁互動趨近零。
**步驟 2——退路（基本版）**：href 拿不到 → 目錄頁連續做完「modal → Open in a new tab」× N，再逐分頁 `get_page_text`。modal 互動仍在但集中連續、不與讀取交錯，插隊風險只承受一次。
**分波上限**：每波 5–8 個分頁，讀完關掉再開下一波（記憶體／站方 session 保護）。

**驗收條件**
- [ ] 真實一輪 AP 段：每則平均呼叫次數、modal 重試次數，對照 0802 基準。
- [ ] 加強版需另驗：由 href／編號開出的詳情頁，內容與走 modal 路徑開出的**同一則完全一致**（防拼錯網址開到別則）。
- [ ] 收錄的每則 `get_page_text` 前先核對頁面素材編號與預期一致（沿用 RT「核對 Edit No」精神）。

**範圍界定**：RT 不適用（SPA 站內 ‹ › 導覽，本來就不回清單）；CNN inline modal 順帶看一眼有無同構空間，不強求。

**流程**：這是操作規則變更、不改腳本——實測驗證通過後直接改 `13b` 批次擷取流程 AP 段，附正反例。

## 五、時序與依賴

```
WP0 上線（0802 定版後 commit）
   └→ 跑一輪真實掃帶，量基準（整併段耗時／AP 段呼叫數）
        ├→ WP1 提案 → 審 → 實作 →上線      （依賴 WP0 的 --pairs 與狀態完整性）

```

- WP1 與 WP2 互不依賴，可並行；都不動既有路徑，各自可獨立回滾（WP1 回退＝繼續手寫 txt；WP2 回退＝改回逐則往返）。
- 每步 commit 都避開掃帶進行時段（同 WP0 的 23:00 原則）。
