## 二、P0：先補量測分桶

**現狀**：`scripts/s2_token_metrics.py` 的 `BATCH_PREP_SUBCOMMANDS` 只列 `dump/build/unwrap/inspect/search/snapshot/compare/dedup-check`。`from-raw/timeline/fill-src-text/collate-category/concat` 雖已註冊，卻被 `classify_bash_tool` 歸回泛用 `s2_batch_prep.py` 桶。

**問題**：無法直接從報表判斷 A24／T12 採用是否有效；看見 inspect 次數高就說浪費，可能把28k工具回傳預算下的正常拆批誤判成重讀。0914-0100／0430 遙測曾見 inspect 35／41、未分桶 batch_prep 6／1，但不據此判定這些呼叫都可取消。

**建議**：
1. 補齊已存在子指令，加入分類對照測試，未知值保留顯式可辨識桶。
2. 若需衡量重讀，區分同 ID／同欄位重取、正常分頁、pending 新版、修補原因；先確認現有 transcript 能提供哪些欄位，避免另加高成本遙測。
3. 報表標明工具呼叫、shell 子命令、模型請求、HTTP 請求的不同口徑。

**預估效益**：直接掃帶 Token 節省約為0；主要節省事後翻 transcript 的研究成本，並避免把優化投在錯誤瓶頸。

**風險／前提**：不得臆測回填歷史未知桶；一個 shell 工具可含多個子命令，命令數下降不保證模型請求等量下降。不得以全輪平均 cache-read ÷ 工具數乘上減少呼叫數宣稱省費。

## 三、P0：正常批次路徑權威化

**現狀**：`13c` 約168–181行仍稱 dump/build 選用、手寫 batch 較省；`13c2` 約134–136行則要求三站骨架路徑。`13c2` 約71–75行允許 `add-batch` 一次帶分類／TC，約174–185行又要求三站各做一次 `set-category`。

**問題**：agent 遵循不同段落會重建資料、重做分類，甚至把正常工具能力當作尚未實作。

**建議**：以已上線路徑為權威：三站 `from-raw --state` → 骨架 → agent 補 `{id:{entry,category,tc}}`／`_new_topics` → `build --skeleton` → `add-batch`。另外 `set-category/set-tc` 限真正修補。把舊「選用」文字和無條件重跑分類段落改成一致描述，保留正常批次檢查。

**預估效益**：若舊輪三站各多一次分類及TC，最多約少6個命令／輪；若已隨批次正確入庫，增量為0。以實際取消的命令及模型往返計，不混算。

**風險／前提**：不能刪必要修正、對帳或 review。`from-raw --state` 不可排除 pending／prelim／early。此三站規則不套用未授權的 D19 platform 骨架擴充。

## 四、P1：草稿前置共用 lint

**現狀**：`s2_state.py` 在建立 item 後才執行 `fmt_issues`／`pretag.lint` 並回報；同批可設分類／TC。`s2_batch_prep.py build` 尚未共用這套 lint。R31 記錄0908-1100的89則中76筆曾經三輪事後修正，是單輪案例，不是普遍失敗率。

**問題**：可機械辨識的格式瑕疵太晚出現，導致事後再讀、再組更新 batch。

**建議**：在既有 build／批次驗稿出口共用同一套 lint，回傳「ID＋原因」，讓 agent 在入庫前一次處理。保留入庫端保險檢查；不複製出另一份漂移的規則，不逐筆加工具呼叫。

**預估效益**：目標是減少純格式事後 `fix/update-entry` 批次，非承諾消除全部編輯修稿。以「減少的修補用量－前置檢查新增用量」驗收。

**風險／前提**：只警告，不自動改稿、不硬拒收、不改編輯判斷。若新增一次檢查卻未減少後續修補，可能更貴；任何硬阻擋或靜默改文稿需另行裁決。必須保持原文、歸因、限制與 BITE 完整。

## 五、P1：回傳契約與舊指路矛盾

**現狀**：
- `13c` 約397行稱 NS 先回小欄位、不含 script，但約444–463行範本仍直接回完整 script。
- 約214–215行承認瘦身輸出仍可被工具卸載，約226行卻把卸載檔一律當未瘦身 raw。
- 約163行稱清單文稿全部 API，但 RT 約245–282行仍需 DOM 取清單 Edit No／href，詳情才走 API。
- 約166行保留 investigation 配方連結，約444行又說不要翻舊 logs；前者是歷史指路，不是每輪必讀命令，不能計成固定重讀成本。

**問題**：agent 不知道手上的是 raw、slim 或 tool-wrapper，重複卸殼／inspect／取全文；互斥文件也使省量目標與實際範本不一致。

**建議**：
1. 明定三種回傳形態與欄位契約，優先重用 `unwrap/inspect/search`，不重建同功能工具。
2. 明寫 RT 清單 DOM、詳情 API 等站別差異；把舊指路標為歷史用途。
3. 可評估同輪把已取得的原全文暫存在瀏覽器內，再選擇性回傳當下所需欄位；這是待驗方案，不是已證明「不必重抓」的能力。
4. 尚未證明安全前，先只修文字矛盾，不改擷取與完整收稿行為。

**預估效益**：若某批原本回 N 份全文、當下只需 K 份且篇幅近似，該批全文回傳量可少約 `(N-K)/N`。40→10只是該批75%的算例，**不是整輪 Token 或費用少75%**；若後續仍需全部全文，須扣掉延後讀回的成本。

**風險／前提**：不改全收、分類、review要求，不變成固定 collector 或 LLM只讀 normalized delta。導覽／頁面重載會失去暫存，須有可恢復路徑。pending 必須查最新稿，不能以舊快取冒充新查。RT Edit No 跨日重用、NS Story ID 週期重用；識別需來源＋原生 GUID/itemid＋日期／版本。同文稿或同事件不代表同畫面，不能刪不同鏡位素材。NS token 必須留在瀏覽器 JS，不回傳至 agent。

## 六、P1：R33 窄 rename-field 出口

**現狀**：R33 記錄 `raw_entry → entry` 欄位修正受 guard 阻擋，現有 batch 工具未提供標準 rename-field／set-field。另三次 DENY 是同事故重複嘗試，不是三項新缺口。

**問題**：單純 schema 修正可能被迫重寫整批，或反覆嘗試不被允許的路徑。

**建議**：提供僅限工作 batch schema 的 rename-field，支援 `{entries,new_topics}` 外殼。先預覽差異；來源鍵不存在、目的鍵衝突或資料形態不符時明確報錯；輸出新檔、不原地覆寫。禁止操作生產 state，不提供任意 JSON 路徑改值或執行功能。

**預估效益**：事故輪可省整批重寫與 DENY 繞路；目前只有單案證據，不保證每輪固定收益。

**風險／前提**：工具是既有授權資料轉換的窄出口，不是繞過 guard。測試包含多筆、外殼保存、衝突、缺鍵、原檔不變、生產 state 拒絕；若需調整 guard 政策，另交使用者裁決，不能自行更動權限。

## 七、P2：T4 按需載規則，維持延後

**現狀**：prompt 已縮為2,099字元，主要必讀量在八份規則152,288字元；ENEX＋ABC正文29,019字元。T4 規則分片（八片＋manifest）目前延後，現行 prompt 明定八份必讀。

**問題**：非全量掃兩站的輪次仍讀兩站詳細規則，但其中也包含當輪必要的保活、補掃與恢復責任，不能整份直接不讀。

**建議**：若使用者批准重啟 T4，先抽出每輪必要存根（保活／整站失守補掃／pending／恢復），再依輪次與狀態載全文；manifest、EOF檢查及 launcher 必須一致。

**預估效益**：非全量兩站輪的毛上限29,019字元、約19%，須扣存根、manifest及臨時補讀；不是固定19% token／美元。

**風險／前提**：未批准前不能略讀現行八份。ABC 即使跳過全量掃描，收工仍可能必須保活；獨立保活與掃帶共用鎖，撞鎖會放棄，不能假設一定覆蓋長輪。不得順便改排程或重啟 D5 看門狗自動代打／D6 S2b排程化。

## 八、D19、模型與明文不做項

### 換模型／本機模型

- E8 跨模型跑通不等於品質與成本等價；如另獲授權試驗，固定同份 raw，比漏收、Restrictions、歸因、BITE、分類與淨成本。

- whisper.cpp 對已有網站文稿的掃帶沒有直接替代收益；ASR 屬另一條素材處理線，不混算。

### 不重提為新方案

依 MASTER：固定 collector、LLM只讀 normalized delta、Message Batches、Haiku分流、Prompt caching專項目前不做或降觀察；D4 diff=0跳分類／review、D10三站子代理、D13每站compact、已結案 gap-check與舊原文缺漏回補不重開。既有保活、登入續期、AP照片批次 check/tick 等能力也不算本次新增優化；S2評估不觸發計量下載。
