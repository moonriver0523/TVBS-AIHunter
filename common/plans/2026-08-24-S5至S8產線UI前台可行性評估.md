# S5–S8 產線 UI 前台可行性評估（編號／下載／掐BITE／寫稿）

- 日期：2026-08-24
- 性質：**評估報告，不是規則、不是授權實作**——結論為「可行，但只有掐BITE那一段值得先做」，實作與否、階段順序由使用者裁定
- 觸發：使用者提問「AIHUNTER 編號素材＋下載＋掐BITE＋寫稿流程，能否建構一個 UI 化的前台（HTML 或 EXE）。尤其掐BITE：理論上只要有影片素材＋跑 ASR，就能在前台列出所有候選 BITE 段落，讓使用者點選、一鍵生成 BITE」
- 範圍：S5（[`05`](../05-material-numbering.md)）／S6（[`reuters/05`](../../reuters/05-batch-download.md)）／S7（[`07`](../07-bite-assistant.md)、[`cnn/02`](../../cnn/02-clip-bite.md)、[`reuters/03`](../../reuters/03-auto-clip-so.md)）／S8（[`06`](../06-auto-script-sot.md)）四站的介面化可行性、架構選型、與既有規則的相容性
- 不包含：UI 視覺設計、資料庫 schema、實際開發、S2 掃帶與晚班交接網頁版（那是另一條線，見 §8）

## 一、先講結論

**三句話：**

1. **「HTML 還是 EXE」是假選擇。** 正確答案是**本機 Python 後端（FastAPI）＋瀏覽器 HTML 前端**，跑在 `localhost`。純靜態 HTML 摸不到檔案系統／ffmpeg／whisper，做不了這件事；EXE 是**打包方式**不是架構，要包等功能穩了再用 PyInstaller 包一層即可。
2. **掐BITE（S7）是唯一「介面化能真正提升正確性」的一站，值得先做。** 其餘三站：S5 是純腳本（有沒有 UI 都能自動化）、S8 已有 `validate_sot.py`（UI 只是把它變即時）、**S6 下載是四站裡最難、且最不適合搬進前台的一站**（見 §5）。
3. **使用者對掐BITE的直覺是對的，但「一鍵生成」中間有一段不是機械的**：候選段落的**列舉**可以全機械化，**選句**可以人工點選（這正是 UI 的價值），但 SB 五行的**第 3 行中文翻譯**不是機械產物——要嘛呼叫 LLM、要嘛人工填。這決定了這個前台要不要帶 API Key（見 §4.5）。

## 二、為什麼是「本機後端＋瀏覽器前端」，不是純 HTML、也不是 EXE 優先

| 需求 | 純靜態 HTML | 本機後端＋HTML（建議） | Electron／PyInstaller EXE |
|---|---|---|---|
| 讀 `G:\...\SOT自動寫稿測試\{SLUG}\` 的影片與文稿 | ❌ 做不到 | ✅ 後端直接讀 | ✅ |
| 跑 ASR（whisper）／ffmpeg 抽格／剪片 | ❌ | ✅ 沿用本機既有環境（`magick`／`ffmpeg` 已裝） | ✅ |
| 影片**精準 seek 到某個 TC**（本案關鍵，見 §4.1） | ⚠️ 僅限使用者手動拖進來的檔 | ✅ 後端出 HTTP Range，`<video>` 可秒級跳轉 | ✅ |
| 沿用 `validate_sot.py`／未來的 SB formatter | ❌ 要用 JS 重寫一份規則（**明文禁止**，見 §7） | ✅ 直接 import | ✅ |
| 開發成本 | 低但做不到事 | **中** | 中大（多一層打包與更新問題） |

**建議選型：FastAPI（或 Flask）＋單頁 HTML／原生 JS，前端不打包、不引入前端框架。** 理由：

- 與 repo 現況同構——`scripts/` 全是 Python，`s2_render_html.py` 已經有「Python 產 HTML 當檢視層」的實績。
- 素材是**授權外電、單檔數十到數百 MB**，本來就只能留在本機；這個前台**本質上就是 local-first**，不存在「要不要上雲」的問題。
- EXE 不是先決條件：先用 `python -m uvicorn ...` 或一個 `.ps1` 啟動器（比照 `s2_watchdog_ctl.ps1`），**功能定版後**再評估 PyInstaller 單檔封裝給非工程同事用。

| 站 | 機械可自動化的部分 | 必須由人／LLM 判斷的部分 | UI 化的實際收益 |
|---|---|---|---|
| **S5 編號** | 代碼辨識（`AP`／`RT`／`APcctv`／`{2字母}-{數字}{星期}`／URL）、遞增編號、`同#XX` 判重、規則 7 的「移除標記後逐字相同」驗證 | X 的 `.../status/{id}` 要**實際打開看有幾支影片／幾張圖**（[`05`](../05-material-numbering.md) 明訂不能只看網址） | **中**——腳本化收益大於介面化；UI 只是提供貼上／預覽／確認的框 |

## 四、掐BITE 工作台（S7）——本案的核心

### 4.1 設計驅動點：TC 漂移問題，UI 正好是解法

[`07-bite-assistant.md`](../07-bite-assistant.md) 今天（2026-08-24）才新增的警示：`video_analyze` 對長片分段轉錄會**累積漂移**，同一支片跑兩次時間軸不同（`CNN台獸` 案例差 24 秒，後段差近 60 秒）。規則給的解法是「用 `ffmpeg -ss` 抽單張畫面核對燒錄字幕」或「跑第二次交叉核對」。

**在前台裡，這個核對從『再跑一次工具』變成『點一下、看一眼』**：候選清單每一列點下去，`<video>` 就 seek 到該 TC 開始播 10 秒，人耳聽到的、人眼看到的燒錄字幕就是 ground truth。**這是這個 UI 最實質的價值——不是省時間，是把一條目前靠自律執行的核對步驟，變成流程上跳不過去的一格。**

同理，另外兩條規則也因此更容易做到：

- **`P-046`（路人／UGC 邊拍邊說也算 BITE，盤點時要實際聽一次音軌）**——UI 裡本來就在播，聽過就是聽過。
- **`P-022`（記者 STAND 優先，但逐字稿分不出出鏡與旁白，必須抽格核對）**——播放器直接看得到記者在不在鏡頭裡，不必再單抽 `ffmpeg -ss`。

### 4.2 資料流（建議）

```
{SLUG} 資料夾（G:\...\SOT自動寫稿測試\{SLUG}\）
   ├─ {SLUG} #01 RT.mp4          ─┐
   ├─ {SLUG} #01 RT (外電文稿).txt ─┤ 後端配對成一個「素材」
   └─ 060710....mp4（側錄，6碼）  ─┘（無 #編號，走 TC offset）
                │
                ▼
   ① TC 來源解析（照 07 的優先序，找到就停）
      官方文稿內建 TC → 既有雙語逐字稿 → RT transcript → YouTube 字幕 → 最後才 ASR
                │
                ▼
   ② 候選段落列舉（機械，見 4.3）
                │
                ▼
   ③ 前台清單 ←→ <video> 播放器（點列跳 TC，人工核對）
                │
                ▼
   ④ 勾選 → 中文翻譯（LLM 或手填）→ 呼叫共用 SB formatter → 五行輸出
```

**輸入探索**沿用既有慣例，不新訂：`{SLUG} #XX {來源}` 與 `{SLUG} #XX {來源} (外電文稿).txt` 的配對規則在 [`reuters/05`](../../reuters/05-batch-download.md)；6 碼側錄的偏移換算一律照 [`02-tc-offset-filename.md`](../02-tc-offset-filename.md)，**前台不另訂一套**。

### 4.3 「列出所有候選 BITE 段落」怎麼機械化

使用者的假設成立，但要講清楚候選是怎麼來的。三種來源，優先序不同：

| 來源 | 怎麼產生候選 | 可信度 |
|---|---|---|
| **A. 官方文稿有標記**（CNN `SOT`／`SUPERS`、AP `SOUNDBITE`、RT `SAYING`） | 直接把每個引言段當一則候選，再用關鍵字對到 ASR 分段拿 TC | 最高（文字是官方的，ASR 只提供時間） |
| **B. 官方文稿無標記**（UGC、社群、側錄） | 純靠 ASR 分段聚合：連續語音、靜音切點分段，過濾出 **10–25 秒**、有實質內容的段落 | 中——`P-046` 說的就是這一類，要靠人聽 |
| **C. 記者 STAND** | ASR 分不出來，只能靠人在播放器裡看 | 只能人工，UI 提供的是「看得到」 |

機械過濾條件（建議可調參，不寫死在規則裡）：秒數落在 10–25 秒（側錄採 `07` 的「2 句話或 10–20 秒、上限 25 秒」）、SOT 素材另依 `P-015` 標示 `<2 秒 FAIL／2–5 秒 WARN`、排除純交接語（「以上是某某為您報導」這類可用字串規則初篩，但**排除結果要顯示、可還原**，不能靜默丟掉）。

⚠️ **候選清單是輔助，不是裁決**：排序（新聞價值、衝突性）本質上是編輯判斷，前台最多做到「按秒數／有無專有名詞／有無數字」排序當提示，**不宣稱它排出來的第一名就是該掐的那一句**。

### 4.4 ASR 引擎要先定案

> ⚠️ **本節已被 §十 的實測結果取代**：引擎定為**本機已裝的 whisper.cpp（`whisper-cli` + large-v3-turbo + silero VAD）**，不是 faster-whisper（本機沒裝也不需要裝）。以下保留當時的推論脈絡。

前台若走本機 ASR，合理選型是 **faster-whisper**（本機、免 token、可指定語言與 `word_timestamps`），而不是呼叫 `video_analyze`。但有一條**必須誠實寫下來**：

> **不能宣稱本機 whisper 沒有長片漂移問題——這件事本評估沒有實測資料。** 因此無論選哪個引擎，**§4.1 的播放器人工核對都是強制步驟，不是可選加值**。引擎只影響「候選準不準」，不影響「輸出前要不要看一眼」。

若決定要做，Phase 1 的第一件事應該是拿 `CNN台獸` 那支已知有漂移的素材當基準，跑一次本機引擎比對真實 TC，**再決定引擎**。

### 4.5 「一鍵生成」中間那個不機械的環節

SB 五行（規格唯一來源在 [`00-寫稿通則.md`](../00-寫稿通則.md)）：

| 行 | 內容 | 能否機械產生 |
|---|---|---|
| 1 | `SB` | ✅ |
| 2 | `{職稱} {姓名}` | ⚠️ 半機械——官方文稿常有，但要套 `P-034`（姓名英文原名／職稱中文，臺灣已有固定譯名者例外） |
| 3 | 中文翻譯口白 | ❌ **要 LLM 或人工**；且 `P-037` 規定代名詞指涉不明要用半形括號補主詞 |
| 4 | TC 欄位 | ✅ 三種寫法（`#XX`／`{來源} {M/D}`／純 6 碼）依素材類型自動判定 |
| 5 | 原文逐字 | ✅ **但一律取自官方文稿，不得用 ASR 文字**（`07`／`cnn/02` 明訂，ASR 只定位時間） |

所以「一鍵」實際上是：**勾選 → 系統填好 1、4、5 行，2 行給預填草稿，3 行呼叫 LLM 產草稿或留白手填 → 人按確認 → 輸出**。決策點：

- **要 LLM**：前台需要一把 Anthropic API Key。⚠️ 這裡要記取 [[project_aicg_cloudrun_deploy]] 的教訓——那次是把 Key 烙進公開網頁。**本前台是 localhost、Key 只存本機環境變數，不進 repo、不進 HTML**。
- **不要 LLM**：翻譯欄位空白給人填，前台退化成「候選列舉＋TC 核對＋格式排版器」——**功能仍然成立，且成本為零**。建議 Phase 1 先做這個版本。

### 4.6 文字 SB vs 真的剪出片段——兩件事

使用者說的「一鍵生成 BITE」有歧義，兩種都涵蓋但屬不同階段：

- **文字 SB（S7 本體，[`07`](../07-bite-assistant.md)）**：只輸出五行文字，**明訂不剪片、不上傳、不另存 txt**。← Phase 1 範圍。
- **剪出片段（掐SO，[`reuters/03`](../../reuters/03-auto-clip-so.md)）**：`ffmpeg -ss/-to -c:v libx264 -c:a aac`，輸出檔名由使用者當次指定、複製到 `Claude共用` 根目錄。← 技術上就是在勾選列旁邊多一顆「剪出這段」按鈕，**難度低、收益高（前台已經知道起訖 TC 與來源檔）**，但要注意它會**改變 S7「不剪片」的產物定義**，屬於規則層變動，需使用者明示。

## 五、S6 下載為什麼建議 v1 不做

三站的下載都有「介面搬不動」的硬阻擋，這不是工程量問題：

- **RT**：`/api/download/video` 對合成點擊做內容協商，`a.click()` 拿回 8KB 帳號 JSON——**只能真人手勢點按鈕**（2026-08-03 實測，22 筆全中招）。前台按鈕點下去，後端仍得驅動一個真實 Playwright 視窗去真點。
- **NS**：走 Signiant 傳輸，**沒有 HTTP 直鏈**，只能 UI 點 Download。
- **AP**：唯一可 API 直取的（`check` → `tick` → `ClientMediaUrl`），但仍需 cookie 登入態。
- 三站都需要維持登入 session（[[project_s2_profile_v4_chrome_channel]]：headed 還必須 `channel:'chrome'`）。

**可行但不划算的做法**：後端起 Playwright、前台只當「佇列與進度看板」（顯示每筆狀態、下載後自動查檔案大小、標紅 <1MB 假檔）。這其實有價值——**「下載驗證」那條硬規則機械化後，假檔再也漏不掉**——但工程量與踩雷面積遠大於 S7，且現行 agent 流程已能跑通。**建議列為 Phase 3，且以「進度看板＋檔案大小驗證」為限，不追求前台取代瀏覽器。**

## 六、S5 與 S8 的介面化（小投入、可搭車）

- **S5 編號**：真正該做的是**腳本化**（`s5_number.py`：貼上清單 → 輸出編號清單 ＋ 自動跑規則 7 的逐字比對）。介面只是包一層 textarea。**唯一 UI 有價值之處**：X 連結要人工開來看，前台可以把每個 `.../status/{id}` 列成待確認清單，人看完選「1影片／2影片／3圖／無媒體」，避免漏編（「俄炸朝彈2200」5 則全漏的那類事故）。
- **S8 寫稿**：`validate_sot.py` 已經在做全部機械檢查。UI 版＝一個 textarea 貼草稿，右側即時顯示主標／次標字寬（半形折半那把尺，肉眼估幾乎一定估錯）、SB 秒數、總長度加總。**寫稿本身不搬進前台**——那是 LLM／人的工作，且 [`10-寫稿風格指南`](../10-寫稿風格指南.md) 第 12 節的風格檢核表無法機械化（`06` 明訂兩道關卡都要過才算完成稿）。

## 七、必須遵守的既有護欄（照抄，不重新發明）

1. **規則不得分叉進 JS**。比照 [`s2_render_html.py`](../../scripts/s2_render_html.py) 的立場——「**這是第二個投影，不是第二份真相**」。SB 五行排版、TC 欄位三種寫法、字寬計算，**一律由 Python 端唯一一份 formatter 產生**，前端只負責顯示與複製。規格來源永遠是 [`00-寫稿通則.md`](../00-寫稿通則.md)，前台不得自行定義格式。
2. **建議新增一支共用 formatter**（例如 `scripts/sb_format.py`），讓 agent 流程與前台呼叫同一支——否則兩邊各自演化，就是 `13b` 立案時點名的維護地獄。
3. **官方文稿優先於 ASR** 是硬規則，前台的資料模型要能同時保存「ASR 文字（定位用）」與「官方文稿文字（輸出用）」兩欄，**輸出永遠取後者**。
4. **不覆寫來源檔**。ASR 結果落地成旁路 `{檔名} ASR.txt`（`06` 省 token 第 3 點已有此慣例），不動原始素材與外電文稿。

- **TC 來源優先序**（`07` 省 Token 核心）：官方文稿自帶 TC → 字幕檔 → ASR，**字幕存在時擋掉轉錄**（回 409，要重跑得帶 `force`）——「找到有 TC 的來源就停」。

- **定位不可靠不猜 TC**（`cnn/02`）：命中率低標記警告，對不上直接標「定位失敗，需人工找 TC」，不給假時間。

- **`P-015`**：<2 秒 FAIL／2–5 秒 WARN。
- **段落顆粒度誠實標示**：來源無詞級時間時（字幕／分段），候選標「起訖需在播放器上自行收窄」——`07` 方式 2 明訂段落級 TC 不足以直接當 BITE 起訖。
