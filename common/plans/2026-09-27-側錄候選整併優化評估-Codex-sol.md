# 側錄候選整併優化評估（Codex gpt-5.6-sol 獨立審查，2026-09-27）

## 背景

2026-09-26整晚，獨立的Claude session（claudex3）證明可以完全自主排CRON（每小時25分）：
偵測CNN整點側錄母帶到位 → 自己跑NeMo Parakeet ASR → 人工複核級過濾 → 生成候選TXT，
連續處理了14/15/16/17/18/20整點六批，全部逐字機器比對通過，且都已被夜間流程正常
入庫（檔名前綴變成「已入庫_」）。

在claudex3自主產線跑通後，請Codex `gpt-5.6-sol`（`model_reasoning_effort=high`）
以獨立審查者角色，評估「候選TXT產生 → 正式入庫（整併）」整條流程有沒有優化空間，
讀了 `AI_Crusher-cnn-nhk-side-pipeline` 的 README/run_pipeline.py、
`TVBS-AIHunter/common/14-S2b-側錄轉譯摘要.md`、`scripts/s2_state.py` 的 add-side
邏輯，以及當晚實際產出的候選檔內容。

## 總結

- 目前流程已能在無人值守下完成「母帶 → 候選 TXT → 正式 state → render → `已入庫_` 改名」。
- 真正需要補強的不是 ASR 精度，而是候選佇列的交易性、嚴格驗證、並發鎖，以及文件／排程責任漂移。
- **不建議讓 claudex3 直接寫 `state.json`**；應把現有入庫端整理成單一、帶鎖的自動 consumer。

## (a) 誰負責正式入庫、何時執行、是否需要人在場

正式設計是：
- claudex3／篩選 agent 只交候選檔。
- **S2 掃帶輪在收工前**執行 `add-side --normalize`、render，再由 `s2_mark_ingested.py --apply` 驗證後改名。
- 依 `13-S2-定時掃帶.md`，外部 agent 禁止直接寫正式狀態檔；原因是 `s2_state.py` 只有原子 replace、沒有檔案鎖。

今晚實際時間也吻合：17、18整點候選約在20:09被標為已入庫；20整點候選約在22:10入庫；
`0926-s2-state.json` 與正式render約在22:12更新。

所以正常情況**不需人工在場**，但目前是「排程叫掃帶agent執行命令」，不是獨立的純機械入庫服務。

文件有兩處危險漂移：
- `14-S2b` 仍大量寫「23:00 最終整併」，但目前23:00輪已取消，晚班最後輪是22:00。
- `13c3-S2-執行版-下-收工與防卡.md` 仍殘留「側錄agent直接寫狀態檔」的舊敘述，與13/14
  相反；收工總表也只明列 `s2_mark_ingested`，沒有明列先跑 `add-side`。

**建議**：新增單一入口 `s2_ingest_side_pending.py`，掃帶輪及獨立排程都只能呼叫它；
把「掃候選 → 驗證 → add-side → render → 驗證 → 改名」寫成不可跳步的固定流程。

## (b) 擬歸位＋T/C 是否落實

有落實，而且相當完整。指定五檔（15/16/17/18/20整點）合計：56個小分題、164個TC段，
全部有擬歸位、T、C，`+` 分隔數也都正確——9/25「只吐TC＋內容、漏做歸位」的問題，
claudex3在9/26已跟上，不是設計仍未實作。

但發現兩個目前保護措施抓不到的實例：
- 18點有小分題名稱殘留控制字：`最高法院限逐人查核SAVE`。
- 15點有 `C:中東,南亞,英國,歐洲`；依 `13f-S2-大分類與各站規則.md`，掛「英國」時
  不應再掛「歐洲」。

逐字機器比對只能證明「內容沒被重打」，不能證明擬歸位／標籤正確。下游影響：
- `SAVE` 會直接成為小分題名稱，造成HTML／矩陣分組污染。
- 不合法的C組合會污染篩選結果與統計。
- `add-side` 對缺T/C、非法T/C採「照樣入庫或丟掉非法標籤」，因此交件檔仍可能被標成已入庫。

**建議新增嚴格模式**：`add-side --strict-candidate`
- 每個單元必須有大／中／小分類、T、C。
- 驗證T上限及C的互斥／連帶規則。
- 擬歸位欄攔截 `SAVE`、`TODO`、`DRAFT` 等控制字殘留。
- 任一單元失敗就讓該候選檔留在待整併並產生錯誤報告，不影響其他整點檔。

## (c) 效能瓶頸與可精簡處

`add-side` 本身只是線性解析，並非瓶頸；主要成本是前面的重複模型閱讀。
`run_pipeline.py` 目前流程中，agent要：對照整份「整點裁切」與「規則已篩選」→
再寫完整TC中文翻譯 → `gen_candidate.py` 擷取一次 → agent再讀一次補分組、歸位、T/C。

建議改成「內容與判斷分離」：
- 腳本產生不可變的TC／內容JSON。
- agent只回傳小型 `decisions.json`：保留／刪除、單元範圍、大中小分類、T/C、形式標記。
- 腳本把decisions與原文機械合成候選TXT；逐字內容從頭到尾不經模型重打。

`filter_promo.py` recall僅約47–83%，目前不宜取消agent複核；可改成輸出「刪除span＋
理由＋前後各兩段」，讓agent審span，而不是完整比對兩份近似全文。

17／18／20點大量重複同一事件（例如美國東北風暴）。可對最近三小時做近重複提示：
高相似只提示「既有單元＋本輪差異」，讓agent判斷是否只收更新；初期只提示、不自動
丟棄，避免漏掉傷亡、裁決等重要進展。

前段目前缺少真正的逐檔resume：baseline是整批結束才更新，中途某檔失敗，前面已成功
的檔案可能下輪重跑ASR。應改為每個來源檔獨立狀態：
`discovered → stable → asr → trimmed → filtered → reviewed → candidate-ready`。

另應在ASR前檢查母帶大小／mtime穩定，避免Google Drive尚未同步完就開始解碼。

## (d) 高頻、非同步模式的新風險

- **狀態檔lost update**：`save()` 雖用tmp＋replace，但沒有鎖，而且所有程序共用同一個
  `.tmp` 路徑；兩個writer同時load／save，後寫者會覆掉先寫者的新增（`s2_state.py:168`）。
- **dry-run與正式執行不同內容**：兩次命令都重新讀候選檔；若producer在中間append，
  正式執行可能吃到未經dry-run的新段落。
- **候選檔重複ID靜默漏段**：同一候選內兩段使用同一個來源＋日期＋TC，第二段會被當成
  「已在庫」略過，沒有「內容衝突」錯誤。
- **跨檔同ID、不同內容**：目前保留第一版、靜默略過第二版；無法分辨安全重跑與真正衝突。
- **checkpoint格式未嚴格驗證**：`add-batch` 有檢查 `{MMDD}-{HHMM}`，但 `cmd_add_side`
  沒有同等阻擋（`s2_state.py:2747`）。
- **跨午夜日期推算**：缺日期時會從入庫checkpoint推；00:25處理前一晚23點母帶可能標成
  隔天，目前只有警告、不阻擋。
- **已入庫改名驗證過弱**：`s2_mark_ingested.py` 比對側錄時只取六碼TC，丟掉CNN／NHK
  與日期（`s2_mark_ingested.py:44`）。同六碼TC若已由另一來源或另一日期存在，檔案
  可能被錯誤改成 `已入庫_`，實際內容卻沒入庫。**這是目前最高優先級的correctness bug。**
- **實際檔名與文件不一致**：文件仍主張每日單檔append；今晚實際採每整點獨立檔。
  後者比較適合並發，應正式化，否則某些agent可能只找精確的 `{MMDD}-側錄候選.txt`
  而漏收分檔。

## 建議實作順序

**P0**
- 修 `s2_mark_ingested.py`：直接重用 `parse_side_txt()` 產生完整canonical ID，
  比對 `CNN 09-26 150227`，禁止只比TC6。
- `cmd_add_side` 加checkpoint正則驗證。
- 同ID若 `raw_entry` 不同，改成硬性conflict，不准靜默略過。

**P1**
- 正式採用每整點唯一檔名。
- producer先寫 `.partial`，全部比對成功後原子改名成 `.ready.txt`；consumer永不讀可變檔。
- 所有入庫都共用 `s2_scan.ps1` 的 `.s2-scan.lock`。
- 加 `--strict-candidate`，避免缺T/C、非法組合或控制字殘留仍被入庫。

**P2**
- 建立queue consumer：每10分鐘或每小時35／45分掃 `.ready.txt`；鎖被掃帶輪占用就
  正常跳過，下輪再收。
- 一次取得鎖、load state一次、依檔驗證、save一次、render一次；壞檔留佇列並附
  `.error.json`，不要阻塞其他整點。
- 同時記錄 `source_hour`、`produced_at`、`ingested_checkpoint`，不要把錄製時間、
  交件時間、入庫時間全塞進checkpoint。

**P3**
- 把agent輸出改成metadata sidecar，由腳本合成逐字候選。
- 加近重複提示及promo span審查，降低每小時重讀整份全文的成本。

此為評估報告，尚未實作任何P0-P3項目，待使用者裁定要不要動工、動工順序。
