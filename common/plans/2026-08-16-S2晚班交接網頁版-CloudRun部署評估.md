# S2 晚班交接網頁版部署 Google Cloud Run 評估

- 日期：2026-08-16
- 性質：**評估報告，不是規則、不是授權實作**——結論為「可行但有前置缺口」，實作時程由使用者裁定，本檔標記的待辦項需使用者明示才能動工
- 觸發：使用者問「晚班交接網頁版適合部署在 Google Cloud Run 嗎？未來想擴充成外電資料庫 Dashboard，記者編輯只要來這裡找素材」
- 範圍：現有 `s2_render_html.py` 產出的靜態 HTML 檢視版 → 常駐雲端網頁；以及後續擴充成可查詢的外電資料庫
- 不包含：資料庫 schema 設計、UI 設計、實際部署動作——本檔只回答「Cloud Run 這個平台選擇對不對、缺口在哪」

---

## 一、先講結論

**Cloud Run 這個平台選擇是對的，但目前晚班交接的「真相源」是本機檔案，不是雲端服務能直接讀到的東西——這才是真正要解的問題，不是「能不能上 Cloud Run」。**

現有產線（見 [[project_s2_wp1_render_pipeline]]）：

```
狀態檔（本機 G:\我的雲端硬碟\...\S2掃帶log\，唯一真相源）
  ├─→ s2_render.py       → 晚班交接.txt   ← 權威產物
  └─→ s2_render_html.py  → 晚班交接.html  ← 純檢視層，衍生物
```

這兩支腳本都是「本機讀狀態 JSON、本機吐檔案」的批次工具，不是常駐服務。`s2_render_html.py` 檔頭本身就寫了「Google Drive 網頁預覽不會執行 JS，篩選會失效，要開本機同步的那份」——代表現在的 HTML 版本設計上就是**本機雙擊看**，從沒打算被遠端網頁伺服器 serve。

## 二、Cloud Run 平台適配性——沒有問題

| 檢查項 | 結論 |
|---|---|
| 無狀態、按用量計費，適合內部工具用途（不是 7x24 高流量服務） | ✅ 適合 |
| 已有實績帳號可用 | ✅ `tvbs-aicg-linebot` 已在跑（GCP 專案同一個帳單帳戶，`asia-east1`），見 [[project_aicg_cloudrun_deploy]]，操作經驗現成 |
| 容器化 Python／Node 服務部署難度 | ✅ 低——`s2_render_html.py` 本身是 Python，包成一支 Flask/FastAPI 服務並不困難 |
| 成本 | ✅ 內部工具流量低，冷啟動免費額度內基本涵蓋 |

**平台本身不是瓶頸。**

## 三、真正的缺口：狀態資料在本機，Cloud Run 摸不到

Cloud Run 容器是無狀態、隨時可能被 GCP 回收重建的執行環境，**沒有辦法直接讀本機 `C:\` / `G:\我的雲端硬碟\` 的檔案**。要讓 Cloud Run 服務有東西可以渲染／查詢，必須先解決「本機狀態怎麼送到雲端」：

### 候選方案（未裁決，列出比較，不代表建議順序）

| 方案 | 說明 | 優點 | 缺點 |
|---|---|---|---|
| A. Cloud Storage（GCS）同步狀態 JSON | 本機排程（`s2_scan.ps1` 收工時）多一步把狀態 JSON 上傳 GCS，Cloud Run 服務讀 GCS 渲染 | 改動最小，狀態檔結構完全不用動 | 只是「換個地方放同一份投影」，還不是真正可查詢的資料庫；查詢功能仍要在應用層自己刻 |
| B. Firestore（NoSQL） | 掃帶入庫時直接寫 Firestore，取代／並行本機 JSON | 天生支援查詢／篩選，適合「記者編輯來查素材」的用途；GCP 原生、跟 Cloud Run 整合簡單 | 要動 `s2_state.py` 的寫入層，改動範圍較大；schema 要重新設計（現行狀態檔是給 render 用的巢狀結構，不是查詢優化過的表） |
| C. Cloud SQL（關聯式） | 同 B 但用 SQL | 熟悉 SQL 的人好上手、複雜查詢（跨站／跨日期／全文搜尋）表現更可預期 | 有固定運算費用（不像 Firestore/GCS 用量計費那麼貼近「內部小工具」的成本模型）；一樣要重寫寫入層 |

**現階段判斷**：若近期只要「把現有晚班交接網頁搬上雲端、可以用瀏覽器打開看」，方案 A 成本最低、風險最小，可以先做。若目標是「未來擴充成外電資料庫 Dashboard」，A 只是過渡——**遲早要走 B 或 C**，而且晚做不如早做：現在 `s2_state.py` 已經是狀態的唯一存取層（agent 禁止直讀寫，統一走這支腳本），如果要換底層儲存，改動會集中在這一支，範圍可控。

## 四、權限／曝險——AICG 的前車之鑑要避開

`tvbs-aicg-linebot` 上 Cloud Run 時，使用者知情選擇把 API Key 直接烙進公開的 `app.js`（見 [[project_aicg_cloudrun_deploy]]），代價是任何人都能打、只是為了省一次手動輸入的麻煩——那次的取捨對象是「燒 OpenRouter 額度」，可以接受。

**這次不一樣**：外電資料庫可能含未發布、有版權限制、甚至還沒公開的素材內容，外洩的代價遠高於燒 API 額度。**部署前就要決定存取控制**，不要等上線後才補：

- 最低限度：Cloud Run 服務掛一組共用密碼／Basic Auth
- 較嚴謹：GCP IAM + Identity-Aware Proxy（IAP），只有 TVBS 網域帳號能進
- 不建議：比照 AICG 那樣直接公開不設防——那次是使用者評估過風險後的個案選擇，不該預設沿用到這個場景

## 五、與現有規則的關係

- `s2_render.py`／`s2_render_html.py` 的「狀態檔＝唯一真相源、render 是單向投影」原則（見 [[project_s2_wp1_render_pipeline]]）不變。無論最後選 GCS／Firestore／Cloud SQL 哪一種，**雲端那份資料的角色都是「投影」或「查詢優化後的鏡射」，本機狀態檔（或其雲端化後的等價物）才是真相源**，不要讓兩邊各自演化。
- 這件事跟 `common/plans/S2-MASTER-追蹤清單.md` 目前列管的省 Token／腳本化項目是不同軸線（那些是「掃帶輪次內部效率」，這個是「掃帶完之後資料怎麼被記者編輯使用」），暫不併入 MASTER 帳本，先以本檔追蹤；若後續決定動工，再評估要不要正式併軌。

## 六、待辦（不代表已核准實作，需使用者明示才能動工）

- [ ] 裁定第一階段目標：先求「網頁能打開看」（方案 A）就好，還是直接瞄準「查詢用資料庫」（方案 B/C）
- [ ] 若選方案 A：本機排程加一步 GCS 上傳；Cloud Run 服務改寫 `s2_render_html.py` 為常駐服務讀 GCS
- [ ] 若選方案 B/C：`s2_state.py` 寫入層改造範圍評估、schema 設計、既有 render 邏輯（`group_items`／`render_item`／`mark_for`）能否原樣搬過去或需要重寫
- [ ] 存取控制機制選定（共用密碼 vs IAP）並在部署前完成，不要上線後才補
- [ ] 成本估算（Cloud Run／Firestore 或 Cloud SQL／GCS 用量）——內部工具流量應該極低，但要有數字而不是憑印象
