### 2-1a ⚠️ 但素材確實是在早上「做出來」的，只是晚幾小時才發布

改用 `creationDate` 重掃同一個 30 天，台北 08:00–13:00 有 **73 則**（約 2.4 則／日，
分布在大多數日子）。逐則比對這 73 則的 `creationDate` → `sortDate`：

- **發布延遲中位數 6.1 小時**（最短 0、最長 37.1 小時，只有 1 則是即時發布）
- 例：`928974` 建立 08-31 10:10 → 發布 08-31 16:12（延遲 6.0h）；
  `928839` 建立 08-29 10:08 → 發布 08-29 21:23（延遲 11.3h）

**意義**：早上的素材不是不存在，是 ENEX 那邊還沒發布。掃帶抓的是**發布時間**
（`sortDate`／`publishedDate`，兩者實測完全一致），所以**跳過早上那兩輪不會漏收**——
那些素材會在下午的輪次自然出現。⛔ 反過來說，**時間窗絕對不能改用 `creationDate`**，
那會讓每輪都去撈一批「還沒發布」的東西。

## 三、🔴 現場查到的既有錯誤（照現有規格實作會踩雷）

### 3-1 🔴 `hits.total` 是純數字，不是 `{value: N}`

- 規格（`2026-08-09-ENEX計畫` 附錄 A-1／A-2③）與 08-26 規劃書的健康檢查都寫
  「回 `hits.total.value`」。
- **實測 `hits.total` 直接就是 `348127`**（整數）。ES 7+ 預設回 `{value, relation}`，
  但 ENEX 這層 proxy 回的是 int。
- 後果：照規格寫 `j.hits.total.value` 拿到 **`undefined`**。
  我自己第一次就踩到——回傳物件被 `JSON.stringify` 丟掉整個鍵，得到空的 `{}`。
- **影響面**：`s2_platform_reconcile.py` 的 `--true-count` 是 agent 現場查回來餵進去的，
  agent 照規格查就會餵 `undefined`／`null` 進對帳。**整個 ENEX 對帳目前可能是假的。**
- 修法：規格與 18 檔健康檢查範本改成
  `const t = j.hits.total; const n = (t && typeof t === 'object') ? t.value : t;`

### 3-2 🔴 `s2_platform_merge.py --apply` 在輪次內**必定失敗**

- `s2_scan.ps1:301-304` 在叫 claude **之前**就用 `FileShare::None` 開 `.s2-scan.lock`，
  一路握到 `finally` 才放——**整輪都握著**。
- `s2_platform_merge.py:143-157` 的 `lock_busy()` 是「檔案存在就中止、exit 1」。
- 兩者相加：**輪次內呼叫 `merge --apply` 100% 撞鎖退出**。
  這條護欄原本是為了防「獨立流程 vs 排程輪」互相蓋掉，設計正確；
  但 ENEX 一旦進輪次，它就從護欄變成閘門。
- 修法（必要，約 5–10 行）：加 `--in-round` 旗標略過鎖檔檢查，
  並在 docstring 寫清楚「只有由 `s2_scan.ps1` 叫起的 agent 可以用」。
  ⛔ 不要直接拿掉鎖檔檢查——人工流程仍然需要它。

### 3-3 🟠 素材量假設差 4 倍

- 附錄 A-2① 註明「ENEX 量級 ~7 則／3 小時，單輪一次呼叫就能取完，不需要分頁」。
- **實測 2 小時 27 則**、單一小時最高 20 則。
- `size:100` 仍然夠用（27 < 100），所以「不需要分頁」的結論**碰巧仍成立**，
  但那句話背後的量級假設錯了，成本估算不能沿用它。
