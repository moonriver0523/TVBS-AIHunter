## 一、現行怎麼跑

固定輪是 **一個 CLI agent 從頭做到尾**，掃描順序 **NS → AP → RT**（不可調換）。

| 層 | 做法 | 依據 |
|---|---|---|
| 啟動 | `s2_scan.ps1` 叫一支 `claude -p`，`--mcp-config` 只掛一個 Playwright | `scripts/s2_scan.ps1` |
| 瀏覽器 | 單一 persistent profile：`C:\Users\User\.playwright-s2-profile-v2` | `scripts/s2_mcp.json` |
| 互斥 | OS 檔案獨佔握把 `.s2-scan.lock`；兩輪並行必互鎖，撞到就跳過不排隊 | launcher 檔頭註解（0803 空窗八小時、0806 連撞） |
| 工具 | `--disallowedTools TaskCreate,TaskUpdate,TaskList,TaskGet,TaskOutput,TaskStop,Agent` | T2，`s2_scan.ps1`；0812–0813 開待辦清單 12–26 次零產出 |
| 工作契約 | prompt 明文「不准轉包」：掃描、分類、稽核、render 全部自己做 | `scripts/s2_scan_prompt.md` 檔頭 |
| 狀態 | 只准 `s2_state.py` 寫 `{MMDD}-s2-state.json` | 13c／13d |
| NS 保活 | 1 小時滑動 JWT；NS 排第一站＋收工再摸 landing | 13c §0 |

收錄路徑已是 API 直查（每站 2–3 次 `browser_evaluate`），不是開詳情頁。貴與慢在 **每則 LLM 寫 entry＋跨站分類**，不在「開三個網站」。

## 二、為什麼看起來吸引人

三站清單／文稿彼此沒有資料依賴，並行可把「寫素材行」的牆鐘從相加變成取最慢那站。現行一輪大約 16–23 分；理論上可壓到「最慢一站 + 整併」。

這項收益 **只在真的並行且三站互不搶資源時才存在**。序掃三個子代理只有三次冷啟動、沒有牆鐘好處，比現況更差。

## 三、四個硬擋（任一條就否決「直接派出」）

### 3.1 瀏覽器是單例

Playwright MCP 只有一個 process、一個 `--user-data-dir`。三個 agent 同時 `navigate`／`evaluate` 會互踩分頁、回應錯站、profile 互鎖。launcher 的鎖就是為防這件事——連**兩輪先後重疊**都撐不住，更不必談一輪內三份並行。

NS JWT 在該 profile 的 `localStorage`。拆成三個 profile 等於三套登入／保活；現行 `s2_keepalive` 只養一個 profile。

### 3.2 狀態檔是單寫者；分類是跨站的

`add-batch` 同時寫同一份 JSON 會搶寫。更關鍵的是分類：同事件跨 NS／AP／RT 必須併成同一中／小分題（13d 4b、`s2_topic_review.py`）。子代理各自歸類後，主代理幾乎要把分類重做一遍——「整併」不是把三份清單接起來。

### 3.3 排程外殼留不住背景任務（已實錯）

本環境的 Agent 工具是背景執行。0811-1800：工作 agent 把整輪丟給背景子代理後提早交卷；外層行程收工時子代理才掃完 NS＋AP，**背景任務只有約 600 秒緩衝就被強制砍掉**。

- 離開碼 0、沒有錯誤訊息
- RT 一則沒收，稽核與 render 沒跑
- 當輪白燒約 $2.9，補掃還得整份清單重撈

這就是 prompt「不准轉包」的由來。主代理「派完等通知」在 `-p` 排程裡等同一個死法。

### 3.4 工具層已禁止派出

`--disallowedTools` 含 `Agent`。不先改 launcher，子代理根本派不出去。T2 硬排除的原因是自律會漂移，不是一時方便。

## 四、跟「Task 6 三站固定 collector」不是同一案

MASTER「明文不做」已列 Task 6：把三站收錄寫死成腳本。否決理由是 **API 漂移會從「agent 當場繞過」變成無聲失敗**。

本案保留現場適應力，但把單一例項資源（瀏覽器／狀態檔／外殼生命週期）拆成三份。風險方向不同，工程量同樣高，**不因為 Task 6 已否決就自動否決本案，也不因為本案是 agent 就自動可行。** 兩者都不要當熱修偷做。

## 五、若日後要重議，最低門檻（目前都不存在）

少任何一項，品質會比現況差。未另開明示前 **不得動工**（D 類鐵律）。

1. **三套 Playwright MCP + 三個 profile + 三套保活**（否則不能並行）
2. 每站只准寫自己的 `batch-NS.json`／`batch-AP.json`／`batch-RT.json`，**禁止碰狀態檔**；主代理單線 `add-batch` → 分類 → audit → render
3. 派出必須是 **launcher 層三個前景 `claude -p` 子行程**（等到結束），**不是** session 內 Agent 工具
4. 接受前綴約 **×3**（T1 才把啟動前綴砍到 43.5k；三個子代理各冷啟動，prompt cache 不共用）——牆鐘可能短、token 幾乎一定更貴
5. 先量現行輪「每站實際分鐘／token」，確認瓶頸真的在站與站之間的序掃，而不是寫 entry／分類

## 六、較便宜、仍能縮時的替代（本案不採用時）

- 主代理獨佔瀏覽器，三站 API 仍序掃。每站本來就 2–3 次 evaluate，**收集不是瓶頸**。
- 真要並行的是「寫 entry」：主代理先把三站瘦身 JSON 落檔再分站寫稿——接近已延後的 Task 7，且仍付三次冷啟動。
- 單站掛掉已有規則：記 `needs-review`、跳過、掃另外兩站；不必為隔離失敗而拆成三個 agent。
- ENEX／ABC 已是獨立人工流程（A9），不要再掛進三站輪——同一輪加掛額外站曾讓 NS token 在收工前過期（0811-0430）。
