## 一、先講結論

**不需要大改，只需要拿掉「自動生成＋覆蓋率重試」這一段，其餘步驟（剪接對齊、字幕產生、終檢）本來就是設計來處理「拿到一份音檔之後怎麼辦」，換成人工配音檔依然成立，甚至終檢的重要性會提高。**

現有自動剪片配音上字流程（見 [[reference_auto_video_pipeline_pitfalls]]）：

```
腳本輸入 → 分組合成(GPT-SoVITS) → 音量正規化 → ASR覆蓋率驗收(弱句換seed重試)
        → 剪接對齊(用配音長度裁畫面) → 字幕產生(ASR時間戳對齊) → 終檢(雙向RMS/抽影格)
```

若改人工配音：

```
人工配音檔 → 【新增：切段消化，見第三節】 → 音量正規化 → 剪接對齊 → 字幕產生 → 終檢
```

## 二、逐步比對：哪些要動、哪些不用動

| 步驟 | 自動配音時的角色 | 換人工配音後 | 結論 |
|---|---|---|---|
| 分組合成（GPT-SoVITS） | 依 2-3 句甜蜜點生成音檔 | 不需要，音檔已存在 | **整段拿掉** |
| ASR 覆蓋率驗收＋換 seed 重試 | 生成失敗時重新生成 | 沒有「重新生成」這個選項，人工音檔是既定事實 | **拿掉重試機制**，但覆蓋率檢查本身要保留、轉為「消化」步驟的一部分（見第三節） |
| 音量正規化 | 解 int16 爆音（GPT-SoVITS 特有問題） | 人工錄音沒有 int16 峰值問題，但不同人工來源音量落差可能更大 | **保留**，理由從「修正模型輸出格式」改為「統一不同錄音批次的峰值」 |
| 剪接對齊（配音長度＋0.3秒裁畫面） | 用生成音檔的長度算畫面裁切點 | 用人工配音每句的實際長度算，邏輯完全一樣 | **不變** |
| 字幕產生（ASR 時間戳對齊） | 對生成音檔跑 ASR 抓詞級時間戳 | 對人工音檔跑 ASR 抓時間戳，人配音語速/停頓跟稿子不會逐字對齊，這步驟只會更必要 | **不變，且更關鍵** |
| 終檢（雙向 RMS／有聲無字幕互查） | 抓生成瑕疵（吞字、雜訊） | 抓人工配音瑕疵（漏念、加詞、忘記剪掉的重錄片段殘留） | **不變，且是少了自動覆蓋率把關後唯一的防線，重要性提高** |

## 三、人工配音檔怎麼「消化」：核心新增機制

人工配音檔跟自動生成音檔最大的差異，不是音質，而是**音檔內容跟文稿不是天生一一對應**——中間可能夾雜念錯、停頓重來、過錄的片段。需要新增一段「切段消化」把整份音檔轉成跟自動配音一樣乾淨的「文稿句子 → 音檔時間區間」對照表，讓下游（剪接對齊、字幕產生）不用改。

### 消化流程（概念）

1. **全檔 ASR 轉錄＋VAD 切段**：對整份人工配音檔跑 ASR，取得逐字稿＋詞級時間戳；搭配靜音偵測（VAD），把音檔切成一段一段的「片段」（每次開口到停頓算一段）。
2. **逐段比對文稿**：把每個 ASR 片段的文字，用文字相似度（覆蓋率／edit distance——沿用既有配音驗收就在用的比對邏輯）去對應文稿的句子，抓出「這段大概對應第幾句」。
3. **重複/重錄的判斷邏輯**：人配音常見模式是「念錯 → 停頓 → 重念」，同一句文稿內容會連續對應到 2、3 個相鄰片段。處理原則：**同一句文稿若匹配到多個相鄰片段，取時間軸上最後一個**，中間念錯／喊卡重來的片段直接捨棄。
4. **覆蓋率二次驗證**：選出的「最後一段」再跑一次覆蓋率檢查，確認完整念完整句，不是又念一半被切斷；沒過就往前找上一個匹配片段。
5. **產出對照表**：最終輸出「文稿句子 → 對應音檔起訖時間」的乾淨對照表，交給後面的剪接對齊、字幕產生步驟，介面跟自動配音產出的資料結構一致。

### 已知風險與取捨（未裁決）

- **「取最後一次」假設的邊界**：這個判斷假設人是照稿順序念、錯了就地重來。若實際錄製習慣是「先念過關、之後又跳回去補錄修飾版」（非線性重錄），「取時間軸最後」會抓錯，需要改成「取覆蓋率最高」或要求人工提供錄製時間軸提示。
- **無法自動判斷的情況**：若某句完全沒有任何片段的覆蓋率達標（人可能整句漏念、或用了跟稿子差異很大的口語轉述），系統只能標記「待人工複核」，不能自動放行——這點跟現有「污染判定文字/語言>聲學」（規則 7）的精神一致，機器判斷有疑慮一律回人工。
- **切段消化本身要不要先問使用者實際錄製習慣**：本次評估先假設「照稿順序線性重錄」為預設情境；若實測不符，這段邏輯需要調整判斷依據。

## 四、實作工作時間評估（獨立於自動配音的另一套平行系統）

假設不動既有自動配音管線、純新增一套模組，估計約 **4–6 個工作天**，最大不確定性在最後的真實素材校調：

| 模組 | 工作內容 | 估時 | 備註 |
|---|---|---|---|
| ASR 全檔轉錄＋VAD 切段 | 接既有 ASR 元件，跑整份人工配音檔取得逐字稿＋時間戳＋靜音切段 | 0.5 天 | 現有配音驗收就在用同一支 ASR，屬串接非新開發 |
| 逐段比對文稿 | 每個片段文字 vs. 文稿句子的覆蓋率/edit distance 比對 | 0.5–1 天 | 覆蓋率演算法沿用既有配音驗收邏輯（規則庫已有），改成雙向比對 |
| 重複/重錄判斷＋二次驗證 | 「同句多片段取最後一次」邏輯＋選定片段再驗覆蓋率 | 1–1.5 天 | 核心新邏輯，非既有模組可直接沿用，需要寫測試案例 |
| 產出對照表＋下游介面對接 | 輸出「文稿句→音檔區間」格式，接剪接對齊/字幕產生 | 0.5 天 | 資料結構刻意跟自動配音產出一致，下游不用改，這步只是轉接層 |
| 真實素材校調＋邊界案例 | 拿實際人工配音檔跑，檢驗「取最後一次」假設是否成立、抓漏網案例 | 1–2 天 | **最大不確定性來源**：目前不知道實際錄製習慣（是否嚴格線性重錄），若常出現非線性補錄，這段可能要重寫判斷邏輯、時間會拉長 |
| 文件/規則庫寫入 | 併入 `production/09`，補踩雷清單 | 0.5 天 | — |

**關鍵前提**：假設「人是照稿順序念、錯了就地重來」的線性重錄模式成立。若先提供幾份真實人工配音檔樣本可先驗證這個假設再估，會比憑空估更準；若假設不成立，第三、五項可能各多抓 1 天緩衝。

### 若只由 Claude 建立流程與必要腳本（非人力開發天估算）

上表是以人力開發天為單位的通用估法；若情境是「只請 Claude Code 在單一/少數 session 內把流程和必要腳本寫出來」，時間單位不同，拆兩段看：

- **純程式建構（切段/比對/重錄判斷/對照表輸出/下游對接）**：因為 ASR 元件、覆蓋率比對邏輯、下游剪接對齊與字幕產生模組都已存在於現有規則庫可直接重用，這部分是**串接與新寫一段判斷邏輯**，不是從零建置。以一個 agent session 實際動手寫程式＋跑過一輪合成測試資料驗證邏輯通，**大約半天內（數小時的專注 session）可以完成一版可跑的腳本**。
- **拿真實人工配音檔校調＋抓邊界案例**：這段耗時不是由「寫程式」決定，是由「使用者提供的樣本數量、樣本裡實際出現多少種重錄模式」決定——不確定「照稿順序重來」假設成立與否前，無法把這段壓縮成固定時數。**這段需要使用者配合提供樣本、逐輪回饋**，不是單靠 Claude 一次 session 能定案，估計仍要來回 1–2 輪測試才能收斂。

**結論**：如果只要「跑得起來的第一版腳本」，一個 session 內可交付；如果要「跟真實人工配音檔的落地版本」，時間主要卡在樣本取得與來回校調，不是卡在寫程式本身。
