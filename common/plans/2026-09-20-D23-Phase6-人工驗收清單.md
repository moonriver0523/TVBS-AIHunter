## 執行前共通準備（待辦）

- [ ] 在隔離的沙箱副本準備可丟棄的 `state.json` 與 `s2-youtube-cursors.json`；不可使用正式 state。
- [ ] 依組織核准的祕密管理方式，僅在目前執行程序注入 `YOUTUBE_API_KEY`；不要把 key 寫進命令列、shell history 或檔案。若既有作業方式無法安全注入環境變數，先停止並詢問管理者。
- [ ] 下列 collect 的共同命令骨架（依站別與檔名替換）：

```powershell
python scripts/s2_youtube_bridge.py collect --site <cna|yna> --checkpoint <MMDD-HHMM> --state <沙箱-state.json> --cursor <沙箱-s2-youtube-cursors.json> --bootstrap-start-utc <UTC-ISO8601> --out <沙箱-manifest.json>
```

預期：stdout 僅有 `status`／`counts`；產生 manifest，但不改寫 state 或 cursor。若沒有 key，預期 stderr 明示 `YOUTUBE_API_KEY` 缺失且不產生輸出檔；這不是可略過的降級。

## Phase 6 的六項人工 checklist（全部待辦）

- [ ] **1. fixture 對照與單站限量真實 API 樣本。** 先用 `--fixture-dir scripts/fixtures/d23_youtube` 跑一次相同命令骨架，確認離線 fixture 的預期結構；再移除 `--fixture-dir`，只對 CNA 或 YNA 其中一站執行上述沙箱 collect。人工開啟 manifest 的每個 ready／deferred 項目，逐一在 YouTube 影片頁面比對：watch URL、`video_id`、標題、發布時間（換算 UTC）、影片時長、頻道 ID 與 `source`。另以 `yt-dlp --list-subs "https://www.youtube.com/watch?v=<video_id>"` 人工確認字幕語言（CNA `en`；YNA 初判 `zh-Hant`）是否存在；本 bridge 的 API-key adapter 不下載字幕，字幕不可用應是明列 deferred，不可假裝成功。

- [ ] **2. manifest／batch 人工審查，絕不套用。** 對第 1 項 manifest 準備人工 decisions 檔後執行：

```powershell
python scripts/s2_youtube_bridge.py finalize --manifest <沙箱-manifest.json> --entries <人工-decisions.json> --out <沙箱-batch.json>
```

預期：產生 batch，沒有 `--apply`，state／cursor 不變。人工以影片頁面和 manifest 回查 batch 的 `ID`（`CNA-<videoId>`／`YNA-<videoId>`，大小寫不變）、`source`、watch URL、發布時間、時長、字幕語言／`src_text` 與分類欄位；並搜尋 manifest、batch、終端 stdout/stderr，確認均無 API key 明文。

- [ ] **3. 沙箱 state 的端對端驗收。** 僅在可丟棄 state 上，依既有 S2 操作手冊先完成 render、source 排序、T/C 預設、標題去重與 `mark-ingested` 的完整流程；使用第 2 項 batch 作為輸入。預期：render 顯示的來源、影片 ID、發布時間與時長均可回鏈到 manifest 及 YouTube 影片頁面，且 `mark-ingested` 後再次檢查不會新增相同 ID。人工記錄每一筆對照結果；不得因此改寫正式 state。

- [ ] **4. 第一個排定輪次前的 CNA 限量上線審查。** 版權／使用權 hard gate 已由權責人書面放行後，才在排定輪次的受控環境準備 CNA 的 collect 與 finalize。命令仍先使用第 2 項的無 `--apply` 版本，人工覆核影片頁面、發布時間、字幕語言、時長、ID 與 source；只有覆核者明確批准才可由**人工**依當時排程手冊執行帶 `--apply --in-round` 的 finalize。預期：任何未批准、deferred 或 preflight 失敗都保留候選且不推進 cursor；本清單不代表已批准或已執行套用。

- [ ] **5. CNA 穩定後再觀察 YNA 至少三輪。** 在 CNA 結果經人工確認穩定後，於三個不同 checkpoint 對 YNA 重複第 1、2 項命令；每輪記錄 API 呼叫／配額觀察值、窗口起訖與 catch-up 結果。人工比對每筆影片頁面的發布時間、字幕語言、時長、ID、source，並特別確認高頻影片沒有因分頁而漏收、跨輪 ID 被去重、字幕失敗率及人工負荷可接受。預期：有失敗時保留待補窗口與 deferred，不因壓配額而縮短分頁，也不偷偷把失敗當成功。

- [ ] **6. D23 全流程通過後的正式核對與 MASTER 回寫決策。** 在外部 D23 驗收全部通過後，先執行既有測試與人工抽查命令，並至少抽 10 筆跨 CNA／YNA 的資料，比對 YouTube 影片頁面、發布時間、字幕語言、時長、永久 ID 與 source。預期：D23 與既有五站的 render／來源排序／去重都一致，且 API 使用量已有人工紀錄。只有權責人確認所有前項與版權 gate 後，才另行決定是否回寫 `common/plans/S2-MASTER-追蹤清單.md`；本文件沒有、也不授權任何回寫動作。
