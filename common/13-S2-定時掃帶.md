## 批次分立與整併（2026-07-30 使用者訂正，取代先前「每輪重寫」設計）

**核心原則：每輪只寫新東西，不碰累積的彙整結果；分類彙整只在整併時做一次。** 這是使用者確認的實務做法——晚班本來就是每批掃帶各自產出摘要、下班前才整併成一份晚班交接，不是邊掃邊維護一份持續更新的總表。

### 兩種節奏，職責不同

| | 批次擷取（每個檢查點都做） | 整併（同一個檢查點，緊接批次擷取之後） |
|---|---|---|
| 觸發 | 決策 2：排程 16/18/20/22/23 或人工加開 | 同一次觸發裡，擷取完接著跑；23:00 額外標記為**最終整併** |
| 做什麼 | 找新素材、寫三段式內容，**存進 JSON 的欄位**，不產生任何 txt | 讀 JSON 裡**尚未整併**的項目，判斷大分類／中主題歸屬、處理同組相鄰，套三方比對保留人工編輯，寫出 `{MMDD}晚班交接.txt` |
| 要不要判斷力 | 不用——是否已見過純靠代碼比對 JSON | **要**——「這則歸哪個中主題、要不要開新大分類」需要語意判斷 |
| 觸碰範圍 | 只有這次新找到的素材 | **只有上次整併後的新增／變動項目**（見下方 `compiled` 欄位如何做到增量），不是每次全量重算 |
| 頻率 | 5 次（16/18/20/22/23） | 5 次，其中 23:00 為最終版 |

**批次擷取不需要三方比對**：每次只是把新素材寫進 JSON 的欄位，不去改動任何已整併過的 txt 內容，沒有「舊版被覆蓋」的風險。三方比對只在**整併**時用——若某次整併後、下次整併前，有人工編輯過上一版 txt，下次整併要靠「比對現行 txt vs 上次機器版快照」保留那些編輯。

**大新聞即時可見（承接決策 4）不受影響**：決策 4 要的是「稿未到也要能看到」，這靠的是**JSON 裡的批次內容立即存在**（不必等整併），跟「有沒有分類彙整成正式三層庫存 txt」是兩回事。急件可以直接查 JSON，不用等下一個整併檢查點——或直接手動加開一次整併。

## 狀態 JSON 欄位設計（2026-07-30 定案）

每則素材一筆，欄位分兩組：**批次擷取寫的**（找到當下就填）與**整併寫的**（分類彙整時才填）。

| 欄位 | 誰寫 | 內容 | 用途 |
|---|---|---|---|
| `id` | 批次擷取 | 素材代碼（`RT0595`）或側錄識別（`CNN 151328`） | 唯一鍵，判斷「是否已見過」的依據 |
| `source` | 批次擷取 | 站台（`RT`／`AP`／`CNN_newsource`／`CNN_recording`／`NHK_recording`…） | 追溯來源、統計用 |
| `first_seen_checkpoint` | 批次擷取 | 首次抓到的檢查點（`16:00`） | 追溯素材何時進系統 |
| `last_checked_checkpoint` | 批次擷取（每次重新確認都更新） | 最近一次確認仍存在的檢查點 | 判斷素材是否過期／該不該繼續追蹤 |
| `script_status` | 批次擷取 | `has_script` ／ `pending`（對應決策 4 的「有稿／稿未到」） | 整併時判斷要不要標 `(稿未到)` |
| `raw_entry` | 批次擷取（`pending` 轉 `has_script` 時**覆寫**） | 三段式內容本身（代碼＋備註＋摘要＋畫面＋BITE），批次擷取當下就寫好 | 整併時的**唯一輸入來源**——整併不重新生成內容，只做分類與排版 |
| `compiled` | 整併寫入 | `null`（未整併）／上次整併的檢查點時間 | **增量整併的依據**：整併時只挑 `compiled` 為 `null`，或 `raw_entry` 在 `compiled` 之後又被改過（`script_status` 從 pending 轉 has_script）的項目來處理，其餘直接沿用上一版 txt 裡已經排好的內容，不重新判斷分類 |
| `category` | 整併寫入 | `{大分類, 中主題}` | 一旦分類過就記住，避免下次整併重新判斷同一則該歸哪裡；也是「同組相鄰」排版時的依據 |

**這組欄位怎麼讓整併變成增量而不是全量**：整併時，一則素材只會落在三種狀態之一——

1. **全新**（`compiled` 為 `null`）→ 要判斷分類、寫進新的 `category`，成本全付
2. **稿到了但已整併過**（`raw_entry` 在上次 `compiled` 之後被覆寫，通常是 pending→has_script）→ **沿用既有 `category`**，只重新排版這一則的內容，不必重新判斷分類
3. **沒變化**（`compiled` 已存在且 `raw_entry` 沒變）→ **直接照抄上一版 txt 裡的內容**，完全不進 LLM

只有第 1、2 類真的要花 token；第 3 類（多數素材，一旦分類過就不會再變）幾乎零成本。這是「增量整併」在數字上比「每次整併都全量重讀」省的地方。

> ⚠️ **這組欄位不能直接拿去當 Dashboard／Aigent-Fable 的 schema**（2026-07-30 使用者問過，答案是不能）。原因：
> - `raw_entry` 是**預先渲染好的顯示字串**（三段式黏在一起），Dashboard 要的是拆開的結構化欄位（標題／摘要／畫面描述／BITE 各自獨立）才能篩選查詢——這正是 Aigent-Fable 藍圖的 `ai_enrichments`／`asset_bites` 已經做對的事，我這裡是把它們黏回去，是退步不是延伸。
> - `compiled` 欄位的存在理由是「沒有即時資料庫」；有了 Dashboard，查詢即時發生，這個欄位跟整個增量整併機制應該直接消失，不是被繼承。
> - `id` 把來源與代碼黏成一個字串，藍圖是分開的 `source_id`／`source_ref`。
> - **唯一值得回饋的是 `category`（大分類／中主題）**——藍圖的 `assets` 表目前完全沒有主題分組概念，這是這輪設計挖出來、藍圖之後可能該補的東西，方向是反過來的。
>
> 這份 JSON 從一開始就是**用完即丟的過渡工具**（見 `common/12`：「Dashboard 建好前用純文字清單暫代」），不是 Dashboard schema 的草案，不要在它身上做超出「撐到 Dashboard 蓋好」以外的擴充規劃。

### Token 成本（2026-07-30，一晚 60–80 則量級，抓量級用非精確值）

以 70 則、16/18/20/22/23 共 5 個檢查點（每點約新增 14 則）試算：

| 項目 | 成本 |
|---|---|
| A. 展開 70 則詳情頁（每則 ~2,500 input） | input 175,000 |
| B. 5 個檢查點 × 3 站輪詢空轉 | input 42,500 |
| **整併×5（增量，只處理當次新增）** | input 6,300／output 6,300 |
| **合計** | input 223,800／output 16,800，加權當量 **≈ 30.8 萬** |

對照四種設計的成本量級：

| 設計 | 加權當量 |
|---|---|
| 每輪 LLM 重寫整份（最初誤判，20 輪） | ≈ 79 萬 |
| 每輪腳本渲染（機械式、無判斷力，20 輪） | ≈ 39.75 萬 |
| 批次分立、20 輪擷取＋整併 1 次全量 | ≈ 43.5 萬 |
| **5 檢查點、增量整併**（現行定案） | **≈ 30.8 萬** |

比最初設計省逾六成。兩個因素疊加：**檢查點從 20 降到 5**（B 項直接砍到 1/4）＋**整併走增量**（多數素材分類過一次就不再重付判斷成本）。若全量重算（每次整併都重讀全部 70 則），5 檢查點版本也還是約 38 萬，比 20 輪整併 1 次略省——可見**降低檢查點頻率**本身就是最大的省法，增量整併是疊加的第二層優化。

## 庫存檔格式（三層標記，2026-07-30 定案）

| 層級 | 寫法 | 說明 |
|---|---|---|
| 大分類 | `======{名稱}======` | 前後各 6 個等號，**整份樣板順序全列**（**無素材的大分類也要留空殼**，見「新開／整併晚班交接」），不重排、不省略 |
| **中主題** | **`【{名稱}】`** | 全形方括號包圍，**一律要寫**，分軸由 AI 依內容判斷 |
| 小分題 | `{名稱}`（裸行） | **通常 4 個全形字元**；可夾雜數字或英文符號，但**不可整行都是數字或英文**；**相似素材應共用同一小分題**（見下） |
| 素材行 | `{代碼} ({備註}) [(BITE)] {摘要}▎畫面：…▎BITE：…` | 掛在小分題底下，三段式，詳見下方「素材行的寫法」 |

**空行／分隔規則**（2026-07-31 使用者訂正；同日再補「小分題 `+` 分隔」）：

| 位置 | 規則 |
|---|---|
| 大分類 `======…======` **與** 其下第一個中主題 `【…】` 之間 | ✅ 空一行 |
| **中主題與中主題** 之間（同一大分類內換下一組 `【…】`） | ✅ 空一行 |
| 中主題 `【…】` **與** 小分題 之間 | ❌ 不空行（緊貼） |
| 小分題 **與** 素材行 之間 | ❌ 不空行（緊貼） |
| 同一小分題下的**素材行與素材行**之間 | ❌ 不空行（緊貼連排） |
| **小分題與下一個小分題**之間（同一中主題內換下一組裸行標題） | ✅ **獨立一行只寫 `+`**（半形加號、前後不空行），**不要用空行**隔小分題 |

**小分題的長度與字元限制**（2026-07-30 使用者補充，並以範例①② 實測校準）：

- **通常 4 個全形寬**。實測：範例① 84.5%（49/58）、範例② 77.8%（56/72）是 4 字；扣掉混進統計的雜訊（`+` 分隔符、講者行如 `川普：`／`柏林市長：`、逐字內文句如 `目前仍有待觀察。`）後，真正的小分題幾乎全是 4 字。範例③ 有 3 字（`屋子倒`）與較長的（`空拍橋斷、煙囪倒塌`），所以是「通常」而非硬性上限。
- **算的是全形寬度，不是字元數**——英數佔半形，兩個才吃掉一格。實測命中 `陸AI廚師`、`陸AI機人`：5 個字元，但正好 4 個全形寬。這正是「可以夾雜數字或英文」成立的原因。
- **不可整行都是數字或英文**。
- ⚠️ **最後這條不只是風格，是解析的保命條款**：小分題是**裸行、沒有任何標記**，唯一能跟素材行區分的依據就是「它不長得像素材代碼」。若允許整行數字或英文，就會跟 `RT1396`、`AP4675135`、`IN-02TU`、`CNN 151328` 這些代碼行撞在一起，機器分不出這行是標題還是素材。

**小分題要夠粗、不要一則一個**（2026-07-31 使用者訂正）：

- **相似／同事件／同面向的素材，應掛在同一個小分題底下**（同一小分題下可連排多則素材行，中間不空行）。
- ❌ 不要為每一則素材各開一個幾乎同義的小分題（例如「岸際聚集」「移民回流」「圍籬破口」其實都可併成「岸際動態」或「休達移民」下的一個粗分題）。
- ✅ 只有**事件階段、地點、主角或新聞面向明顯不同**時才另開小分題。

**三段的分工**

| 段 | 內容 | 規則 |
|---|---|---|
| 第一段 | `{代碼} ({備註}) [(BITE)] {摘要}` | 備註放**最精華的一兩個詞**供一眼掃視；摘要一句話講完事件 |
| `畫面：` | 逐項列出畫面內容 | 頓號分隔、同群用分號、句號收尾。這裡放**完整清單**，與備註的「精華詞」分工 |
| `BITE：` | 引言 | **濃縮版，不是逐字**；無引言時整段寫 `無BITE。` |

**分隔符用全形直線 `▎`，不加前後空格。**
- ❌ 不用 `///`——會跟多來源代碼的 ` / ` 混淆，人工手打也容易打成 `//` 或 ` / / `。
- ✅ `▎` 在 39,851 字的既有語料裡零出現，不與 `/`（多來源代碼）、`+`（**小分題**分隔）、`：`（段落標籤與地點前綴）衝突。

**`(BITE)` 第二括號只在「有 BITE」時出現**（使用者 2026-07-30 訂定）。無 BITE 時不標，靠尾端的 `無BITE。` 表達即可。用途是讓編輯只看行首前半段就知道這支有沒有引言，不必把整行約 90 字讀完。

⚠️ **第一個 `({備註})` 禁止再寫 `BITE`**（2026-07-31 使用者訂正）：有引言時**只**用第二括號 `(BITE)` 與尾端 `▎BITE：…` 表達；備註裡再寫 `BITE` 是重複、一律刪掉。  
❌ `RT2244 (官房長官 BITE 限日本) (BITE) …`  
✅ `RT2244 (官房長官 限日本) (BITE) …`

⚠️ **`BITE：` 段是濃縮不是逐字**——像 `「我和兒子徹夜守住，拒撤離，終救四戶」` 這樣，讓編輯知道「這句在講什麼、值不值得用」。**不可直接拿去當 SB**；逐字原話與精確 TC 是下游 [`07-bite-assistant.md`](07-bite-assistant.md)（S7）的事。

> 📌 **這是新版三段式，取代範例①② 的舊寫法**（舊的只有「代碼＋一句話＋句尾 BITE」）。舊範例仍可參考排版與分類，但素材行以本節為準。

**細部規則**

- **代碼後接一個半形空格**。實測範例有 26/101 則代碼與摘要黏在一起（`IN-09TU中國航班…`），那是瑕疵，一律補空格。
- **多來源用 ` / ` 相接**，斜線**前後各一個半形空格**（`AP4675107 / IN-02TU`）。實測範例寫成 `AP4675107/IN-02TU` 沒有空格，同樣是瑕疵。
- **備註緊接在代碼後面、摘要之前**，用**半形括號 `()`**。實測範例多數把備註放在最後，只有 `RT0957 (炸瞬 無聲) 監視器畫面…` 這種放在前面——**以放前面為準**，因為編輯掃清單時先看到「這支畫面值不值得看」才決定要不要讀摘要。
- 備註要**非常簡短**，涵蓋四件事：**畫面重點／使用限制／畫面種類／畫面好不好**。電視新聞最重視畫面吸不吸引人，全靜態、沒有吸睛畫面就不是好素材，這點要讓編輯一眼看到。
  - 畫面種類實例：`(空拍圖)`／`(氣象圖)`／`(棚內解說)`／`(記者STAND)`／`(有google街景前後對比)`／`(共4張照片)`／`(有多張圖)`／`(白天)`／**`(資料畫面)`**
  - 使用限制實例：`(標來源)`／`(180天下架)`／`(可上網不下架)`
  - 畫面／聲音重點實例：`(炸瞬 無聲)`／`(畫面好!!)`
  - **資料畫面（舊稱 FILE／檔案）**（2026-07-31 使用者訂正）：通訊社介面的 **FILE／「檔案」**（庫存／重發／非當日新攝畫面）**一律改注記 `資料畫面`**，**禁止**在備註再寫 `FILE`、`檔案`、`File`。  
    ❌ `(大衛營 內閣會 FILE)`／`(特斯拉 上海廠 檔案)`  
    ✅ `(大衛營 內閣會 資料畫面)`／`(特斯拉 上海廠 資料畫面)`  
    摘要或 `畫面：` 段若描述畫面上的歷史影像，可用中性敘述，但**備註標記統一用「資料畫面」**。
  - **供稿來源標註：SNTV（2026-07-31）**：**僅** `AP5…`（體育）且本則 `Source:`／`Provided by: SNTV` → 備註**必含** `(SNTV)`（可並排，如 `(SNTV 詹姆斯轉隊)`）。**`AP4…` 禁止標 SNTV**。SNTV **可收、不排除**。列表扁平文字易把下一則 SNTV 徽章黏到上一則——見上文「列表文字黏標」。
  - **CNN Newsource：PKG／DONUT 長片標 SOT**（2026-07-31 使用者訂定）：詳情 **Footage Type** 為 **`PKG`** 或 **`DONUT`**，且**時長超過 1 分鐘** → 備註**必含** `SOT`（可並排其他詞，如 `(地方 海灘 SOT)`、`(第三方 睡眠危機 SOT)`）。  
    - ≤1 分鐘的 PKG／DONUT **不**標 SOT（短包／短甜甜圈當 VO 用即可）。  
    - 非 PKG／DONUT（如 raw VO、STILL、TAGS-only）**不**因有旁白就亂標 SOT。  
    - 此 `SOT` 寫在**第一個備註括號**內，與第二括號的 `(BITE)` **不同職能**：SOT＝整包可用成音／成稿感；BITE＝有可掐引言。兩者可並存：`(地方 SOT) (BITE) …`。

- **括號的半形／全形有分工，不可混用**（實測 109 個括號零反例）：
  - **半形 `()` ＝ 備註標記**（給編輯看的畫面／限制資訊）
  - **全形 `（）` ＝ 摘要內文**（譯名原文對照如 `（Patriot）`、單位換算如 `（約攝氏43度）`，依 [`00-寫稿通則.md`](00-寫稿通則.md)）

4. **未歸類的進「話題」**（清單最後一格）——但前提是**樣板上已有的格（如烏俄）必須先用對**，不能因為懶得開空格就把該進烏俄的丟話題。
5. **整份樣板必現**（本節上一小節，2026-07-31）：空分類也要放。

### 各站時間／時區（2026-07-31 訂正，必讀）

S2 時間窗一律以**台北時間（+08）**陳述與整併，但**各站介面顯示時區不同**——比對前必須先換算，**不可把畫面數字當本地時間**：

| 站 | 介面時間標記 | 換算成台北（+08） |
|---|---|---|
| **CNN Newsource** | **`GMT` / GMT+0**（例：`31 Jul 26 12:22 GMT`） | **+8 小時**（12:22 GMT → 台北 20:22） |
| **AP Newsroom** | 列表常顯示本地相對時間／站內時鐘（依帳號設定） | 以詳情 Arrival／Creation 為準，**不要假設＝GMT** |
| **Reuters Connect** | Details 常見 `Friday, July 31st, 2026, 19:15`（實務上與台北掃帶窗對得上；若見 `GMT`／`UTC` 字樣再另換） | 見標示；有時區字樣就換算 |

**CNN 換算口訣（不可再犯）**：

- 台北 **19:30–20:30** ⇔ Newsource **11:30–12:30 GMT**
- 台北 **15:13–19:30** ⇔ Newsource **07:13–11:30 GMT**
- 台北 **17:22–19:30** ⇔ Newsource **09:22–11:30 GMT**

❌ **禁止**：看到 Newsource `12:xx` 就當成台北中午、或以為「列表很新所以掃完了」卻其實只掃到 GMT 上午／只抓了最新可見 4–5 則。  
✅ **正確**：先把目標台北窗換成 GMT 窗 → 列表**漸進下捲**收集該 GMT 區間全部 ID → 再與狀態 JSON 差集。

> 2026-07-31 實錯：掃「至 20:30」時未把 Newsource 當 GMT 處理，導致窗內 CNN 幾乎漏掃；已補規則，之後每次 S2 必換算。

### RT 詳情頁 Previous／Next（‹ ›）連讀（2026-07-31 實測補強）

S2 或任何需**連掃多則 RT 素材**時：

1. 先開 **Video 全列表**（My Subscription ON、`all?media-types=vid` 或帶結果集的 `all?id=…&media-types=vid`）→ 點進**清單最上方／時間窗內最新一則**詳情。
2. 詳情頁上方／導覽列有 **Previous／Next**（介面常作 **‹ ›**，aria-label `Previous`／`Next`）——在**目前結果集**內切換，**不必每則回清單重點**。
3. **掃時間窗標準走法（2026-07-31 操作口訣）**：**從最新的素材進去 → 反覆按 Next（›）往時間更早收集** → 讀 Details 時間戳，**低於截止時間就停**。Previous（‹）是往更新／更新近。
4. 每一則用代碼（Edit No. → `RT{4碼}`）對狀態 JSON 做差集；已見過的只更新 `last_checked_checkpoint`。
5. ⚠️ **必須從「有前頁清單」的結果集進詳情**——只搜單支 `search=all:####` 或純 `/detail` **沒有結果集就沒有 ‹ ›**。進詳情後 URL 宜保留 `all?id=…&media-types=vid` 形態。
6. ⚠️ 這是**素材詳情頁內**的前後鍵，不是瀏覽器分頁切換，也不是清單頁的 Load more。
7. 列表**淺色項目＝已看過**（本 session 操作提示）；可跳過已淺色且已在庫存的 ID。
