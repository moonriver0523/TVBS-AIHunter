## 批次分立與整併（2026-07-30 使用者訂正，取代先前「每輪重寫」設計）

**核心原則：每輪只寫新東西，不碰累積的彙整結果；分類彙整只在整併時做一次。** 這是使用者確認的實務做法——晚班本來就是每批掃帶各自產出摘要、下班前才整併成一份晚班交接，不是邊掃邊維護一份持續更新的總表。

### 兩種節奏，職責不同

| | 批次擷取（每個檢查點都做） | 整併（同一個檢查點，緊接批次擷取之後） |
|---|---|---|
| 觸發 | 決策 2：排程 16/18/20/22/23 或人工加開 | 同一次觸發裡，擷取完接著跑；23:00 額外標記為**最終整併** |
| 做什麼 | 找新素材、寫三段式內容，**存進 JSON 的欄位**，不產生任何 txt；若掃到**已在庫且 `pending`** 的同則且稿已到 → 覆寫 `raw_entry` | 讀 JSON 裡**尚未整併**的項目，判斷大分類／中主題歸屬、處理同組相鄰，套三方比對保留人工編輯，寫出 `{MMDD}晚班交接.txt`。**最終整併另加「稿未到清查＋品質掃」**（下節） |
| 要不要判斷力 | 不用——是否已見過純靠代碼比對 JSON | **要**——「這則歸哪個中主題、要不要開新大分類」需要語意判斷；最終清查時還要判斷稿是否已到、摘要怎麼補、格式／可疑是否回站 |
| 觸碰範圍 | 只有這次新找到的素材（＋順手補到的 pending） | **增量**：上次整併後的新增／變動；**最終整併額外**：(1) 全部仍 `pending`／`(稿未到)`；(2) **品質掃命中的可疑／缺漏列**（見下） |
| 頻率 | 5 次（16/18/20/22/23） | 5 次；**每輪都做 pending 清查**（2026-08-03 起，見決策 4），23:00 為最終版（另加品質掃） |

⚠️ **2026-08-03（WP1）起，走 V2 執行層時本節的「三方比對／增量整併」已不適用**：晚班交接 txt 改由 `scripts/s2_render.py` 從狀態檔**全量渲染**，狀態檔是唯一真相源、人工不改 txt，`.snapshot.txt` 與 `diff3` 一併廢除，`compiled` 增量欄位也廢除。格式規則（三層骨架、素材行寫法、標記）仍以本檔為準，執行流程見 [`13b`](13b-S2-定時掃帶-v2省token.md) §2／§3。

**批次擷取不需要三方比對**：每次只是把新素材寫進 JSON 的欄位，不去改動任何已整併過的 txt 內容，沒有「舊版被覆蓋」的風險。三方比對只在**整併**時用——若某次整併後、下次整併前，有人工編輯過上一版 txt，下次整併要靠「比對現行 txt vs 上次機器版快照」保留那些編輯。

**大新聞即時可見（承接決策 4）不受影響**：決策 4 要的是「稿未到也要能看到」，這靠的是**JSON 裡的批次內容立即存在**（不必等整併），跟「有沒有分類彙整成正式三層庫存 txt」是兩回事。急件可以直接查 JSON，不用等下一個整併檢查點——或直接手動加開一次整併。

### 最終整併：稿未到清查＋品質掃（2026-07-31 但書，同日晚補品質掃）

**觸發**：**最終整併**（排程 23:00 定版，或使用者明確下令「最終整併／定版晚班交接／收班整併」）。中繼整併**不強制**跑全量清查／全量品質掃。

**目的**：
1. 避免定版晚班交接仍殘留「稿其實已到、庫存還寫稿未到」（實務：RT2333）。
2. 避免定版帶著**格式異常、明顯可疑、明顯缺漏**出廠——**先掃可疑，有命中才回站**，不是 100 則全回站（省 token／時間）。

**步驟**（在一般增量整併**之前或緊接其後、寫出定版 txt 之前**完成）：

#### A. 稿未到／pending 清查

1. **列清單**：狀態 JSON 全部 `script_status = pending`，**並** txt 字串掃 `稿未到`（雙保險）。
2. **逐則回查**（2026-08-03 起**優先走 `13b` §1a API 批次重查**——NS 一次查詢可重判整批、RT 用 Promise.all 打 /api/item；API 不可用才退回開詳情頁），看是否已有完整 SCRIPT／STORYLINE（非僅 shotlist／佔位）。0803 實例：52 則 NS pending 用 API 一次重判完，舊做法逐則點 Preview 約需 130 次呼叫。
3. **稿已到**：覆寫 `raw_entry` 為完整三段式（含畫面／BITE 或無BITE、**講者**、時長若可見）；備註**去掉**「稿未到」；`script_status → has_script`；整併**沿用既有 `category`**。
4. **稿仍未到**：維持 `pending` 與 `(稿未到)`，**不要**刪列。
5. **回報**：「pending 清查：N 已補／M 仍稿未到／（代碼）」。

> ⚠️ **「有稿」判準（2026-08-03 使用者訂案，兩點都是為了讓 pending 不再無限堆積）**
>
> **(1) 判準看內容不看標記字串**：有 `--LEAD IN--`／`--VO SCRIPT--` 當然算；**沒有這兩個標記、但有完整敘事段落**（成句的稿件文字，如 CNN 的 `CORRESPONDING SCRIPT` 區塊）**一樣算稿已到**。實例：0803 `WE-014SU` 有完整敘事卻缺標記字樣，嚴格抓字串會誤判成稿未到。
>
> **(2) 「本來就不會有旁白稿」的素材＝`has_script`，不是 `pending`**：只有 `--SUPERS--`／拍攝資訊的原始素材——國會聽證會 ISO／CLEAN AIR 長帶、政論節目裸 SOT 引言、字卡——**這類天生沒有通訊社旁白稿，等再久也不會有**。一律標 `has_script`，並在**第一括號備註寫明素材形態**（`ISO長帶`／`裸SOT`／`CLEAN AIR` 等），**不要**標 `(稿未到)`。
>
> ⚠️ **NS 兩類素材不採納，列表判讀階段直接排除（2026-08-03 使用者訂正，判準 08-03 晚實測確認為機械欄位）**：**不寫入 `add-batch`、不進狀態檔、不建 `needs-review` 殼**，掃到直接略過。
>
> **(a) 純音軌 —— `footageType === "AUDIO TRACK"`**：沒有獨立畫面內容，只有記者各地播出署名、頻道標籤這類配套聲軌（實例：`PY-04MO`「(TAGS) PACIFIC NORTHWEST INFERNO (4AMET)」、`PY-02SU`）。⚠️ 跟上一條「有畫面但沒稿」的 ISO／裸 SOT／CLEAN AIR **不是同一件事**：那些**有可用畫面**只是沒有旁白稿，音軌是**連畫面都沒有**，兩者判準不同，不要混為一談。
>
> **(b) 初稿佔位公告 —— `footageType === "GRAPHIC"` 且 script 含 `THIS IS NOT THE FINAL SCRIPT`**：這**不是一支可用的新聞帶**，是站方發的佔位公告，內文會明講最終版在哪一則、幾點更新。實例 `PRE-400aET`「PRELIM SCRIPT & EMBARGO INFO FOR 400amET PKG」，script 開頭固定寫 `***THIS IS A PRELIMINARY SCRIPT FOR THE 4:00amET PKG*** / THIS IS NOT THE FINAL SCRIPT. / ***THE FINAL EMBARGOES AND SCRIPT WILL BE IN ITEM PY-03MO AT 4:00aET***`。
> - **代碼形態**：這類 id 常是 `PRE-` 開頭（如 `PRE-400aET`），但**不要只靠代碼判**——以 `footageType` ＋ script 字樣為準。
> - ⭐ **它點名的最終版 ID 要記下來**（上例的 `PY-03MO`）：那才是真正要收的素材，下一輪掃到時正常收錄。可寫進當輪回報，不必進狀態檔。
>
> 錯誤示範（0803 實錯，NS pending 一度堆到 59 則的主因）：把 26 則聽證會長帶與裸 SOT 全標 `pending`，每輪新增十幾則、永遠沒有一則能被清掉——因為它們等的那份稿根本不存在。
>
> ⚠️ **AP 初稿 `++PRELIMINARY SCRIPT++` ＝ 素材照收、標 `pending`，下一輪回頭補正式稿（2026-08-04 使用者訂案）**
>
> **跟上面 NS 的 (b) 佔位公告完全不同，不要混為一談**：NS 那種是「站方發的公告」，本身**不是新聞帶**、要整則排除；AP 這種是**真的素材**（實例 `AP4676355` 伊朗外交部簡報，有畫面也有 SOUNDBITE），只是稿子還是初稿版、之後會出正式稿。
>
> - **判準**：AP 詳情的 `script`（`script.nitf`）**開頭**寫 `++PRELIMINARY SCRIPT ++`。⚠️ AP **沒有**對應的機械欄位可判（不像 NS 有 `footageType`），只能掃這個字樣——所以**只認開頭**，不要對全文 `find`，內文順帶提到不算。
> - **處置**：素材照常寫進 `add-batch`，`script_status` 標 **`pending`**、第一括號備註加 **`(初稿)`**。內容照初稿版正常寫三段式（有 BITE 就寫 BITE，不要因為是初稿就留白）。
> - **下一輪 pending 清查時回頭重查**：正式稿到了就照 A 節第 3 步覆寫 `raw_entry`、拿掉 `(初稿)`、轉 `has_script`。
> - **不會無限堆積**：正式稿一定會出，跟「等一份根本不存在的稿」是兩回事，不違反上面那條錯誤示範的精神。若連續數輪都沒等到，照一般 pending 處理（維持 `pending`、不刪列）。

#### B. 格式異常／明顯可疑／缺漏掃 → 有則回站補

**先機器＋規則掃整份定版 txt（與必要時 JSON `raw_entry`）**，只對**命中列**回外電網站核對並修 `raw_entry`＋txt。中繼整併不強制；使用者單獨下令「抽查／掃可疑」時可只做 B 而不做 A。

| 類型 | 怎麼抓（例） | 命中後 |
|---|---|---|
| **格式異常** | `(BITE)` 與 `無BITE` 矛盾；有 `▎BITE：` 無 `(BITE)` 或相反；缺 `▎畫面：`；結尾既非 `無BITE` 也非 `BITE：`；第一備註寫了 `BITE`；第二括號不是 `(BITE)` 卻重複備註內容；備註仍寫 `FILE`／`檔案`（應 `資料畫面`）；素材行出現 `GMT`；**來源／格式／狀態標在半形備註與摘要全形 `（）` 重標**（`SNTV`／`CCTV`／`資料畫面`／`直式`／`稿未到`＋`script待補` 等）；素材行出現 **`（列表摘要）`** 等操作備註 | 回站對 shotlist／script 改對格式與內容；重標則刪摘要側重複、必要時併限制語進第一備註 |
| **明顯缺漏** | `▎BITE：「…」` **無講者**（違反講者規則）；摘要／畫面寫「待補／依shotlist／模板先上／early script」卻**已** `has_script`（應完整）；`片未到` 但稿已齊時可保留片況標記、內容仍應完整 | 回站補講者／完整摘要畫面 BITE |
| **明顯可疑** | 數字／單位／開收盤用語前後矛盾；同一代碼 txt 與 JSON 不一致；同一代碼重複列；摘要與代碼來源常識嚴重不符（例：標無BITE 但摘要大段引用受訪） | 回站核原文後再改；**不確定就不改**，回報「待人工」 |
| **非缺漏** | 行尾無 `▎MM:SS`（**允許省略**，不溯及）；空大分類標題保留（樣板要求） | **不**當錯誤、不為此回站 |

**回站修完**：同步 JSON `raw_entry`（與必要時 `script_status`）；品質修過的列若已 `compiled`，視為 `raw_entry` 變動，整併沿用 `category` 重排該則。

**回報**：「品質掃：X 則命中／Y 則已回站修正／Z 則仍待人工（代碼＋原因）」。

**不做的事**：

- **不**為品質掃去**無差別**重掃當日全部已 `has_script` 的素材（只掃命中／可疑）。
- 品質掃（B）仍**不強制**中繼輪全量做——只有 pending 清查（A）2026-08-03 起改為中繼輪也要主動全量做（見決策 4）。
- 不回溯改更早日期的舊晚班交接檔。
- 不把「可選省略」（如時長）當錯誤。

## 隔夜續掃：接續晚班交接掃到白天（2026-08-02 使用者定案；2026-08-04 固定排程定案）

23:00 晚班定版**不是收工**——同一份 `{MMDD}晚班交接.txt` 繼續往隔天白天掃，讓早班一開檔就看得到整夜進的素材。

**標記邊界**（`mark_for()` 判準，只認「實際開掃時間」，不做任何「下一個整點」換算——這條 2026-08-03 深夜訂正過的原則維持不變）：16:00–23:00（含）＝`△`；隔天 07:00 前＝`▲`；07:00–09:00＝`■`；09:00–14:00＝`◆`。

**時刻是原則不是鐵律**：使用者可以當天隨時因應實際狀況加開、跳過、或調整某一輪的時間，不需要每次都回來改這份表；`mark_for()` 判斷的是**素材實際被收進來那一刻的時鐘時間**，不是排程表上該輪「應該」是幾點。

> 🎫 **排程間隔全部超過 1 小時，所以 NS 需要「保活」（2026-08-04 訂案）**：NS（CNN Newsource）的登入態是**1 小時滑動時效**，沒有任何長效 cookie 撐著（AP 有 7 天、RT 有 23 小時，NS 一個都沒有），過期就只能人工重登。而上表每一段間隔都 > 1 小時（23:00→01:00 隔 2hr、01:00→04:30 隔 3.5hr、13:00→隔天 16:00 隔 3hr），等於每輪開工 NS 幾乎必定已過期。
> **做法**：掃帶 agent 在兩輪之間的等待期，距上次接觸 NS 接近 **58 分鐘**時，順手開一次 NS 頁面續期（1–2 次工具呼叫，不查清單不打 API）。
> ⏱️ **配套：每輪掃描順序固定 `NS → AP → RT`（2026-08-04 使用者訂案）**。NS 排第一站，「上次接觸 NS」就等於整點開工那一刻，續命時刻用整點推算即可；NS 若排最後，實際打開的時間會隨當天素材量浮動（16:05 或 16:40 都可能），基準點每輪都在飄、算不準。
> ⛔ **必須由掃帶 agent 自己做，不可另開獨立 agent／排程**——Playwright 只有一個 persistent profile，另開行程會跟掃帶互鎖（0803 曾害 RT 空窗八小時）。詳細機制、實測證據與失敗處置見 [`13b`](13b-S2-定時掃帶-v2省token.md) §1a-3「NS 登入態」與「NS 保活」兩節。

每輪一樣是「批次擷取 → 整併寫檔」，做法與晚班的中繼整併相同（見上節），**不另開檔、不另開狀態 JSON**，續用當晚那一份。

⚠️ **檔名不換日**：01:00 之後掃到的素材仍寫進**當晚**那份 `{MMDD}晚班交接.txt`（MMDD＝晚班起始日）。8/2 晚班開的 `0802晚班交接.txt`，8/3 凌晨到早上的續掃全部續寫進去，**不要**在 8/3 另開 `0803晚班交接.txt`。13:00 那輪之後到下一個 16:00 之間沒有排程，是刻意的空檔。

### 素材編號前的時段標記

**每一則素材的代碼前都要加一個全形符號＋空格**，讓編輯一眼分出哪些是新的、也方便快速瀏覽時定位素材：

```
△ RT2650 (23:00 前晚班既有素材) ▎…
▲ RT2681 (希臘野火 空拍) ▎摘要…▎畫面：…▎無BITE。
▲ 🔴 IN-23SU (希臘直升機相撞) ▎…　←重大素材：時段標記後、代碼前加 🔴
■ AP1234567 (東京地鐵事故) (BITE) ▎摘要…▎畫面：…▎BITE：…▎01:12
◆ RT2699 (國會聽證追蹤) ▎摘要…▎畫面：…▎無BITE。
△ CNN 16:14:30　（主播）
△ NHK 16:53:50-16:56:38　（記者）
```

| 符號 | 時段 | 意義 |
|---|---|---|
| `△` | 23:00（含）前 | 晚班既有，16:00～23:00 五輪都算晚班有人值班（23:00 是下班前最後一輪） |
| `▲` | 23:00–07:00 | 無人值守新增（01:00、04:30 兩輪） |
| `■` | 07:00–09:00 | 晨班新增（07:00、08:00 兩輪） |
| `◆` | 09:00–14:00 | 早班新增（10:00、12:00、13:00 三輪） |

> ⚠️ **每則都要有標記，包含 `△`（不用「無標記」表示既有素材）**：三種以上標記齊全、格式統一，快速瀏覽時每一行起手都一樣寬，好找素材。**側錄行（CNN／NHK）同樣要標**，寫在來源之前：`△ CNN 16:14:30　（主播）`。
>
> 🔄 **`■` 原本是 `●`，2026-08-04 使用者訂正改用方塊**（理由：`●` 與其他圓形標記——`🔴` 重大、`🟤` 已做過——擠在同一個行首位置容易看混）。
> **舊資料不回頭改**（使用者訂案）：0803 以前的晚班交接整份仍是 `●`，維持原樣不重新渲染。
> ⚠️ **所以腳本的解析端必須永遠認得 `●`**——`s2_validate.MARK_RE`／`s2_render.MARK_RE` 都保留了它，`MARKS` 也留著 `●=07:00–09:00 新增（舊符號）` 的圖例對照。**這是長期相容分支，不是過渡碼，不要當成殘留清掉**：拿掉的話舊檔那些 `●` 行會 `LINE_RE` 不 match，從品質掃與檔頭統計裡**靜默消失**（不報錯、只是數字少算，`△` 上線時已經踩過一次）。實測 `Archive/20260803/0803晚班交接.txt` 的 56 行 `●` 仍正常計入 362 則統計、品質掃 0 命中。

- ⚠️ **符號歸屬看「這則是哪一輪掃進來的」，不是看素材的上站時間**。同一輪掃進來的素材標記一致，不必逐則去查發稿時間。
- ⚠️ **標記一律看實際開掃時間，不做「下一個整點」換算**——交件時間可以算下一個整點方便排程回報，但那跟標記是兩件事，不連動。
- 標記**只加在素材行行首**，加在代碼之前、空一格。三段式其餘結構完全不變。
- 側錄段落（[`14-S2b`](14-S2b-側錄轉譯摘要.md)）若在隔夜時段補進來，比照加同一組標記。⚠️ **但隔夜輪次現階段不跑側錄篩選**（2026-08-02 定案：23:00 之後不會有新側錄，跑了空轉）——標記規則先寫著當**預留接口**，日後要開啟時流程與格式都不必再改，見 `14-S2b` 的「時段範圍」。
- `scripts/s2_validate.py` 已支援：品質掃與檔頭統計都會先剝掉標記（`△▲■◆`）再比對，標記不影響任何既有檢查；另外會檢查「用了標記但檔頭沒圖例」。**檔頭「隔夜續掃 N 則」只計 `▲`／`■`／`◆`，`△` 是基底不計入。**

## 狀態 JSON 欄位設計（2026-07-30 定案）

每則素材一筆，欄位分兩組：**批次擷取寫的**（找到當下就填）與**整併寫的**（分類彙整時才填）。

| 欄位 | 誰寫 | 內容 | 用途 |
|---|---|---|---|
| `id` | 批次擷取 | 素材代碼（`RT0595`）或側錄識別（`CNN 151328`） | 唯一鍵，判斷「是否已見過」的依據 |
| `source` | 批次擷取 | **封閉字彙，只能用這六個**：`AP`／`RT`／`NS`／`YT`／`SIDE_CNN`／`SIDE_NHK`。⚠️ **不得自創同義值**（2026-08-02 訂正，0802 實錯：同一個 Newsource 同時出現 `NS` 與 `CNN_newsource` 兩種寫法，per-source 統計與差集全亂）。`NS`＝CNN Newsource，與檔頭統計用的縮寫一致 | 追溯來源、統計用 |
| `first_seen_checkpoint` | 批次擷取 | 首次抓到的檢查點，**格式統一為 `{MMDD}-{HHMM}`**（`0802-1600`）。⚠️ 2026-08-02 實錯：同一份檔案混用 `16:00`／`r1-0802-1400-1500`／`19:00-21:00` 三種寫法，無法比對排序 | 追溯素材何時進系統 |
| `last_checked_checkpoint` | 批次擷取（每次重新確認都更新） | 最近一次確認仍存在的檢查點 | 判斷素材是否過期／該不該繼續追蹤 |
| `script_status` | 批次擷取 | `has_script` ／ `pending`（對應決策 4 的「有稿／稿未到」） | 整併時判斷要不要標 `(稿未到)` |
| `raw_entry` | 批次擷取（`pending` 轉 `has_script` 時**覆寫**） | 三段式內容本身（代碼＋備註＋摘要＋畫面＋BITE），批次擷取當下就寫好。**含行首的時段標記（`△▲■`）與重大標記（`🔴`）**（2026-08-03 訂案：與 txt 行完全一致，整併照抄不再加工；`s2_validate` 比對時會自行剝掉標記） | 整併時的**唯一輸入來源**——整併不重新生成內容，只做分類與排版 |
| `compiled` | 整併寫入 | `null`（未整併）／上次整併的檢查點時間 | **增量整併的依據**：整併時只挑 `compiled` 為 `null`，或 `raw_entry` 在 `compiled` 之後又被改過（`script_status` 從 pending 轉 has_script）的項目來處理，其餘直接沿用上一版 txt 裡已經排好的內容，不重新判斷分類 |
| `category` | 整併寫入 | `{大分類, 中主題}` | 一旦分類過就記住，避免下次整併重新判斷同一則該歸哪裡；也是「同組相鄰」排版時的依據 |

⚠️ **`items` 只放素材，不准塞待辦**（2026-08-02 訂正）：0802 實錯——`items` 裡出現 `SCRIPT-TODO`、`SCRIPT-TODO-2`、`CATEGORY-FIX-1`、`FORMAT-FIX-1`、`RT-MISC-20-30`、`AP-MISC-20-30`、`CEUTA-DEATH-TOLL-UPDATE` 等 8 筆**假素材**（拿 items 當備忘錄用），害 per-source 統計出現 `?` 分類、`pending` 數字灌水。每一筆 `id` 都必須是**真實素材代碼**；agent 自己的待辦寫在回報訊息裡，不進狀態檔。

**這組欄位怎麼讓整併變成增量而不是全量**：整併時，一則素材只會落在三種狀態之一——

1. **全新**（`compiled` 為 `null`）→ 要判斷分類、寫進新的 `category`，成本全付
2. **稿到了但已整併過**（`raw_entry` 在上次 `compiled` 之後被覆寫，通常是 pending→has_script）→ **沿用既有 `category`**，只重新排版這一則的內容，不必重新判斷分類
3. **沒變化**（`compiled` 已存在且 `raw_entry` 沒變）→ **直接照抄上一版 txt 裡的內容**，完全不進 LLM

只有第 1、2 類真的要花 token；第 3 類（多數素材，一旦分類過就不會再變）幾乎零成本。這是「增量整併」在數字上比「每次整併都全量重讀」省的地方。

> ⚠️ **這組欄位不能直接拿去當 Dashboard／Aigent-Fable 的 schema**（2026-07-30 使用者問過，答案是不能）。原因：
> - `raw_entry` 是**預先渲染好的顯示字串**（三段式黏在一起），Dashboard 要的是拆開的結構化欄位（標題／摘要／畫面描述／BITE 各自獨立）才能篩選查詢——這正是 Aigent-Fable 藍圖的 `ai_enrichments`／`asset_bites` 已經做對的事，我這裡是把它們黏回去，是退步不是延伸。
> - `compiled` 欄位的存在理由是「沒有即時資料庫」；有了 Dashboard，查詢即時發生，這個欄位跟整個增量整併機制應該直接消失，不是被繼承。
> - `id` 把來源與代碼黏成一個字串，藍圖是分開的 `source_id`／`source_ref`。
> - **唯一值得回饋的是 `category`（大分類／中主題）**——藍圖的 `assets` 表目前完全沒有主題分組概念，這是這輪設計挖出來、藍圖之後可能該補的東西，方向是反過來的。
>
> 這份 JSON 從一開始就是**用完即丟的過渡工具**（見 `common/12`：「Dashboard 建好前用純文字清單暫代」），不是 Dashboard schema 的草案，不要在它身上做超出「撐到 Dashboard 蓋好」以外的擴充規劃。

|---|---|

| 2 | `時間窗：{YYYY-MM-DD} {起}–{訖}（約Xhrs）`——起訖之間用**全形連接號 `–`**；時數取整數小時 |
| 3 | `收錄外電共{N}則（AP X則／RT X則／NS X則[／其他 X則]）[；隔夜續掃 ▲ X則／■ X則／◆ X則]`——`NS` 指 CNN Newsource；非 AP／RT／NS 的**通訊社／網址素材**（YouTube 等）併入**其他**，其他為 0 時該段省略。⚠️ **CNN／NHK 側錄段落完全不計入**，見下。隔夜續掃那半段只列出實際有的標記（0 則的標記不印） |
| 4 | `標記：△=23:00 前既有　▲=23:00–07:00 新增　■=07:00–09:00 新增　◆=09:00–14:00 新增`——素材行的時段符號對照圖例，中間用**全形空格**分隔。只要檔案裡出現任何 `△`／`▲`／`■`／`◆`，這行就**必須有**（2026-08-03 起素材一律帶標記，所以這行實務上一定有），見「隔夜續掃」節 |
| 5 | **（僅有重大素材時才有）** `🔴 重大：{標記}{代碼} {一句話}`——**重大提醒行**，放在檔頭**最後**、每則一行、**最多 3 行**。見下節 |

0802 晚班交接

### 重大提醒行（2026-08-03 使用者訂案）

**問題**：一份近百則的晚班交接裡，重大突發跟例行素材長得一模一樣，都是三段式的一行，**編輯得自己掃完整份才會發現今天有什麼非處理不可的東西**。0802 深夜 `IN-23SU`（希臘消防直升機撲滅野火時空中相撞、有事發瞬間畫面）就是實例——素材已在庫，但沒有任何機制讓它跳出來。

**做法**：檔頭最後補**重大提醒行**，一則一行：

```
🔴 重大：▲ IN-23SU 希臘消防直升機撲滅野火時空中相撞，有事發瞬間畫面；1人傷、第二架機組下落未明
```

| 項目 | 規則 |
|---|---|
| **位置** | 檔頭**最後**（圖例行之後、第一個 `======` 之前）。落到大分類區塊裡＝錯，`check` 會抓 |
| **格式** | `🔴 重大：{標記}{代碼} {一句話}`——`🔴` 半形空格接 `重大：`；`{標記}` 沿用素材行的 `△`／`▲`／`■`；`{代碼}` 必須是**正文真的存在的素材代碼**（`check` 會比對，找不到＝命中） |
| **一句話怎麼寫** | 事件 ＋ **為什麼重大／畫面亮點**，約 40 字以內。不是摘要的複製貼上——摘要講「發生什麼」，這裡要講「**為什麼你現在就該看這則**」（獨家事發畫面／死傷規模／台灣關聯…） |
| **上限 3 行** | 全都標重大＝都不重大。同時有 4 件以上時只留當班最該先處理的 3 件，其餘靠正文分類 |
| **禁止** | 操作備註（`待查`／`待人工`／`未開詳情`）；只有敘述沒有代碼；同一事件標兩行（取最完整的那則代碼） |
| **正文也要標**（2026-08-03 訂案） | 檔頭點名的那則，**正文素材行也要帶 `🔴`**——位置在**時段標記之後、代碼之前**：`▲ 🔴 IN-23SU (…) ▎…`。行首對齊不變（時段標記仍固定第一位）。檔頭有、正文沒有＝漏，`check` 會抓 |
| **正文 🔴 標過就永久保留**（2026-08-03 訂正） | **檔頭的重大提醒行每輪汰換**（新的大事進來、舊的退場，上限 3 行）；**但正文素材行的 `🔴` 一旦標了就留著，之後每一輪都不准拿掉**。所以「正文有 `🔴`、檔頭已經沒有它」是**正常狀態不是錯**，`check` 不會抓這個方向 |

> **為什麼正文也要標**：檔頭只告訴編輯「今天有這幾則重大」，但一份近百則的交接檔裡，編輯還是得自己往下找那一行在哪。正文帶 `🔴` 就能直接掃到。
> **為什麼標過不拿掉**：檔頭是「當下最該處理的前 3 件」，會一直換；正文的 `🔴` 是「這則素材曾被判定重大」的永久註記——凌晨標的重大素材，早班翻整份檔時還是該一眼看到，不能因為檔頭換人了就消失。
> ⚠️ 側錄行（CNN／NHK）不標 `🔴`——重大提醒只針對通訊社素材行。
> **例外（2026-08-19 使用者訂）**：側錄內容涉及臺灣時，經使用者當場明確下令，
> 該則側錄正文可以標 `🔴`，位置與寫法比照通訊社素材行（時段標記之後、代碼之前）。
> 這條例外**只開放「使用者指名」這一種情境**——沒有使用者當場下令時，agent
> 仍不得自行判斷幫側錄行標 `🔴`／`🟡`／`🟤`，預設維持「側錄不標」不變。

### 🟡 次級重大：重大、但沒擠進檔頭（2026-08-05 使用者訂案）

> 📅 **上線範圍：0805 新開的晚班交接起生效，0804 以前不追溯**（使用者訂案）。已定版的舊檔不重新渲染、不回頭補標——那幾天本來就一則都沒標過，沒有東西要回溯。
> 🎨 符號一度用 `🟠` 橘圓（同日稍早），使用者反映與 `🔴` 對比不夠明顯，當天改為 `🟡`。⚠️ 不要再換回圓形色系裡對比更弱的顏色——這個標記的用途就是讓編輯一眼分出兩級輕重。

**兩層是為了解開一個結構性綁架**：檔頭只有 **3 行上限**，但一晚常有十幾件重大事件（0803 實測 15 件）。單一層級下，agent 判斷「這則排不進前三」時會**連正文標記一起放棄**——0804 整晚 164 則只標了 1 則 🔴，而當晚至少有瓜地馬拉火山噴發、休達邊境死亡升至 75 人、黑海無人機襲 7 死等明顯該標的。**標 🟡 不必宣稱自己是今天前三**，門檻的綁架就解除了。

| 標記 | 語意 | 檔頭 | 生命週期 |
|---|---|---|---|
| `🔴` | **曾進過檔頭**的最高層級重大 | 有（或曾有） | **永久保留**，檔頭汰換後仍是 🔴，**不降級** |
| `🟡` | **重大，但沒擠進檔頭前三** | 無 | **永久保留**，同樣標了就不拿掉 |

- **兩者互斥**：`🟡` 後來升進檔頭就改標 `🔴`；不會同時掛兩個（render 若讀到兩個都寫，取較高層級的 `🔴`——降級會讓「曾進過檔頭」這個永久註記憑空消失）。
- **位置**：時段標記之後、`🟤` 之前、代碼之前 —— `▲ 🟡 🟤 IN-23SU (…) ▎…`。
- **誰來標**：**agent 判斷**，兩層都是。判準沿用下方「什麼算重大」四條——差別只在「要不要占用檔頭那 3 個名額」。⚠️ **拿不準就標 `🟡`**：它沒有名額限制，漏標的代價遠大於多標。
- 🇹🇼 **跟臺灣有關的一律至少 `🟡`**（2026-08-09 使用者訂）：只要素材內容涉及臺灣
  （漢光演習、國軍、臺海、兩岸、我國政要、臺灣廠商／社會事件等），**不必再判斷夠不夠重大，
  直接給 `🟡` 保底**；視情況重大再升 `🔴`。
  **理由**：這是臺灣的電視台，外電裡出現臺灣本來就是稀缺、編輯一定會想看的素材，
  但它常常在國際新聞的量尺上「不夠大」而被漏標——判準改成**題材保底**、不走重大性判斷，
  就不會再漏。⚠️ 這條**優先於**下方「什麼算重大」四條，兩者衝突時以本條為準。
- **圖例**：當份有用到 `🟡` 才印 `🔴=重大　🟡=次重大`，沒用到不印。
  ⚠️ 用字**與網頁版篩選 chip 一致**（2026-08-09 使用者要求）——同一件事兩種說法，
  編輯在 txt 與網頁之間切換會以為是兩種標記。
- ⚠️ 側錄行（CNN／NHK）同樣不標。

> ❌ **不要改用機械偵測自動標 `🟡`**（2026-08-05 已實測否決）：拿 0803 那 25 則真正的重大當標準答案，關鍵字＋傷亡數字偵測器**召回只有 20%（5/25）**——漏掉川普對伊「最後機會」、華州野火 700 棟燒毀、古巴全國大停電、翁山蘇姬「生還證明」等，因為**重大是「意義」問題不是「傷亡關鍵字」問題**；而且它另外標出的 24 則跟原本那批交集只有 5，等於是**另一種訊號、不是補漏**。機械偵測最多只能當弱提示，不能取代判斷。

### 🟤 已播標記：本台已經做過的素材（2026-08-04 使用者訂案）

**語意**：這則新聞**本台已經做過了**。⚠️ **但素材仍照常摘要入庫、留在庫存裡**——後續發展可能還要再做，`🟤` 只是把優先度降下來，讓編輯一眼略過已處理的，**不是「不要收」、也不是「可以刪」**。

| 項目 | 規則 |
|---|---|
| **符號** | `🟤`（U+1F7E4 棕圓，2026-08-04 使用者選定）。與 `🔴` 同一系列、寬度一致，色調沉、視覺上比 `🔴` 弱，符合「已處理、優先度降低」的語意。⚠️ **一度用過 `⚪` 白圓，實際畫面上辨識度不佳已換掉**；也不要改用空心圓 `○`／`◯`——圓形符號容易與其他標記混淆（`●` 就是因此在 2026-08-04 被換成 `■` 的） |
| **位置** | **時段標記之後、`🔴` 之後、代碼之前**：`▲ 🔴 🟤 IN-23SU (…) ▎…`。兩者**可以並存**（重大素材本台已做過，但還有後續） |
| **誰來標** | ⛔ **只有使用者下令才標，agent 不得自行判斷**——外電網站不會知道 TVBS 播了什麼，這是純人工資訊。性質同 `set-alert`（重大提醒行） |

| **會不會被清掉** | 同 `🔴`，標了就留著，除非使用者明講要取消 |

> **為什麼還要入庫**：晚班交接是給編輯看的**庫存**，不是待辦清單。已經做過的新聞常常會有後續（傷亡數字更新、官方回應、追蹤報導），素材留著才調得到；直接不收等於後面要重找一次。
> ⚠️ 側錄行（CNN／NHK）同樣不標 `🟤`——標記只針對通訊社素材行。

**什麼算重大**（符合任一即可，拿不準就**標**——漏標的代價遠大於多標）：

1. **重大傷亡／災難／攻擊事件**，且**我們手上有第一手事發畫面或關鍵現場**。
2. **國際級突發**的當日首出素材：戰事開打／停火、元首級人事變動、重大政經衝擊。
3. **與台灣直接相關**的突發（台灣人傷亡、兩岸軍事動態、台廠重大衝擊）。
4. **使用者當場指名**的素材——不必自行判斷，直接標。

**什麼時候撤掉**（每次整併重評，不是標了就長在那）——⚠️ **以下三條只講「檔頭那行」；正文素材行的 `🔴` 標過就永久保留，任何一輪都不准拿掉**（2026-08-03 訂正）：

- 事件已成當日主線、正文已有完整一組素材並各自分好類 → 撤掉，改由分類本身承擔。
- 續報已取代原素材（有更完整的一版）→ 換代碼，不要兩行並存。
- 隔日換檔（新的 `{MMDD}晚班交接.txt`）→ 不繼承，重新評。

**腳本支援**（`scripts/s2_validate.py`）：

```
# 新增／取代重大提醒（可重複給多個 --alert，最多 3 則）
python scripts/s2_validate.py stats {MMDD}晚班交接.txt --window "…" \
    --alert "▲ IN-23SU 希臘消防直升機空中相撞，有事發瞬間畫面；1人傷、第二架機組下落未明"

# 撤掉全部重大提醒
python scripts/s2_validate.py stats {MMDD}晚班交接.txt --window "…" --clear-alerts
```

- ⚠️ **不給 `--alert` 時，`stats` 會自動沿用檔內既有的重大行**。因為檔頭每輪整併都要重算覆寫，若不沿用，一次例行 `stats` 就會把上一輪標好的重大行洗掉——這是設計上刻意的保險，不要改成每次重生。
- `check` 會抓五種錯：代碼在正文找不到、沒寫代碼、超過 3 行、行落在檔頭以外，**以及檔頭點名了但正文那行沒標 `🔴`**。⚠️ **反向（正文有 `🔴`、檔頭沒有）不算錯**——那是檔頭汰換後的正常狀態。
