二、AP 配方
────────────────────────
1) 清單：POST https://api.newsroom.ap.org/v1/nrsearch/search/topic
   headers: Content-Type: application/json ＋ credentials:'include'（cookie 驗證）
   body 範例（照 /home Latest 頁實際發出的請求；TopicId 是 Latest 主題的 id，
   可從 GET /v1/topics/get-topics?location=latest,top 拿）：
   {"SearchType":"keyword","PageNumber":1,"PageSize":16,"MediaTypes":["video"],
    "TopicId":"{latest主題id}","isTopicSearch":true,"ProductGroup":"","language":"",
    "digitizationType":null,"isSemanticItemIdSearch":false,"Semantic":null,
    "MyPlanSearch":false}
   回應：Items[]._source → itemid(32碼GUID)／editorialid(＝AP編號數字部)／
   friendlykey／title／headline／dateline／caption／renditions
   ⚠️ 待確認：用上述 body 直接重放時排序偏 relevance 抓到舊素材，正式使用前
   要先驗「重放的清單順序＝頁面 Latest 順序」；保險做法是照抄頁面當下發出的
   同一 request body（用 read/network 抓），不要自己拼。

2) 詳情：POST https://api.newsroom.ap.org/v1/nrsearch/search/item/details
   body: {"ItemIds":"{itemid}","mediaType":"video","IsNonSalable":false}
   回應含 STORYLINE＋SHOTLIST＋Restrictions＋editorialid 全文（實測 27KB）。
   ⚠️ ItemIds 逗號串多則實測失敗（回空），要一則一次——但可在同一次
   browser_evaluate 裡 Promise.all 打 N 則，工具呼叫仍只算 1 次。

三、RT 配方
────────────────────────
1) 清單（可續用 §1b DOM 直撈，或改 API）：
   POST https://www.reutersconnect.com/api/search-api?hash={hash}
   （hash 從當下頁面網路請求照抄，如 klwn20；同源 cookie 驗證）
   headers: Content-Type: application/x-www-form-urlencoded
   body（照抄實際請求即可）關鍵參數：
     content-api-filters=med://vid、cursorMark=*（翻頁用 nextCursorMark 回填）、
     limit=60、selected-facet-media-types=V、sort=ts、search-scope=:my-feed
   回應：transit 壓縮 JSON（欄位名只出現一次，後續用 ^N 參照，regex 直抓
   欄位值會漏）。含 editnumber／guid／headline／slug／duration／versioncreated／
   fragment(稿件前300字)／early-access-script 訊號。
   guid 本身就含 Edit No＋日期：newsml_RW{4碼EditNo}{DDMMYYYY}RP1。

2) 單則：GET https://www.reutersconnect.com/api/item/{guid}?hash={hash}&live=false
   guid 例：tag:reuters.com,2026:newsml_RW266702082026RP1:3（版次尾碼照清單 href 抄）
   同源 fetch＋credentials:'include' 即可，回應含完整 SCRIPT＋SHOTLIST＋
   Restrictions（實測 8KB，transit 格式）。
   建議組合：清單照 §1b DOM 直撈（已上線、順序保證）→ 新素材 guid 一次
   Promise.all 打 /api/item/ ×N → 免開任何詳情分頁、免等 8-9 秒。

四之二、待驗事項的驗證結果（2026-08-03 09:40 實測，尚未上規則）
────────────────────────
✅ 1. AP 清單排序：**照抄頁面 request body 重放 → 順序與 DOM 完全一致**
   （16 則逐一比對 itemid，sameOrder=true）。先前「偏 relevance 抓到舊素材」
   是我自己拼 body 造成的，照抄就沒問題。

⚠️ 2. AP 翻頁：**PageNumber 不可靠，不要用**。實測 PageNumber=2 + PageSize=16
   回了 100 筆、與第 1 頁零重疊，回應卻自稱 Page=2/PageSize=16（伺服器行為
   異常）。**可靠做法：固定 PageNumber=1，加大 PageSize**。
   TotalRows 約 10.7 萬，窗內素材用 PageSize 50–100 綽綽有餘。

   🔴🔴 2026-08-03 18:50 重大訂正（推翻上面「16/50/100/200 都精準」的說法）：
   **PageSize 絕對不可以「調小」**。同一個 body 只把 PageSize 從 16 改成 5，
   回傳的就從「當下最新素材」（2026-08-03T10:46）變成 2024–2025 年的舊素材
   （Afghanistan Earthquake Bereaved 2025-09、HZ US CES BOSCH 2024-01），
   排序整個換掉、且毫無錯誤訊息。調小會靜默把兩年前的素材當新素材收進庫存。
   → **一律照抄頁面的 PageSize=16**，要更多才往上加（50/100/200 已驗過）；
     永遠不要為了「只想看幾則」而調小。

✅ 3. AP TopicId 跨 session 穩定：兩次 session（08-03 凌晨與早上）都是
   `116e9ab7aa044476925398d731289267`，可直接沿用；但仍建議每輪從頁面
   實際請求照抄，成本只有一次 read_network_requests。

✅ 4. RT hash 跨 session 穩定：兩次 session 都是 `klwn20`，重放成功。
   注意這像是前端 build hash，**站方改版會變**，規則要寫「照抄當下頁面請求」
   而非硬編。

✅ 5. RT transit 抽取的機械做法（原問題：欄位名只出現一次、之後用 ^N 參照，
   regex 會只抓到第一則）→ **結論：不要用 regex 硬解清單**，分工如下：
   - **清單**：照 §1b DOM 直撈（已上線）拿 Edit No／href／狀態，順序有保證。
   - **Edit No 也可從 guid 機械推出**：`newsml_RW{4碼}` 那 4 碼即 Edit No
     （實測 `newsml_RW275603082026RP1:4` → Edit No 2756），可與 DOM 值互相
     校驗。
   - **單則詳情**：`/api/item/{guid}` 每個欄位在單則回應裡只出現一次，
     **第一次出現一定是字面值不是 ^N 參照，所以 regex 可靠**。實測 2 則
     （17.7KB／19KB）headline／SHOTLIST／SCRIPT／Restrictions 全抓得到。
   - ⚠️ 但 `editnumber` 在 item 回應裡結構較深、regex 抓不穩定
     （實測回 undefined）——**Edit No 一律以清單 DOM 或 guid 推導為準**，
     不要從 item 回應抓。
