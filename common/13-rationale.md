| 4 | 稿未到的素材 | **先進庫存、就地標記**：依 shotlist 寫一句摘要並標 `(稿未到)`，正常歸入分類；稿到後回頭換成完整摘要。理由：大新聞的畫面晚班會想馬上知道，不該因為稿未到就看不見。**後補節奏**：平時批次擷取若再碰到同則且稿已到 → 覆寫 `raw_entry`＋`pending`→`has_script`；**最終整併晚班交接時，必須清查 pending／「稿未到」並回站補齊**；**定版／收班整併還必須掃格式異常、明顯可疑、缺漏，有則回外電網站核對後修**（見下「最終整併：稿未到清查＋品質掃」）。⚠️ **2026-08-03 訂正（WP1 上線後）：中繼整併（16/18/20/22）也要主動全量重查 pending**，走 `13b` §1a API 批次重查（NS 整批一次、RT／AP 一次 `Promise.all` 打 N 則），不是舊時代逐則點頁面那種成本——**查完照規則直接覆寫，不必詢問使用者**；pending 為 0 就跳過，不必空跑。舊的「不強制、只能順手補」是 UI 逐則點擊時代的顧慮，API 批次重查上線後已不成立 |
| 5 | 庫存 txt 維護 | ⚠️ **2026-07-30 再訂正——批次分立，5 個檢查點整併**（使用者確認：實務上晚班本來就是這樣做，每批次掃帶的摘要先分立存放，收班前才整併成一份晚班交接）。**不是每輪重寫、也不是每輪跑三方比對**——每輪只把新找到的素材寫進 JSON，不碰、不重讀先前批次；三層分類與人工編輯的三方比對，只在**整併時**（16/18/20/22 中繼、23:00 最終，見決策 2）做，且靠 JSON 的 `compiled` 欄位做**增量整併**（只處理上次整併後的新增／變動，不是每次全量重算）。細節見下方「批次分立與整併」與「狀態 JSON 欄位設計」 |
| 6 | 大分類歸屬 | **照使用者的樣板**（見下節，順序照抄不重排）。**同時滿足兩格時一律放最前面那格**（2026-08-03 訂案，見「大分類歸位通則」）。不在清單上的歸「話題」；最上面的**機動格由使用者當天決定**，agent 不自行開 |

### Token 成本（2026-07-30，一晚 60–80 則量級，抓量級用非精確值）

以 70 則、16/18/20/22/23 共 5 個檢查點（每點約新增 14 則）試算：

| 項目 | 成本 |
|---|---|
| A. 展開 70 則詳情頁（每則 ~2,500 input） | input 175,000 |
| B. 5 個檢查點 × 3 站輪詢空轉 | input 42,500 |
| **整併×5（增量，只處理當次新增）** | input 6,300／output 6,300 |
| **合計** | input 223,800／output 16,800，加權當量 **≈ 30.8 萬** |

對照四種設計的成本量級：

| 設計 | 加權當量 |
|---|---|
| 每輪 LLM 重寫整份（最初誤判，20 輪） | ≈ 79 萬 |
| 每輪腳本渲染（機械式、無判斷力，20 輪） | ≈ 39.75 萬 |
| 批次分立、20 輪擷取＋整併 1 次全量 | ≈ 43.5 萬 |
| **5 檢查點、增量整併**（現行定案） | **≈ 30.8 萬** |

比最初設計省逾六成。兩個因素疊加：**檢查點從 20 降到 5**（B 項直接砍到 1/4）＋**整併走增量**（多數素材分類過一次就不再重付判斷成本）。若全量重算（每次整併都重讀全部 70 則），5 檢查點版本也還是約 38 萬，比 20 輪整併 1 次略省——可見**降低檢查點頻率**本身就是最大的省法，增量整併是疊加的第二層優化。

### 與範例①② 的差異（只登記，不自行調和）

樣板比範例①② 精簡，且切法不同：

- **樣板有、範例沒有**：關稅
- **樣板沒有、範例有**：以黎、伊波拉（財經、娛樂已於 2026-07-30 補回，中東亦已改回，見上）
- **改過名的**：範例的「伊朗」→ 樣板「美伊」；範例的「美國政治」拆成「美國」與「政治」兩格

範例①② 是 7 月中的實際產出，樣板是使用者現在給的版本，**以樣板為準**。「以黎」被併進「中東」（美伊以外的中東總匯），是切法改變不是遺漏；「伊波拉」屬機動題，本來就該用最上面那格。
