### Token 成本（2026-07-30，一晚 60–80 則量級，抓量級用非精確值）

以 70 則、16/18/20/22/23 共 5 個檢查點（每點約新增 14 則）試算：

| 項目 | 成本 |
|---|---|
| A. 展開 70 則詳情頁（每則 ~2,500 input） | input 175,000 |
| B. 5 個檢查點 × 3 站輪詢空轉 | input 42,500 |
| **整併×5（增量，只處理當次新增）** | input 6,300／output 6,300 |
| **合計** | input 223,800／output 16,800，加權當量 **≈ 30.8 萬** |

對照四種設計的成本量級：

| 設計 | 加權當量 |
|---|---|
| 每輪 LLM 重寫整份（最初誤判，20 輪） | ≈ 79 萬 |
| 每輪腳本渲染（機械式、無判斷力，20 輪） | ≈ 39.75 萬 |
| 批次分立、20 輪擷取＋整併 1 次全量 | ≈ 43.5 萬 |
| **5 檢查點、增量整併**（現行定案） | **≈ 30.8 萬** |

比最初設計省逾六成。兩個因素疊加：**檢查點從 20 降到 5**（B 項直接砍到 1/4）＋**整併走增量**（多數素材分類過一次就不再重付判斷成本）。若全量重算（每次整併都重讀全部 70 則），5 檢查點版本也還是約 38 萬，比 20 輪整併 1 次略省——可見**降低檢查點頻率**本身就是最大的省法，增量整併是疊加的第二層優化。
