# 子系統地圖

> **這是一份地圖，不是規則。** 它只說明「目前這些文件分別屬於哪個子系統」，不改變任何流程的內容，也**沒有搬動任何檔案**——所有文件仍在原本的 `common/`／`reuters/`／`ap/`／`cnn/`／`production/` 位置。
> 目錄重構列為待辦（見 `TODO.md`），確定後再搬。

## 為什麼需要這份地圖

**一條規則 ≠ 一個子系統。** 現在的目錄是按**來源**切的（`reuters/`／`ap/`／`cnn/`），但子系統是按**動作**切的，兩者垂直交叉，所以同一個動作被拆散在不同資料夾：

- 「搜尋素材」＝ `reuters/01` ＋ `ap/01` ＋ `common/11` 輸入模式 B 的 CNN 搜尋框 ＋ 模式 C 備援來源 → 一個子系統、四處文件
- 「掐 BITE」＝ `common/07` ＋ `cnn/02` ＋ `reuters/03`（掐 SO ＝ 掐 BITE 再加剪片上傳）→ 一個子系統、三份文件
- 反過來 `common/01`／`02`／`08` 不屬於任何子系統，是所有子系統共用的地基

**判準**：子系統 ＝ 可以獨立被呼叫、有明確輸入與輸出、跑完會產出交付物。
**來源差異（RT／AP／CNN／YouTube／DVIDS…）不構成子系統**，那是同一個子系統底下的 adapter。

> 命名（S1–S9）為 2026-07-30 暫定，之後可調整。

## 主線順序（2026-07-30 使用者訂正）

```
S2  通訊社網站輪詢 ─┐
                    ├─▶ S3 入庫（庫存） ──AI 依議題整理──▶ S4 rundown 稿單
S2b 側錄轉譯摘要  ─┘             ▲                                │
                                 │ ①先查庫存          S4b 分派給記者
                                 │                              │
                        S4c 補充素材搜集 ◀──缺素材時人工發動──┘
                        （②搜尋 ③備援）    │
                                            ▼
                        S5 編號 ──▶ S6 下載 ──▶ S7 掐BITE ──▶ S8 寫稿 ──▶ S9 製片
```

**S4c 是人工發動的側支，不是主線的一站**：分派後若判斷某則稿子素材不足才啟動，取材優先序是**①既有庫存 → ②通訊社搜尋 → ③備援來源**，找到的素材接回 S5／S6。
S1 手動搜尋是 S2 的替代入口（沒有自動掃帶時人工找），也被 S4c 的第②步當工具呼叫。

### 庫存有兩個來源，S2 只涵蓋其中一個

`wire-rundown-cases/` 範例①② 裡混了兩種來源，兩者都進同一份庫存，但取得方式完全不同：

| 來源 | 長相 | 取得方式 |
|---|---|---|
| 通訊社網站素材 | `RT1453 伊朗威脅…BITE`、`AP4675107`、`IN-02TU` | **S2** 輪詢 AP／Reuters Connect／CNN Newsource |
| 側錄大段摘要（CNN／NHK…） | `CNN 151328`＋講者＋該段摘要；`NHK 222009 內部慘況`＋摘要 | **S2b**——6 碼是側錄檔時間戳（[`02-tc-offset-filename`](02-tc-offset-filename.md)），逐字稿在「掃帶歐印萬」資料夾，**網站上沒有，輪詢永遠拿不到** |

側錄在本 repo 目前只有**下游消費端**的規則（[`07-bite-assistant`](07-bite-assistant.md) 方式 2 用 6 碼側錄掐 BITE、[`01-shared-folders`](01-shared-folders.md) 的資料夾位置），**上游的「轉譯成摘要進庫存」這一段從來沒落地**。使用者 2026-07-30 定調：那是獨立子系統 S2b，先前討論過做法但未實作，列入待辦，未來要併進來源庫。

### 庫存層與決策層的差別（先前搞混過，記在這裡）

**S3 是庫存，S4 是決策，兩者是上下層、不是兩種樣板。**

| | S3 庫存層 | S4 決策層 |
|---|---|---|
| 收什麼 | 當班收到的**全部**素材，不篩選 | 從庫存**挑出**今天要開的幾則 |
| 回答什麼問題 | 「我們手上有什麼」 | 「今天做哪幾則、每則配哪些素材、誰來做」 |
| 有無稿頭 | **沒有**——它不提案，只歸檔 | **有**——稿頭就是這則新聞的切角提案 |
| 現在長什麼樣 | 逐則進 Notion（`reuters/02`）／定時掃帶產出的純文字清單（「晚班交接」，範例①②） | **還沒有**——S4 未建。`common/11` 的 `{SLUG} 稿單.txt` 是 **S4c 補充素材**的產物，只是共用同一種稿單格式 |
| 未來 | Supabase `assets` 表，用 Dashboard 瀏覽 | Dashboard 上的選題與開稿分配 |

「稿頭只有一邊有」不是格式怪癖，是層級不同的必然結果。
