# Codex CLI hooks 驗證與 S2 掃帶轉接規劃

日期：2026-09-23  
驗證環境：Windows、`codex-cli 0.154.0`  
範圍：只在本 scratch 目錄建立 PoC；`E:\GitHub\TVBS-AIHunter` 僅唯讀檢查，未修改任何檔案。

## 結論

Codex CLI 目前有可用的 `PreToolUse` hook，能在 `apply_patch` 實際寫檔前拒絕工具呼叫，並把拒絕原因送回 agent。這一點已用真正的 `codex exec` runtime 實測，不只是閱讀文件或直接呼叫 hook 腳本。

不過它不是 Claude Code `Edit`／`MultiEdit`／`Write` 的逐欄位相容介面。Codex 對檔案 patch 的 canonical hook 輸入是：

```json
{
  "tool_name": "apply_patch",
  "tool_input": {
    "command": "*** Begin Patch\n*** Update File: protected.txt\n..."
  }
}
```

因此不能把現有 `s2_gate_guard.py` 原封不動掛上去：它目前只接受 `tool_name` 為 `Edit`／`MultiEdit`，並從 `tool_input.file_path`、`old_string`、`new_string` 或 `edits` 判讀。需要一層很薄、但必須正確解析 patch 的 adapter。

另有一個重要差異：Codex 把 Claude 的 Edit、MultiEdit、Write 用途收斂到 `apply_patch`。現有 PostToolUse／Write「完整重寫後清 gate lock」的語意不能只靠 matcher 還原，必須額外定義何謂完整重寫，或先不做自動清鎖，保留 build lint／`gate-clear` 的既有清鎖路徑。

## 1. 實測驗證

### 1.1 PoC 檔案

PoC 放在：

```text
poc-workspace/
├── .codex/
│   ├── hooks.json
│   ├── protect_hook.py
│   └── hook_events.jsonl       # 實跑後產生的 stdin 紀錄
├── protected.txt
├── mock_responses_server.py    # 離線、決定論模型端點，只供本驗證
└── run_project_hook.py         # 重現本次離線 codex exec 測試
```

scratch 根目錄本身的 `.codex` 在本執行沙箱中有唯讀 ACL，因此 PoC 放到同一 scratch 下的 `poc-workspace`，並從該目錄啟動 Codex。這是本測試容器的限制，不是 Codex hooks 的限制。

`hooks.json` 的核心設定如下：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "python -X utf8 .codex/protect_hook.py",
            "commandWindows": "python -X utf8 .codex/protect_hook.py",
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

hook 將收到的 stdin 原樣 append 到 `hook_events.jsonl`；當 `tool_name == "apply_patch"` 且 `tool_input.command` 含 `protected` 時，stdout 印出：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "POC_DENY: filenames containing 'protected' may not be edited."
  }
}
```

hook 正常以 exit code 0 結束；deny 是由 JSON 決策表達，不是以非零 exit code 表達。

### 1.2 實際執行與結果

先嘗試直接連 OpenAI 執行 `codex exec --json --dangerously-bypass-hook-trust ...`。CLI 能啟動並載入 hook trust 設定，但本工具沙箱封鎖 `wss://api.openai.com/v1/responses` 與 HTTPS，重試後仍無法取得模型回應；見 `default_model_run.jsonl`。因此這次無法把「外部實際模型」算入已驗證範圍。

為了驗證 CLI 本身的 hook pipeline，而不是只測 Python 腳本，我在 localhost 起了一個最小 Responses API fixture，由它決定論地回傳一次 `apply_patch` tool call。Codex 仍是實際安裝的 `codex.exe`，實際完成了：解析模型 tool call → 執行 `PreToolUse` → 拒絕 tool → 把拒絕結果放回下一個模型 request → 產生 agent message。fixture 不會自行讀寫受保護檔案。

結果記在 `project_hook_run.jsonl`：

```text
Command blocked by PreToolUse hook: POC_DENY: filenames containing 'protected' may not be edited.
```

下一個模型回合收到的 tool output，並回傳：

```text
MODEL_RECEIVED_TOOL_OUTPUT: Command blocked by PreToolUse hook: POC_DENY: ...
```

驗證後 `poc-workspace/protected.txt` 仍為：

```text
ORIGINAL
```

所以已實測確認：

- hook 在檔案副作用前執行。
- deny 真的擋下 patch。
- agent 的下一輪上下文收到拒絕原因。
- `Edit|Write` alias matcher 會匹配 `apply_patch`，而 stdin 仍回報 canonical `tool_name: "apply_patch"`。
- `--dangerously-bypass-hook-trust` 適合由外部已審核 hook 的無人值守 launcher 使用；CLI 會在事件流留下明確警告。

### 1.3 實際觀察到的 PreToolUse stdin

第二次、由專案 `.codex/hooks.json` 載入的實際 payload 是：

```json
{
  "session_id": "01a0cd80-6eda-7660-80cd-c657faed3387",
  "turn_id": "01a0cd80-6f14-72b1-9573-0fc817fc1c83",
  "transcript_path": "C:\\Users\\CodexSandboxOffline\\.codex\\sessions\\2026\\09\\23\\rollout-2026-09-23T17-02-21-01a0cd80-6eda-7660-80cd-c657faed3387.jsonl",
  "cwd": "...\\scratchpad\\codex-hook-poc\\poc-workspace",
  "hook_event_name": "PreToolUse",
  "model": "gpt-5.5",
  "permission_mode": "bypassPermissions",
  "tool_name": "apply_patch",
  "tool_input": {
    "command": "*** Begin Patch\n*** Update File: protected.txt\n@@\n-ORIGINAL\n+CHANGED\n*** End Patch"
  },
  "tool_use_id": "call_edit"
}
```

欄位名稱和型別與官方文件一致：共同欄位有 `session_id`、`transcript_path`、`cwd`、`hook_event_name`、`model`；turn-scoped 欄位有 `turn_id`；PreToolUse 再加 `permission_mode`、`tool_name`、`tool_input`、`tool_use_id`。

`transcript_path` 有值，但官方明確說 transcript 格式不是穩定 hook 介面，不應讓 adapter 依賴其內部格式。

### 1.4 deny 回傳格式

本次實測成功的是目前建議格式：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "拒絕原因"
  }
}
```

handler exit code 為 0。官方文件另列兩個相容方式，但本 PoC 未逐一實測：

- 舊格式：`{"decision":"block","reason":"..."}`
- exit code 2，並把阻擋原因寫到 stderr

對 S2 建議沿用 `permissionDecision` JSON，因為現有 `s2_gate_guard.py` 已產生同一形狀，且理由欄位結構清楚。

### 1.5 matcher 規則

已實測：

- matcher 是 regex 字串。
- `matcher: "Edit|Write"` 能攔到 Codex `apply_patch`。
- 實際 stdin 仍是 `tool_name: "apply_patch"`，不會變成 `Edit` 或 `Write`。

官方文件另說明：

- `apply_patch`、`Edit`、`Write` 都可作為 apply_patch 的 matcher alias。
- 精確匹配可寫 `^apply_patch$`。
- `"*"`、空字串或省略 matcher 代表匹配所有該事件。
- Bash／unified exec 的 canonical matcher 是 `Bash`。
- MCP 工具用完整名稱，例如 `mcp__filesystem__read_file`，可使用 regex。

建議正式設定用 `^apply_patch$`，因為 adapter 明確只處理 Codex patch 格式；若想保留可讀性，可用 `Edit|Write`，但必須記住這只是 matcher alias，payload 不會是 Claude Edit schema。

官方依據：

- Hooks：https://learn.chatgpt.com/docs/hooks
- Codex config reference：https://learn.chatgpt.com/docs/config-file/config-reference

### 1.6 模型與環境限制（務必保留）

使用者指定「預設 gpt-6-sol」，但本機目前 `~/.codex/config.toml` 的實際預設是 `gpt-5.6-sol`；`codex debug models` 的本機 catalog 也沒有 `gpt-6-sol`，顯式使用時會出現 metadata fallback 警告。先前 scratch 既存紀錄還顯示 ChatGPT 帳號拒絕 `gpt-6-sol`，但那不是本輪重新連線成功的證據。

本輪對外連線又被執行沙箱封鎖，所以「正式 OpenAI provider + 指定 gpt-6-sol」沒有完成實測。最終 hook pipeline 實測使用 localhost fixture provider 與本機 catalog 中有直接 `apply_patch` tool schema 的 `gpt-5.5`。hook dispatch 位於 Codex runtime、與模型內容解耦，但仍應在正式主機上補一個 live canary，才能宣稱目標模型端到端驗證完成。

## 2. `s2_gate_guard.py` adapter 設計

### 2.1 建議邊界

新增一支很薄的 `s2_codex_gate_adapter.py`，不要把 Codex 相容邏輯塞進 `s2_gate_guard.py`。adapter 負責：

1. 從 stdin 讀 Codex hook payload。
2. 確認 `hook_event_name == "PreToolUse"` 且 `tool_name == "apply_patch"`。
3. 從 `tool_input.command` 解析 Codex patch grammar。
4. 對每個受影響檔案組出 Claude-style 參數，呼叫既有 `decide_edit(file_path, tool_input, session_id)`。
5. 任一檔案被拒絕就輸出 Codex deny JSON；否則 stdout 保持空白、exit 0。
6. 任何 payload／patch 解析錯誤依現行哲學 fail-open 或 fail-closed，必須由專案明確決策。安全閘用途建議對「看起來會動 JSON，但無法解析」fail-closed；完全非目標工具則放行。

概念 mapping：

```python
payload = json.load(sys.stdin)
patch = payload["tool_input"]["command"]

for change in parse_codex_patch(patch):
    file_path = resolve_against_cwd(change.path, payload["cwd"])
    claude_like_input = {
        "file_path": file_path,
        "edits": [
            {
                "old_string": hunk.removed_text,
                "new_string": hunk.added_text,
            }
            for hunk in change.hunks
        ],
    }
    reason = decide_edit(
        file_path,
        claude_like_input,
        payload.get("session_id"),
    )
    if reason:
        deny(reason)
```

這個 mapping 能保留目前五層判斷：

- gate lock、ENEX/ABC、NS/AP/RT 主要看 `file_path`，可直接沿用。
- batch category／tc 判斷會看到每個 hunk 的 removed/added 文字，可沿用 `_batch_tool_input_touches_fields`。
- 通用次數上限繼續使用 Codex 的 `session_id`；這個欄位已實測存在。

### 2.2 patch parser 必須處理的情況

不要只用 regex 搜尋第一個 `*** Update File:`。至少要處理：

- 一個 patch 內多個檔案；任何一檔 deny，整個 apply_patch deny。
- `*** Update File:` 的多個 hunk。
- 相對路徑以 payload `cwd` 解析並正規化。
- `*** Move to:`／rename；來源與目的都要檢查，避免改名繞過檔名規則。
- `*** Delete File:`；removed text 應視為 old side，避免刪除受保護 JSON 繞過欄位鎖。
- `*** Add File:` 不等同 Claude Edit。若要維持現行語意，新增檔案應走 Write policy，不應無條件套用 Edit 鎖。
- 拒絕 `..` 越界、絕對路徑歧義與重複 path header。

最好抽出純函式 `parse_apply_patch(command) -> list[FileChange]`，用 fixture 做 table-driven tests。不要依賴 Codex transcript，也不要從 agent 文字猜 path。

### 2.3 PostToolUse／Write 清 lock 的語意缺口

現有 `s2_gate_guard.py` 在 Claude `PostToolUse/Write` 成功時清 lock；Codex 沒有同等的獨立 Write tool，成功 patch 仍回報 `tool_name: "apply_patch"`。

第一階段建議：

- 只移植 PreToolUse deny。
- 不因一般 apply_patch 成功就清 lock。
- lock 仍由 build lint 歸零或人工 `gate-clear` 清除。

若必須完全對齊，再加入一個明確、可測的 full-rewrite 判準，例如專用 `rewrite-file` helper 或 patch 覆蓋整份檔案的嚴格驗證。不要把任何成功 apply_patch 都當 Write，否則一次局部 patch 就會誤清安全鎖。

## 3. launcher 轉接規劃

### 3.1 參數對照

現行核心：

```powershell
claude -p $prompt `
  --permission-mode bypassPermissions `
  --model $Model --effort $Effort `
  --mcp-config $McpConfig `
  --add-dir $Repo --add-dir $StateDir `
  --output-format stream-json --verbose
```

Codex 方向：

```powershell
codex exec $prompt `
  --json `
  -C $scratchCwd `
  --sandbox workspace-write `
  --add-dir $Repo --add-dir $StateDir `
  --model $CodexModel `
  -c "model_reasoning_effort=$Effort" `
  --dangerously-bypass-hook-trust
```

但不能機械替換，還要處理：

- `codex exec` 沒有 Claude 的 `--mcp-config` 同形參數；S2 browser MCP 必須移到 Codex profile/config，或由 launcher 用 `-c mcp_servers...` 注入並鎖定版本。
- Claude `--disallowedTools`、`--strict-mcp-config`、`--disable-slash-commands`、`--setting-sources` 沒有一對一旗標，要以 Codex profile、exec policy／rules、功能設定與最小化 MCP 清單重建。
- 無人值守時不要依賴互動 trust UI。可先部署並人工 trust 固定 hash；或 launcher 在啟動前驗證 hook/config hash，再帶 `--dangerously-bypass-hook-trust`。
- 若 `-C` 保持每日 scratch 目錄，Codex 不會自動載入 TVBS repo 的 `.codex/hooks.json`。選項是：在受控 Codex profile 定義 hook、launcher 用 inline hook config、或改以 repo 為 `-C` 並把 scratch/state 加為 writable dir。後者會改變目前依賴 cwd 的 transcript／暫存行為，要單獨驗證。
- 本機 PowerShell execution policy 會攔 `codex.ps1`；本次需用 `codex.cmd` 或實際 `codex.exe`。生產 launcher 應明確解析可執行檔，不要依賴 PowerShell alias resolution。
- `--dangerously-bypass-approvals-and-sandbox` 只應在已有外部 OS sandbox 的環境使用。正式 S2 應優先用 `--sandbox workspace-write` 加精確 `--add-dir`；本 PoC 使用 bypass 是因巢狀 Windows sandbox 的 `CreateRestrictedToken` 在測試容器內失敗。

### 3.2 split session 與 exit code

現有 core/platform split manifest 流程可保留，但每段把 `claude @sessionArgs` 換成共同的 `Invoke-CodexS2` wrapper。wrapper 應回傳：exit code、thread id、stdout JSONL path、stderr path、最後 agent message。

不要把「exit code 0」當完成證據；目前 state/receipt 驗證仍應保留。hook deny 本身不必讓整個 `codex exec` exit 2：agent 可能收到理由後改走正確批次路徑並成功完成，這正是期望行為。

## 4. 輸出格式與下游影響

### 4.1 Claude stream-json 與 Codex `--json`

兩者都是 JSONL，但 schema 不相容。

Claude 現行 parser 期待：

- `row.type == "result"`，內含 `session_id`、`total_cost_usd`、`usage`。
- `row.message.content[]` 裡的 `type == "tool_use"`，含 `name`／`input`。
- `~/.claude/projects/<sanitized-cwd>/*.jsonl` transcript，每個 message 有 usage 與 timestamp。

本次實際觀察到 Codex stdout 事件：

- `thread.started`，thread id 在 `thread_id`。
- `turn.started`。
- `item.started`／`item.completed`；常見 item type 由工具而異，例如 `command_execution`、`file_change`、`agent_message`、`error`。
- `turn.completed.usage`，本版欄位為 `input_tokens`、`cached_input_tokens`、`cache_write_input_tokens`、`output_tokens`、`reasoning_output_tokens`。

Codex 沒有 Claude `result` record，也沒有本次可見的 `total_cost_usd`。`cached_input_tokens` 不能直接假裝成 Claude 的 `cache_read_input_tokens` 而不標 schema/provider。

### 4.2 stdout/stderr 必須分流

現行 `*> $runLog` 會把 stdout 與 stderr 混在一起。本次實跑證明 Codex stderr 會包含 hook trust 警告、transport 診斷與內部 error；混進後檔案不再是純 JSONL。

建議：

```powershell
& $CodexExe @codexArgs 1> $runJsonl 2> $runStderr
```

JSON parser 只讀 stdout；stderr 另外保留作診斷。若需要即時監看，寫一層 process wrapper，而不是再把兩條 stream 合併。

### 4.3 必改的 parser

`s2_round_manifest.py::_read_stream_log`：

- 從 `thread.started.thread_id` 取 Codex thread id。
- 從 `item.*` 取 tool name/input，並用 item id 去重 started/completed。
- 從 `turn.completed.usage` 取 token usage。
- `total_cost_usd` 改 nullable，或由獨立價格表計算並把估算來源/version 寫入。
- platform operational trace 要能從 Codex `command_execution.command`／MCP arguments 找到，不再讀 Claude `tool_use` block。

`s2_token_metrics.py`：

- 現在直接讀 Claude transcript schema，不能指向 Codex rollout 後繼續使用。
- 建議第一版直接解析 `codex exec --json` stdout；工具次數以 unique item id 計數，usage 以 turn.completed 彙總。
- Phase timing 目前靠 transcript timestamp。Codex stdout 事件在本次輸出沒有 timestamp；若要保留階段分鐘數，launcher wrapper 必須在收到每一行時加 receive timestamp，或接受第一版只有 call count、沒有 phase minutes。
- 官方文件說 hook 的 `transcript_path` 格式不穩定，因此不建議把 rollout JSONL 當長期契約。

Gemini 429 fallback 診斷：目前用 Claude `tool_result` 行數與特定錯誤字串估算，Codex 版必須另寫；若 Codex 不再走 Anthropic/Gemini provider，這段應依 provider 分支停用，而不是誤解析。

### 4.4 `_輪次紀錄.txt` 的影響

`Write-Run` 的 TSV 格式與 START／DONE／DIAG／CRASH 事件本身由 PowerShell launcher 產生，且 DONE 的新增則數、txt 是否存在主要由 state/output 檔判定，所以基本格式可以維持不變。

需要改的是 detail：

- START 記 `runtime=codex`、Codex model、reasoning effort、sandbox/profile/hash。
- split session manifest 的 `transcript_session_id` 應改名或新增 `codex_thread_id`，避免把不同產品的 id 混為一談。
- token metrics 失敗仍維持不影響主流程，但 DIAG 要明確寫「Codex parser 尚未支援的事件」，不能靜默產生 0。
- raw log 檔名建議改 `.jsonl`，stderr 用 `.stderr.log`，不要都叫 `.txt`。

## 5. 測試改寫建議

保留所有現有 `decide_edit` unit tests；它們是業務規則本體，不需重寫。新增：

1. Adapter unit tests：單檔、多檔、多 hunk、rename、delete、add、路徑正規化、category/tc 改值與只改其他欄位。
2. Hook contract subprocess tests：Codex stdin → adapter → `permissionDecision: deny`；放行 stdout 空白；爛 JSON／未知 tool 的 fail policy。
3. CLI integration test：像本 PoC，用決定論本機 Responses fixture 讓 `codex exec` 真正發出 apply_patch，斷言檔案沒變且下一 request 含 deny 原因。
4. 一次正式 provider canary：在部署主機與目標模型跑 protected fixture，補齊本次因網路限制未驗證的部分。
5. Launcher DryRun tests：確認參數、cwd、add-dir、hook source、MCP profile、stdout/stderr 分流。
6. JSONL golden tests：Claude 舊 log 與 Codex 新 log 各一份，驗 manifest receipt、thread id、usage、tool count、錯誤事件。

## 6. 工程量估計

以下是「可灰度上線」而不是只讓單一 happy path 跑通的估計，一人日以約 6 小時有效工程時間計：

| 項目 | 估計 | 內容 |
|---|---:|---|
| launcher 替換 | 2–3 人日 | CLI 參數、cwd/add-dir、sandbox/trust、MCP profile、split session、stdout/stderr、DryRun |
| hook adapter | 1.5–2.5 人日 | patch parser、Claude-like mapping、multi-file/path safety、deny output；若做 full-rewrite 自動清鎖再加 1 人日 |
| 測試改寫 | 2–3 人日 | unit、subprocess contract、local fixture integration、正式 provider canary、launcher regression |
| 下游 log 解析 | 2.5–4 人日 | manifest parser、token metrics、tool 去重、usage/cost schema、phase timing 策略、golden fixtures |
| 合計 | 8–12.5 人日 | 不含實際五站完整掃帶觀察期 |
