## 1. 中間暫存檔一律直接寫 scratch-dir 絕對路徑，禁止先落 repo 根目錄再搬

**⛔ 這是硬規則，不是建議**：batch/list/detail 這類本輪中間檔（`batch.json`／清單快照／
卸載檔整理結果等），**開檔當下就寫到 `s2_state.py scratch-dir --mmdd {晚班起始日}`
印出的資料夾裡**，不准先落在 repo 根目錄再搬過去。

- **2026-08-13 D7 起，你的工作目錄一開場就是本班 scratch 夾**（launcher 設好才叫你）——
  相對路徑落檔（`ns_list.json` 這種寫法）天然就落在對的地方，這是最省事的合規方式。
  呼叫 repo 腳本一律用絕對路徑或先 `cd "E:/GitHub/TVBS-AIHunter"`（你本來就這麼做）。
- 需要確認路徑時再跑：
  ```
  python scripts/s2_state.py scratch-dir --mmdd {晚班起始日}
  ```
  本輪剩下的暫存檔都寫進這個資料夾，路徑記住就不用每次重跑。
- ⛔ **以下三種變體都算違規**（0812-2200／0813-0100／0813-1000 三輪各撞一次實錯，
  每輪多花約 3 分鐘在「發現寫錯地方→搬檔→確認 git status」上）：
  1. `Read`＋`Write` 先讀到 repo 根目錄再另存到 scratch dir。
  2. PowerShell 先 `New-Item`/`Set-Content` 到 repo 根再 `Move-Item`。
  3. `python -c` 先寫檔到當前工作目錄（通常是 repo 根）再 `mv`／`Move-Item` 搬移。
- 這條跟 13c §0-2 的「卸載檔算本輪中間檔，事後搬進 scratch-dir」不衝突——本條是把
  「事後搬」提早成「一開始就別落錯地方」，兩條同時成立：能一開始就寫對路徑的，不要
  再繞去 repo 根目錄；卸載檔那種由工具層自動決定落點的，才照 13c §0-2 事後搬。

## 2. `set-category` 改「一站一批」，取代舊「一輪一次」

13c §2 原規則（2026-08-12 立規）要求 `set-category`／`update-entry`／`add-batch` 三個
寫入指令**一輪各只叫一次**。實測發現「一輪一次」在長輪次（含建檔輪、補掃窗較長的輪次）
會把分類累積到收工前才送出，中途沒有查核點，一旦某站分錯要等到很後面才發現。

**新規則：`set-category` 改成「一站一批」**——NS／AP／RT **各站掃完各下一次**
`set-category --pairs`，不必等三站全掃完才一次送出。

- `update-entry`／`add-batch` 仍照 13c §2 原規則，**一輪一次**（不受本條影響）。
- **收尾允許 ≤1 次補刀**：三站都跑完、`topic_review` 看過整張表、發現同義／同事件
  需要合併分類之後，**最多再補一次** `set-category --pairs` 做收斂調整。
  超過這一次補刀就是踩線——真的還有錯，累積到下一輪或用 `needs-review add` 記錄，
  不准為了「這則也要改」再叫第三次。
- 順序仍是**先累積草稿、看過沒問題才送出**（13c §2 ①b 稽核前置那條不變）：
  一站的分類清單在心裡／草稿湊齊，確認沒問題才下 `set-category`；不是「掃到一則
  就下一次指令」。

## 3. 分類工具新用法：`--compact` 為每輪預設用法

`list-topics`／`topic_review` 新增 `--compact` 旗標，**每輪預設用這個**（省掉開新
中主題前、render 前各要讀一次全表時的 head/tail 雙讀）：

```
python scripts/s2_state.py list-topics --compact
python scripts/s2_topic_review.py --file "<狀態檔>" --compact
```

- 開新中主題前（13c §2 的 `list-topics` 那步）、render 前檢視中／小分題
  （13c §2a-2、`s2_scan_prompt.md` 步驟 5 的 `s2_topic_review.py`）**都改用
  `--compact` 版本**，不必再另外讀一次未壓縮輸出。
- 需要看小分題明細時，`list-topics` 仍可加 `--subs`（`--compact --subs` 可並用）。

另外新增 `show --uncat`，用來查「有 id 但分類欄位還沒填」的項目：

```
python scripts/s2_state.py show --uncat
```

批次 `add-batch` 後想確認有沒有漏 `set-category` 的則，用這個查，比逐則 `get` 快。

## 4. 檢查 scratch raw 一律用 `s2_batch_prep.py` 的 inspect/unwrap 子指令

⛔ **不要每輪即興檢查暫存 raw 檔**——0813 三輪各用了不同的臨時工具（`Read` 整檔
讀進 context、PowerShell 切片、`python -c` 寫一次性腳本），三種變體都算違規，
理由跟 13c §2「不准自己寫 python 讀狀態檔」同一套（呼叫次數與臨時腳本自傷風險）。

**改用 `s2_batch_prep.py` 的兩個子指令**：

```
python scripts/s2_batch_prep.py inspect <raw檔路徑> [--ids A,B] [--fields f1,f2] [--limit N] [--site ns|ap|rt] [--lengths]
    # 摘要模式印筆數＋id＋標題行；讀取時自動卸殼，不整包讀進 context
    # --lengths 只印各欄位字數不印內容（檢查摘要 150 字上限就用這個，不要自己寫 python 數）
python scripts/s2_batch_prep.py unwrap  <raw檔路徑> [--out 檔]
    # 卸殼成裸陣列另存 _unwrapped.json；無殼會明講「原樣複製」不報錯
python scripts/s2_batch_prep.py search  <raw檔路徑> --contains 關鍵字 [--field script|story|head|all]
    # 列出命中項 id＋命中欄位＋前後片段
    # ⚠️ --contains 搜的是「欄位的內容」，不是欄位名稱
python scripts/s2_batch_prep.py snapshot <raw檔路徑> --site rt --checkpoint 0817-1600
    # 壓成純文字稽核快照（預設落 _audit_{site}_{HHMM}.txt，同目錄）
python scripts/s2_batch_prep.py compare --raw <raw檔> --batch <batch檔> [--site rt]
    # 只印差異：raw 有 batch 沒有／batch 有 raw 沒有／batch 缺欄位／batch 內重複 id
python scripts/s2_batch_prep.py dedup-check <raw檔> --ids A,B[,C] [--site ns] [--fields script,desc]
    # 兩則以上逐字比對，判斷是不是同一則的不同版本
```

- 🔴 **要確認「站方到底有沒有給稿」，用 `inspect --lengths`，不要用 `search`**
  （2026-08-18 A13 實錯）：`search --contains script` 是拿 **script 這五個字母去搜
  欄位的「內容」**，不是問「有沒有一個叫 script 的欄位」——正常的稿子內文裡本來就
  不會出現 "script" 這個字，所以它回 0 命中是**正確行為**，不代表沒有稿。
  查欄位在不在、有多長，一律 `inspect --lengths`（不指定 `--fields` 會把該筆
  所有文字欄位連同 AP 的 `script.nitf`／`caption.nitf` 一起列出來）。
  - ⛔ **「工具說沒有」不等於「站方沒給」，退 §1b 之前先換一支工具確認**。
    0818-2200 就是這樣賠掉的：AP API 其實成功、15/15 筆都有完整 SHOTLIST／
    SOUNDBITE，但當時的 `--lengths` 有 bug 沒列出 `script`（已修）、`search`
    又被誤用，兩個訊號都像「沒有稿」，於是整站退 §1b **逐則開了 14 個詳情頁**，
    12 則燒掉 89 次呼叫／10.5 分（前一輪同站 14 則只要 31 次／5.7 分）。
  - `--lengths` 現在會分清楚 **`<無此欄位>`**（真的沒有）與
    **`<欄位存在但非文字>`**（欄位在、只是不是文字，例如 `shots` 是陣列）——
    看到後者不要當成站方沒給。

- **`compare` 在 `add-batch` 之前跑**最划算：它一次查完「有沒有漏收」「有沒有
  來源不明的 id」「有沒有整批漏帶 `src_text`」（13d §5 那個踩過兩次、合計 145 則
  的坑）。乾淨就只印一行，不會佔 context。
- **判斷「這兩則是不是重複」一律用 `dedup-check`，不要自己寫 python 算 `a==b`。**
  它把四種情況分開講：逐字相同／只差空白／**只差 HTML 標記**（NS 的 script 夾
  `<p>`、`<b>`，同一則的不同剪輯版常常只差在這）／真的不同（並指出剝掉標記後
  第幾字起不同）。0817-2200 那輪 NS 去重就是缺這個工具，花了 5 次臨時 `python -c`。
  ⚠️ 它**只回答機械問題**——要不要當成重複、留哪一則，是編輯判斷，工具不做也不猜。
  id 打錯或找不到會直接失敗中止，不會默默只比得出來的那幾則。
- **`snapshot` 不覆寫舊檔**——快照的價值就是「當時長什麼樣」，覆寫等於靜默銷毀
  稽核依據。要另存就給不同的 `--out`。
- 兩個都吃 `--site`：**RT 的 id 欄位是 `code` 不是 `id`**，不給 `--site` 會退回
  通用猜測。
- **AP 清單檔（ES 形狀）自動看穿 `_source`**（2026-08-18 起）：`inspect`／`search`／
  `snapshot`／`dedup-check` 的 id 一律解成 `AP<editorialid>`（跟 state 對得起來的那個），
  `--fields headline` 這類欄位也直接取得到——不必再自己剝 `_source`。

- 用途是**檢查**（結構、筆數、有沒有拆對層），不是 13c §1a 開頭撤回的那套強制
  `raw.json → dump → entries.json → build` 三步流程——那條「規定要用整套流程」的
  規則仍然撤回，`browser_evaluate` 抽完直接累積 `batch.json` 仍是現行主路徑。
  `inspect`／`unwrap` 只在**需要檢查某份 raw 檔**時才叫，不是每輪必經步驟。
- 兩個子指令由另一支 agent 同步實作中；若指令還不存在或報 `unrecognized arguments`，
  照 13c §2「腳本連續失敗 2 次」退化：記進回報，當輪改最小必要的一次性讀取繼續，
  不卡住，收工後在回報裡註明工具還沒到位。

## 5. batch 每筆**必帶 `src_text`**（站方原文），漏帶當場回補

`add-batch` 的每一筆都要帶 `src_text`（抽取白名單瘦身後的站方原文，13b §543）——
它是事後離線查證的**唯一依據**，漏帶就得重開瀏覽器。0812-2200（65 則）與
0813-1200（80 則）兩輪整批漏帶，都是組 batch 時漏了這個欄位。

- `add-batch` 會當場印 ⚠️ 列出漏帶的 id；稽核對「單一 batch 檔整批漏帶」直接 🔴。
- **看到警告當輪就回補**（瀏覽器還開著、素材最新，成本最低）：
  ```
  python scripts/s2_state.py update-entry --batch <檔>
  ```
  批次檔每筆只要 `{"id": "...", "src_text": "..."}` 就是純回補原文，不動稿子本體；
  單筆也可用 `update-entry --id X --src-text-file <檔>`。

## 6. `browser_evaluate` 大回應落檔連結＝資料遺失，不是「檔案存哪了」

**⛔ 這是硬規則，不是建議**：`browser_evaluate` 回傳太大時，Playwright MCP 不會把
資料寫進任何實體檔案，而是回一個 `[Evaluation result](./檔名.json)` 這種**看起來
像檔案連結的字串**。**那個檔案不存在**——連 MCP 自己的 output-dir
（`D:\Downloads\PlaywrightMCP`）都沒有落地。

- **2026-08-13 2200 輪 NS 站實錯**：一次抓 60 則清單，回應太大，MCP 回了
  `[Evaluation result](./ns_probe_2200.json)`。agent 把它當成「檔案真的存在、只是
  不知道路徑」，花約 9 分鐘全機找檔（含 `find /` 全磁碟掃描、120 秒 timeout，加上
  多次 60 秒 `find`），一無所獲。**同一輪又踩第二次**（`ns_full_2200.json`），
  再損失約 4 分鐘。最後靠「分段回傳」才解掉——證明資料從頭到尾就沒寫到磁碟，
  不是找錯地方。
- ⛔ **看到 `[Evaluation result](./檔名)` 這種連結，一律視同資料遺失，禁止去找
  那個檔**。它不在工作目錄、不在 `D:\Downloads\PlaywrightMCP`、也不在任何地方——
  找了只是白燒時間。
- **正確動作（2026-08-14 訂正，蓋過「分段貼回對話」）**：
  1. 清單先小欄位、不含 `script`（13c §1a-3 已寫）。
  2. 只要收的那批全文，**一次** `browser_evaluate`，並設 `filename` 為 scratch-dir
     **絕對路徑**（例如 `{scratch}/ns_full_{HHMM}.json`）——結果落磁碟，不要
     把稿全文倒進對話。
  3. 若仍出現 `[Evaluation result](./檔)`：視同遺失，**立刻重跑上一步**（縮小
     `size`／只帶 NEW id），**禁止**去找那個假檔（0814-1200 又找了一次）。
  4. ⛔ **禁止把 script 全文分多次 evaluate 貼回 context**（0814-1200 NS 連打 5 次
     詳情，再花約 7 分鐘在對話裡組 49 則中文稿——分類階段 10 分就是這樣肥的）。
     真的必須切段：每段用 `filename` 落到 scratch，下一段不要再帶前段全文；
     組 `batch.json` 讀磁碟檔，不要靠對話裡殘留的陣列。
- ⛔ **任何情況下禁止用 `find /` 做全磁碟搜尋**（單次就燒 2 分鐘 timeout，而且找的
  東西根本不存在）。要找本輪暫存檔，只准看兩個地方：**目前工作目錄**（＝本班
  scratch 夾）與 `D:\Downloads\PlaywrightMCP`；兩處都沒有就是不存在，回頭用
  `filename` 重抓，不要再往下找第三個地方。

## 8. 開工只精讀 13c＋本檔；NS body 用固定配方

**0814-1200 實錯**：開工讀了標示「規格草案」的 V1 `13.md` 全文、`13c` 讀了兩次，

  **真的要查那一節**（素材行／分類／時區）時才翻**對應節**，禁止整本從頭讀。

  ```js
  () => {
    const tok = JSON.parse(localStorage.getItem('newsourceSession')).token;
    const body = {
      bundlesOnly: false, date: new Date().toISOString(),
      facets: {contentType:[], videoTypes:[], categories:[], digitalCategories:[], videoFormats:[]},
      filters: {contentType:{}, videoTypes:{}, categories:{}, digitalCategories:{}, videoFormats:{}},
      from: 0, language: ['en','es'], scriptOnly: false, size: 30,
      sort: {order: 'ascending', type: 'relevancyDate'}, term: null
    };
    return fetch('https://newsource-content-api-530.ns.cnn.com/api/v3/stories', {
      method: 'POST',
      headers: {'Content-Type':'application/json', authorization:'Bearer '+tok},
      body: JSON.stringify(body)
    }).then(r => r.text()).then(t => {
      const d = JSON.parse(t.split('\n').find(l => l.includes('"stories"')));
      return (d.stories.content || []).map(it => ({
        id: it.alternateIds && it.alternateIds.bitcentralId,
        ft: it.footageType, dur_ms: it.duration, created: it.createdDate,
        desc: (it.description || '').slice(0, 200),
        has_script: !!(it.content && it.content.bitcentral && it.content.bitcentral.script)
        // 清單這輪不要帶 script；全文另一次、用 filename 落到 scratch（§6）
      }));
    });
  }
  ```

  - `size` 可改 30／60，**不要**改 `facets`／`filters`／`sort`／`language` 的形狀
    （自拼 `sort:[{createdDate}]` 就是 400）。
  - 先這包小欄位 → `diff` → 只對 NEW id 再打一次帶 `script` 的查詢，`filename`
    寫進 scratch（§6）。

## 9. 素材行不要加「摘要：」、不要自創分隔

`raw_entry` 格式（`s2_parse.py`）：

```
{時段標記} {代碼} (備註) ▎摘要正文 ▎畫面：… ▎BITE：…|無BITE。 ▎MM:SS
```

- ⛔ **第一個 `▎` 後面直接寫摘要正文**，禁止加 `摘要：`／`摘要:` 標籤
  （0814-1200 約 31 則 NS 這樣寫，`fields` 空、`parse_ok=false`——入庫不擋，
  但結構化欄位整批沒了，下一輪若要修又是一輪 token）。
- `畫面：`／`BITE：`／`無BITE。`／時長**各佔一個 `▎` 段**，不要把「無BITE」黏在
  畫面段尾。
- 時段標記只用 `△▲■◆`（09:00–14:00 用 `◆` 沒錯），不要自創其他符號。

## 10. 工具層防護：臨時 `python -c` 檢查 json 會被 hook 直接攔下（2026-08-18 起）

launcher 掛了 PreToolUse hook（`scripts/s2_bash_guard.py`，MASTER D9）：
**Bash／PowerShell 指令裡出現 `python`/`python3`/`py` 的 `-c` 內聯程式、
且碰到 `.json` 檔或 `-s2-state.json` 狀態檔時，呼叫會被拒絕**。

- 被攔到不是錯誤，是指路——**deny 訊息裡就有可直接貼的替代指令**
  （`s2_batch_prep.py inspect/search/compare/dedup-check/snapshot` 或
  `s2_state.py show/…`），照著換工具重下即可，**不要**改寫成其他變體
  （heredoc、先寫 .py 檔再跑、PowerShell `ConvertFrom-Json`）去繞——那還是 §4 違規，
  遙測看得到。
- 純計算（`python -c "print(...)"` 不碰檔）、`.txt`、呼叫 repo 標準腳本都不受影響。
- 字數檢查（摘要 150 字上限）用 `inspect --lengths`，不必也不准自己寫 python 數。
