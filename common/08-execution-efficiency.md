## ⛔ 鐵則：不得用會消耗額度的操作做測試（2026-07-21 使用者明令）

**這條優先於本文件所有其他準則，也優先於任何「先驗證再繼續」的直覺。**

- **不得為了偵錯或驗證流程而反覆點擊 Download。** 下載是有實際成本的動作，不是可重複的測試手段。
- 任何會消耗**帳號額度／點數／授權次數**的操作（Reuters Connect 點數、AP 下載計量等），**預設一律先問使用者**，不得自行判斷「這支應該不扣點」。
- **頁面標示不是可靠的免扣點依據。** 2026-07-21 實測：以「FREE TO ME」為由挑素材測試，**點數仍被扣**（452 → 446，共 6 點）。素材頁顯示 `HD 60fps (MP4) = Included` 同樣不足以判定不扣點（尚未釐清，見 [`09-known-issues.md`](09-known-issues.md#規則由來案例歷史紀錄)）。在查明前一律從嚴。
- 驗證下載是否成功，**只用不產生新下載的方式**：`read_network_requests` ＋ 檔案系統檢查。**不要「再點一次看看」。**
- 若確實必須驗證下載流程，先向使用者確認**要拿哪一支素材測、可否接受成本**。

## 前置檢查：瀏覽器自動下載權限（2026-07-21 訂定）

自動化批次下載能否運作的**前提**，不在站台也不在帳號，而在 Chrome 的內容設定。

- 開始批次下載前，確認該站台（`reutersconnect.com`、`newsroom.ap.org`、`newsource.ns.cnn.com`）已加入 `chrome://settings/content/automaticDownloads` 的**允許清單**。Chrome 對「同一網站連續觸發多個自動下載」有內建封鎖，預設只放行**第一個**，之後全部靜默丟棄。
- ⚠️ **改完設定後必須重新 `navigate` 頁面才生效**——Chrome 內容設定不會套用到設定前就已載入的頁面。在舊頁面上直接重點會繼續失敗，且極易誤判成「白名單無效」或「自動化根本無法下載」。2026-07-21 實測：重新導航後 4/4 全部成功。
- **判斷線索**：若「第 1 段 API 回 200、帳號點數有扣，但 CDN 請求不發出且檔案沒落地」，**優先懷疑瀏覽器端下載封鎖**，不是站台或帳號問題。（Reuters 下載是兩段式：先 `api/download/video/...` 取簽章網址，再由 `videobroadcast.cdn.thomsonreuters.com/...` 實際傳檔。）
- 使用者**手動點擊永遠成功**（真實使用者手勢不受此限），所以「使用者點得動、AI 點不動」正是這個症狀，不代表流程有問題。

## 準則

- **多用批次工具，但 batch 裡不要盲猜座標**：連續的「搜尋→點擊→等待」動作盡量用單次批次呼叫（例如 `browser_batch`）送出，只有下一步真的需要先看結果才拆開。**但 batch 內要點擊的元素，一律用當次 `find` 實際回傳的 ref，不要跨素材沿用前一筆算好的固定座標**——同一流程不同素材的頁面版面可能差幾十像素（多一個下載選項、多一行限制文字）。若 batch 裡包含「看不出有沒有真的觸發」的動作（例如送出下載），batch 跑完仍要依下方「下載確認用檔案系統」與「重試階梯」驗證一次，不因包進 batch 就跳過。
- **截圖只在必要時用**：不要每點一次、每個batch跑完就截圖確認一次。結果可預期的操作（關閉彈窗、收合/展開卡片、送出下載、按下已知位置的按鈕）不需要截圖驗證，直接接下一步；只有在結果真的無法透過其他方式判斷、且下一步動作真的需要先看到這次操作的結果時（例如第一次遇到陌生UI、不確定點擊是否命中、需要讀取畫面上的資料），才截圖或zoom。
- **找不到的元素別靠zoom亂猜座標**：畫面上一時看不到要點的圖示/按鈕，screenshot或zoom一次沒找到，就直接改用 `find` 工具語意定位，不要重複多次zoom不同區域去猜——這比連續zoom更省token也更準（實例見 [`09-known-issues.md`](09-known-issues.md#cnn-newsource) CNN Newsource ≡Q圖示案例）。
- **`navigate` 或回到列表頁之後，用座標點擊前先重新截圖**：橫幅廣告、通知彈窗等元件常在換頁/回首頁時重新出現，把版面往下推幾十像素，沿用前一次畫面記下的座標會點歪甚至誤觸其他連結、跳轉到不相關頁面。換頁後第一次要用座標點擊時，先 screenshot 確認目前版面，不要假設版面跟上次相同。
- **下載確認改用檔案系統檢查**：判斷下載是否成功，優先用 shell 指令檢查目標資料夾（例如 `Get-ChildItem D:\Downloads`）是否出現對應檔案＋檔案大小，不要用截圖確認。**「瀏覽器沒有跳出下載提示」不是失敗的證據**——CNN Newsource 交給背景下載程式、AP 是伺服器端非同步排隊，兩者都不會出現在 Chrome 的下載清單，檔案會直接落到 `D:\Downloads`。**看不到瀏覽器反應時先查檔案系統，不要枯等、更不要重點一次**（重點會消耗額度，違反上方鐵則）。
- **檢查下載結果只查詢有關的檔名，不要列出整個 Downloads 資料夾**：用 SLUG／關鍵字／副檔名／時間範圍限定查詢（例如 `Get-ChildItem D:\Downloads -Filter "{SLUG}*"` 或篩選 `LastWriteTime`），避免把資料夾裡大量無關甚至私人的檔案也列出來，既浪費 token 也有隱私疑慮。**一律用 `-Filter` 精確比對，不要用寬鬆 regex**（2026-07-21 實例：用 `-match 'PY-03MO|13'` 查一支素材，`13` 命中大量無關甚至私人檔名，等於把整個資料夾攤開）。
- **簡單、確定性的檢查優先用腳本/工具驗證，不要用人工手算，也不必為此派專門的驗證用子 agent**：字數、TC 範圍是否超出片長、SB 五行格式是否齊全、總長度加總、檔案雜湊值等，都是可以用 `python_repl`、`ffprobe`、shell 指令直接算出來的確定性結果，比人工估算或另外啟動一個驗證 agent更快更準，也不會遇到 agent 延遲/沒回傳的問題。
- **驗證必須「解析實際標記」且「有能力亮紅燈」，不得用固定行號猜位置（2026-07-21 訂定）**：這是上一條的必要條件——用腳本檢查不代表檢查有效。
  1. **依實際標記解析區塊**（`【】`、`##`、`SUPER:`、`BAR n`、`SB` 等），**不要用固定行號／固定陣列索引抽文字**。稿件多一行空行、SUPER 多一位人物，固定行號就整段抽錯或漏抽，卻照樣回報 PASS。（實例：`罕見四胞1600` 的臨時檢查漏驗兩行 SUPER 與 BAR4。）
  2. **交付前自問「這個檢查如果規格真的不合，會不會 FAIL？」** 答不出來就代表沒驗到。PASS 只有在檢查確實涵蓋目標區塊時才有意義。
  3. **不得拿不涵蓋該流程結構的工具充數**。各流程規格不同（CTV 的 BAR 是 17–18 全形字 vs SOT 的主標／次標 18–19 字；換算方式與空格／標點規則則是共用的），用錯模式等於沒驗。[`scripts/validate_sot.py`](../scripts/validate_sot.py) 以 `--mode sot`／`--mode ctv` 區分，跑之前先確認模式對得上流程。
  4. **臨時手寫檢查不能當交付依據**。正式流程有指定的驗證工具就用它；工具不涵蓋時，先把檢查補進工具（連同一個會 FAIL 的反例確認它真的抓得到），不要在對話裡臨時寫一段只跑一次的腳本充當關卡。
  5. **驗證器不得逼寫稿改壞內容（2026-07-21 訂定）**。工具與流程文件衝突時，先判斷**哪一邊才是使用者要的成品**，再決定改哪一邊。若「照驗證器過關」會讓內容變差——砍掉翻譯、湊碎句、刪事實——那是**工具或規格有錯**，應停下來回報並修工具，**不得為了拿到綠燈而降低成品品質**。（實例：`爆紅浣熊1600` 的驗證器把 SB 中文當固定單行，代理為了過關把完整譯文壓成殘句、又硬塞 1 秒碎句充數，被使用者退回。）
  6. **改動驗證器一律要跑反例測試**：[`../scripts/test_validate_sot.py`](../scripts/test_validate_sot.py)。新增規則時同時補一個「會 FAIL 的反例」，證明它真的擋得住——這是第 2 點「會不會 FAIL」的自動化版本。
  7. **規則異動不溯及既往：舊稿可以驗，但不要改（2026-07-21 訂定）**。規格改版後，已交付或已歸檔的舊稿跑驗證會亮一批 `[FAIL]`，那是**新舊規格的差異，不是舊稿有錯**。**驗證本身可以做**（有助於了解改版的影響範圍，也可當回歸樣本），但**不得因此回頭修改舊稿**——尤其 [`auto-script-learning/cases/`](auto-script-learning/) 底下的歷史存檔，它們是校稿機制的比對基準，改了就失去證據價值。只有使用者要求重出某篇舊稿時，才依現行規則重寫並**另存新檔**。
- **工具回傳明顯異常的結果不要採信，要重新驗證**：例如時間碼超出影片實際總長、抽取畫面時應該有內容卻回傳0張等，這類結果代表快取或工具本身出錯，不要順著異常結果繼續往下做判斷，應重新執行該步驟或改用其他方式（例如重新對單一影片直接分析/抽幀）交叉確認。
- **頁面文字只抓一次**：每筆素材的限制/逐字稿只抓一次，抓到後直接寫進對應的文稿txt檔，不要重複抓取，也不要把整段原文貼進對話（除非使用者要求看原文）。
- **不重複貼長清單**：已編號的素材清單或任務清單，完整貼過一次之後，後續只用編號/代號引用，不要整份重新貼出。
- **下載卡住的統一重試階梯（2026-07-21 訂定，本 repo 唯一權威，各流程文件不另訂門檻）**：
  1. 下載沒出現 → 直接重點一次，用檔案系統檢查結果。
  2. 仍無檔案 → **第2次就查 `read_network_requests`（篩 `download` 關鍵字）**，不要盲目再點 2-3 次賭運氣——network log 能直接看到請求是否真的送出、HTTP 狀態碼多少，比重複點擊＋輪詢更快定位問題。
  3. 確認失敗後依情境收尾：**批次類流程**（外電批次下載、找AP照片多張）→ 跳過該筆、繼續下一筆，全部跑完再回頭補試一次，仍失敗則在最終彙整表標 ⚠️；**單支任務**（自動寫稿CTV、自動掐SO）→ 直接回報使用者，不無限重試。
  4. accessibility tree 等更花 token 的診斷工具，留到 network log 也看不出問題時再用。
- **下載落地路徑：預設 `D:\Downloads`，但不寫死不驗證**：各流程文件寫的 `D:\Downloads` 是預設值；若該資料夾沒出現檔案，以工具實際回報的落地路徑為準（部分瀏覽器自動化工具會落在專屬暫存資料夾），不要因為預設路徑沒有就判定下載失敗。
- **Windows 端列舉/改名檔案一律用 PowerShell，不要用 Bash `ls`/`mv`**：`D:\Downloads` 常有中文或emoji檔名，Git Bash 下常編碼錯誤、誤判路徑；改用 `Get-ChildItem`／`Rename-Item`／`Copy-Item` 才穩定可靠。
- **寫入 `.txt` 檔案一律用 CRLF（`\r\n`）換行，不要用純 LF（`\n`）（2026-07-24 訂定）**：本 repo 所有落地 `.txt` 的產出（原始文稿、ASR逐字稿、素材清單、完成文稿、初步分析段落表等）最終多半在剪接電腦用 Windows 記事本開啟；記事本對純 LF 換行不會正確分行，整份文字會擠成一段，使用者端看起來像「沒有分行」。用工具/腳本寫檔時明確以 CRLF 換行（例如 Python 用 `open(path, "w", newline="\r\n")` 或內容裡直接用 `\r\n` 分行；PowerShell `Set-Content`/`Out-File` 預設已是 CRLF，不需額外處理），不要依賴可能只寫入 `\n` 的預設 text mode。
- **（2026-09-05 增訂）「完成文稿」`.txt` 一律再加 UTF-8 BOM（`utf-8-sig`）**：所有寫稿流程（CTV／SOT／業配／準連等）落地的 `完成文稿.txt` 統一為「CRLF 換行＋UTF-8 BOM」，避免剪接端 Windows 程式以 cp950 誤判編碼出現亂碼；Python 用 `open(path, "w", encoding="utf-8-sig", newline="\r\n")` 一次到位。其他 `.txt`（原始文稿、ASR、素材清單等）維持 CRLF，BOM 可有可無。
- **長時間背景工作要主動回報進度，不要等使用者追問**：影音分析、批次下載等單一步驟若執行超過約90秒（尤其是被系統轉入背景執行時），應主動說明目前在等哪一支素材／哪個步驟、預期還剩什麼，不要悶著跑到使用者自己來問「卡在哪」才回報。
- **有落地上傳步驟的流程，若過程中產生了 ASR.txt，一律隨完成檔一起上傳（2026-07-24 訂定，初步分析流程不適用——它不產生 ASR，見 [`03-preliminary-analysis.md`](03-preliminary-analysis.md)）**：自動寫稿(CTV)／自動寫稿(SOT) 等流程若因為缺 TC 而呼叫 `video_analyze` 落地了 `ASR.txt`，存檔位置就直接放進該流程的上傳目的地資料夾（跟完成文稿、原始文稿同一層），不要另外存到暫存工作目錄之後就漏了上傳這一步。**但這條只規範「已經產生的 ASR 要不要一起上傳」，不改變「該不該呼叫 `video_analyze`」本身**——找 TC 仍照各流程既有優先序（官方文稿 TC／既有雙語逐字稿／YouTube 字幕優先，最後才 ASR），不得為了讓這條規則有東西可傳而多跑或提前跑轉譯，本末倒置。**掐BITE助手／CNN掐Bite 不適用本條**：這兩個流程本來就明文不落地、不上傳任何檔案（純對話輸出五行 SB），中途暫存的 ASR 只是省 token 的內部快取，不因本條規則變成需要上傳。
