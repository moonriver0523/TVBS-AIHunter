# 執行效率（省Token）準則

執行本 repo 任何流程（外電批次下載、掐BITE助手、搜尋外電素材RT/AP、找AP照片、自動寫稿(CTV/SOT)、掃帶入庫、自動掐SO 等）時的瀏覽器自動化操作，一律遵守以下準則，目標：瀏覽器工具呼叫減少約60~75%、網頁snapshot回傳量減少約80~95%、整體token使用量降低約70~90%。

各流程另有步驟級省 Token 規則（與本文件併用）：
- CTV：[`cnn/01-auto-script-writing.md`](../cnn/01-auto-script-writing.md)
- SOT：[`common/06-auto-script-sot.md`](06-auto-script-sot.md)
- 掐BITE／CNN掐Bite：[`common/07-bite-assistant.md`](07-bite-assistant.md)、[`cnn/02-clip-bite.md`](../cnn/02-clip-bite.md)
- 掃帶入庫／自動掐SO／搜尋 RT·AP／找AP照片：見對應 `reuters/*`、`ap/*` 文件開頭的省 Token 節

## 準則

- **多用批次工具**：連續的「搜尋→點擊→等待」動作盡量用單次批次呼叫（例如 `browser_batch`）送出，不要每一步都拆成單獨呼叫。只有下一步動作真的需要先看結果才拆開。
- **截圖只在必要時用**：不要每點一次、每個batch跑完就截圖確認一次。結果可預期的操作（關閉彈窗、收合/展開卡片、送出下載、按下已知位置的按鈕）不需要截圖驗證，直接接下一步；只有在結果真的無法透過其他方式判斷、且下一步動作真的需要先看到這次操作的結果時（例如第一次遇到陌生UI、不確定點擊是否命中、需要讀取畫面上的資料），才截圖或zoom。
- **找不到的元素別靠zoom亂猜座標**：畫面上一時看不到要點的圖示/按鈕，screenshot或zoom一次沒找到，就直接改用 `find` 工具語意定位，不要重複多次zoom不同區域去猜——這比連續zoom更省token也更準（實例見 [`09-known-issues.md`](09-known-issues.md#cnn-newsource) CNN Newsource ≡Q圖示案例）。
- **`navigate` 或回到列表頁之後，用座標點擊前先重新截圖**：橫幅廣告、通知彈窗等元件常在換頁/回首頁時重新出現，把版面往下推幾十像素，沿用前一次畫面記下的座標會點歪甚至誤觸其他連結、跳轉到不相關頁面。換頁後第一次要用座標點擊時，先screenshot確認目前版面（尤其確認有沒有新出現的橫幅），不要假設版面跟上次相同（2026-07-20 實例：SE-003SA 搜尋時因此連續兩次點歪、誤跳轉到 Planner 頁）。
- **下載確認改用檔案系統檢查**：判斷下載是否成功，優先用 shell 指令檢查目標資料夾（例如 `Get-ChildItem D:\Downloads`）是否出現對應檔案＋檔案大小，不要用截圖確認。
- **檢查下載結果只查詢有關的檔名，不要列出整個 Downloads 資料夾**：用 SLUG／關鍵字／副檔名／時間範圍限定查詢（例如 `Get-ChildItem D:\Downloads -Filter "{SLUG}*"` 或篩選 `LastWriteTime`），避免把資料夾裡大量無關甚至私人的檔案也列出來，既浪費 token 也有隱私疑慮。
- **簡單、確定性的檢查優先用腳本/工具驗證，不要用人工手算，也不必為此派專門的驗證用子 agent**：字數、TC 範圍是否超出片長、SB 五行格式是否齊全、總長度加總、檔案雜湊值等，都是可以用 `python_repl`、`ffprobe`、shell 指令直接算出來的確定性結果，比人工估算或另外啟動一個驗證 agent更快更準，也不會遇到 agent 延遲/沒回傳的問題。
- **工具回傳明顯異常的結果不要採信，要重新驗證**：例如時間碼超出影片實際總長、抽取畫面時應該有內容卻回傳0張等，這類結果代表快取或工具本身出錯，不要順著異常結果繼續往下做判斷，應重新執行該步驟或改用其他方式（例如重新對單一影片直接分析/抽幀）交叉確認。
- **頁面文字只抓一次**：每筆素材的限制/逐字稿只抓一次，抓到後直接寫進對應的文稿txt檔，不要重複抓取，也不要把整段原文貼進對話（除非使用者要求看原文）。
- **不重複貼長清單**：已編號的素材清單或任務清單，完整貼過一次之後，後續只用編號/代號引用，不要整份重新貼出。
- **失敗重試要精簡，卡住時提早查network log（2026-07-20 修訂）**：下載失敗（例如 Reuters 常見的503）先直接重點＋用檔案系統檢查結果；**若第1次重試後檔案仍未出現，第2次就直接查 `read_network_requests`（篩 `download` 關鍵字），不要盲目再點2-3次賭運氣**——network log 能直接看到下載請求是否真的送出、HTTP狀態碼多少，比重複點擊+輪詢更快定位問題（2026-07-20「油輪觸雷1200」RT下載案例：盲點4次才查network log，其實一查就看到請求已送出，只是還在處理）。accessibility tree等更花token的診斷工具才留到network log也看不出問題時再用。
- **Windows 端列舉/改名檔案一律用 PowerShell，不要用 Bash `ls`/`mv`**：`D:\Downloads` 常有中文或emoji檔名，Git Bash 下常編碼錯誤、誤判路徑；改用 `Get-ChildItem`／`Rename-Item`／`Copy-Item` 才穩定可靠。
- **長時間背景工作要主動回報進度，不要等使用者追問**：影音分析、批次下載等單一步驟若執行超過約90秒（尤其是被系統轉入背景執行時），應主動說明目前在等哪一支素材／哪個步驟、預期還剩什麼，不要悶著跑到使用者自己來問「卡在哪」才回報。

## 已知問題（症狀→解法）

以下是特定站台/工具才會出現的邊角案例，**不需要每次執行流程前預先讀過**——執行中真的撞到對應症狀、或真的需要接觸表這種備援手段時，才去查 [`09-known-issues.md`](09-known-issues.md) 對應章節：

| 撞到的症狀／需要的手段 | 查這裡 |
|---|---|
| CNN Newsource 搜尋框按 Enter 沒反應／下載檔案時間戳記異常 | [CNN Newsource](09-known-issues.md#cnn-newsource) |
| 瀏覽器座標點擊點不中／`find`工具過載／下載檔案沒出現在預期資料夾 | [瀏覽器自動化](09-known-issues.md#瀏覽器自動化) |
| 多支影片同時跑 `video_analyze` 被安全分類器拒絕 | [video_analyze](09-known-issues.md#video_analyze) |
| 需要一次瀏覽整支片縮圖（接觸表） | [接觸表（Contact Sheet）](09-known-issues.md#接觸表contact-sheet) |

**Why：** 2026-07-20 使用者審視一次RT/AP批次下載+掐BITE任務的實際token消耗，發現主因是每步截圖、每筆素材整段原文貼進對話、清單重複輸出、以及503失敗時的重截圖+查log迴圈；使用者因此明確設定量化的效率目標，並要求往後同類任務都套用這套精簡流程。同日稍晚多次任務（「追殺川普1730」、「酷澎難滅1700」）陸續補了多條卡點修正，原本準則清單膨脹到18條，其中約7條屬於特定站台/工具才會出現的邊角案例（例如CNN Newsource時間戳記、搜尋框Enter失效、座標點擊失效、find過載、video_analyze分類器拒絕、接觸表Fontconfig問題），卻因為本文件被每個流程強制套用而每次都要讀過——評估後拆分到 [`09-known-issues.md`](09-known-issues.md)，本文件只留下不管什麼任務都適用的預設行為準則，避免規則越堆越多反而拖慢每次執行的讀取成本。

**How to apply：** 執行本 repo 任何流程時的瀏覽器操作，預設套用本文件準則；沒有特別情況不需要每次向使用者重新確認。
